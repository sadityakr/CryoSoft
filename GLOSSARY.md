# CryoSoft Glossary

Canonical definitions of project terms. When a human and an agent (or two
agents) talk about CryoSoft, these are the meanings in force. If a term is
used in code, docs, or conversation with a different meaning than defined
here, the glossary wins; if a new recurring term appears, add it here in the
same commit that introduces it.

## Architecture layers (bottom to top)

| Term | Definition |
|---|---|
| **Layer (L0–L6)** | The layered architecture: L0 Driver → L1 Virtual Instrument → L2 Station/Config → L3 Orchestrator → L4 Procedure → L5 Data Manager → L6 Session Manager, with the GUI on top. Lower layers never import higher ones; the machine-checked rules live in `pyproject.toml` under `[tool.importlinter]`. |
| **Driver (real driver)** | L0. A Python class that talks to one physical instrument over PyVISA (GPIB/serial). Constructor takes exactly one required argument: the VISA resource string. Lives in `cryosoft/drivers/`, imports nothing from CryoSoft except `core.exceptions`. |
| **Sim driver** | A drop-in simulated twin of a real driver (`sim_` filename prefix), used for all testing without hardware. Must expose exactly the same public API as its real twin — enforced by `tests/test_conformance.py`. |
| **Virtual Instrument (VI)** | L1. A device-role abstraction (magnet, temperature controller, measurement) built on one or more drivers. VIs never import drivers; the Station constructs driver objects and injects them into the VI constructor as a `drivers` dict (dependency injection). All VIs subclass `BaseVirtualInstrument` and use `__init__(self, drivers, **init_params)`. |
| **Measurement method** | L1. A self-describing measurement VI (subclass of `MeasurementInstrumentBase`) that declares its own GUI knobs and output shape and implements one uniform lifecycle, so a generic procedure can run any of them without knowing the instrument or protocol. Self-description: `measurement_parameters` (name→`ParamSpec`, the single owner of the knobs), `measurement_data_keys` (the raw-sample array names `take_reading()` returns, each ending `_array` — see **Measurement quantity**), and `measurement_scalar_columns` (the mean/error pair per quantity, plus optional extras like `n_valid`). Lifecycle: `data_arrays(params)` (declared array lengths for the same params `initiate_measurement` receives), `initiate_measurement(**params)` (arm the hardware; `@control(panel=False)` where GUI-exposed; deliberately not named `initiate` — the plain lifecycle `initiate()` on a measurement VI is a harmless connection check, so Initiate-All can never start a source current), the argument-less `take_reading()` (one datapoint: for every quantity, the raw-sample array padded to the declared length plus its mean and standard error, always exactly the declared keys — a VI that can return fewer points pads with `float("nan")` and reports the true count in a scalar column), `standby()` (safe-off), and the optional **`reading_setters`** declaration (default `{}`; see **Reading loop**). `DCMeasurementBase` fixes the DC-resistance shape (`readings_per_point` samples of `voltage_V`/`current_A`); the full written standard lives in `MeasurementInstrumentBase`'s docstring and is machine-enforced by `test_conformance.py` (declaration validity, lifecycle presence, sim round-trip, the mean/error/array convention). |
| **Measurement quantity** | L1. The mean/error/array naming convention every measurement VI follows for each quantity it reports (e.g. `"voltage_V"`), derived mechanically by `MeasurementInstrumentBase.quantity_columns()`: the raw samples under `"{quantity}_array"` (in `measurement_data_keys`), the mean under the bare `"{quantity}"` — what the GUI plots — and the standard error of the mean under `"{quantity}_error"` (both in `measurement_scalar_columns`, dtype `"float"`). The VI computes the mean/SEM itself, over the valid (non-NaN) samples, via the shared `MeasurementInstrumentBase.mean_and_sem()` helper (`n=1` → SEM `0.0`; `n=0` → both NaN) — never the GUI, which only plots the scalar it's handed. `test_conformance.py` enforces the triple for every `_array` key on every measurement VI, and rejects a base quantity name that already ends `_array`/`_error`. |
| **Raw diagnostic block** | L1. A second, orthogonal self-description on `MeasurementInstrumentBase` for an instrument that returns far more raw data per reading than any single physical quantity, where the **measurement quantity** mean/error/array convention does not apply (no single mean makes sense across many mixed-unit channels). A VI declares `measurement_raw_blocks: ClassVar[dict[str, list[str]]]` (block name → ordered channel-label list, fixing the channel axis) and overrides `raw_block_row_counts(params) -> dict[str, int]` (row count per block, mirroring `data_arrays()`'s params-dependent role); `take_reading()` returns the block as a nested `rows x channels` list, NaN-padded on the row axis only when the instrument under-delivers (the channel axis never pads). The block's own `rows x channels` matrix is deliberately excluded from `measurement_data_keys`/`measurement_scalar_columns` so it never itself appears in a GUI plot-axis dropdown — a diagnostic/provenance record, not a plotted quantity. Its declared CHANNELS are, however, independently plottable: `SweepMeasureProcedure` derives one scalar column per channel (row axis reduced by a NaN-safe mean — the same "N readings at one measurement point" treatment `mean_and_sem` gives a quantity's own array column), added automatically to `live_plot_measurement_keys()` and `DataSchema.measurement_scalars`, with zero VI-side code — see `SweepMeasureProcedure._raw_block_channel_columns`/`measure()`. The one exception to the **loop axis** convention: `DataSchema.measurement_blocks` carries the `(n_loop1, n_loop2)` axis only when a reading loop is actually configured (`loop_shape != (1, 1)`) — with no reading loop, HDF5 storage is bare `(rows, cols)`, not `(1, 1, rows, cols)`; `SweepMeasureProcedure.measure()` squeezes the trivial axis away before saving, while a VI's own `take_reading()` always returns the block as a flat `rows x channels` list regardless. The shape it is built for is an instrument whose every reading is a wide record — a many-column diagnostic dump, or a frame whose rows and columns are pixels — where the block IS the datum and the scalar columns are derived from it. Self-description travels all the way to disk: `DataManager` writes the declared label list as the block dataset's own `channel_names` HDF5 attribute (column index → channel name) plus an `axes` attribute naming every dimension in order (e.g. `"sweep_point, row, channel"`, or `"sweep_point, loop1, loop2, row, channel"` when a reading loop is active) — a reader never needs to parse the `metadata` group's JSON `data_config` to know what a column means. Full text: `MeasurementInstrumentBase`'s docstring, "Raw diagnostic blocks", and `virtual_instruments/measurement/README.md`. |
| **Externally configured** | L1. A `configured_externally: bool` init param (default `False`) on `MeasurementInstrumentBase` (`devices.yaml`'s `init_params`, no per-subclass boilerplate) that splits ownership of an instrument's configuration between the vendor's own tool and CryoSoft: the external tool owns excitation, analysis, and routing parameters — `initiate_measurement()` MUST NOT write any of them, only accept the now-inert `measurement_parameters` (logged, never rejected) — while CryoSoft still owns the data path, triggering, reading, and saving (verifying connectivity with a true round trip, arming buffers/channel selection, reading back any value its own timing/decoding depends on). `standby()` MUST NOT overwrite the externally-owned source state; it only resets CryoSoft's internal arming state. Pairs with the declared `detach_when_idle` standard on `BaseVirtualInstrument` (`detach_when_idle` property, `is_attached()`, `_attach()`/`_detach()` — see **Availability**): an externally configured VI narrows `detach_when_idle` to `return self._configured_externally`, one line, and the base does the rest — born detached at the end of `__init__` (`self._detach()`), `ping()` (and so the inherited `initiate()`) verify-and-release automatically (reattach → true round trip → release), `initiate_measurement()` reacquires the session for the measurement window, and `standby()`'s `__init_subclass__`-wrapped release hands the session back the instant the VI's own safe-off commands return — so the operator can attach the vendor tool at any time between runs, with no VI-specific lifecycle code beyond the one-line declaration. Motivated by single-client instrument firmware (vendor tool and CryoSoft are mutually exclusive at the instrument); the full normative text lives in `BaseVirtualInstrument`'s docstring ("Detach-when-idle declaration"), `MeasurementInstrumentBase`'s docstring, and `virtual_instruments/measurement/README.md`. A supporting VI declares `externally_owned_parameters: ClassVar[frozenset[str]]` naming exactly the `measurement_parameters` the external tool owns; the `active_measurement_parameters` property (what the procedure form renders) and `reading_parameters` (what the reading-loop registry offers) both subtract it automatically whenever `configured_externally` is true, so a form never shows — and a reading loop can never write to — an inert excitation/analysis/routing knob, with zero per-VI GUI code. |
| **Reading loop** | The per-datapoint iteration a **generic sweep procedure** runs inside `measure()`: up to TWO generic **slots**, each a loopable parameter (see **`reading_setters`**) plus an ordered value list. Slot 1 (loop1) is axis 0 (outer), slot 2 (loop2) axis 1 (inner) of every measurement column's real **loop axis**. The auto-rendered "Reading loop" form group (shown above the measurement VI's parameter group whenever the station's reading path offers anything loopable) carries one structural `{slot}_parameter` drop-down per slot plus that parameter's values input — per-choice `{slot}_pick_{value}` checkboxes when the spec is enumerated, a `{slot}_values` comma-separated text field otherwise (currents). A slot with ONE value is a static setting (dispatched once at `initiate()`, trivial length-1 axis); with two or more it loops: the setter is dispatched as a `Command` through the Station before every reading at that axis index. Axis index → physical value is recorded in the run's HDF5 metadata as `procedure_params["loop1_values"]` / `["loop2_values"]`. Non-measurement VIs that took part get their `reading_safe_off` at standby/abort. A measurement VI with no setters simply has no loopable parameters — no group, no special case. |
| **`reading_setters`** | The VI-level declaration behind the **reading loop**: a `BaseVirtualInstrument` class attribute mapping a parameter name to the cheap setter method that reprograms just that quantity between readings (e.g. the DC VI's `{"current_A": "set_source_current"}`), paired with `reading_parameters` (the ParamSpec per loopable parameter — enumerated specs render as pick checkboxes, free specs as a value-list text field; a measurement VI inherits an implementation reading its `measurement_parameters`) and optional `reading_safe_off` (a method dispatched at standby/abort when a non-measurement VI took part, e.g. `open_all`). Declaring an entry is ALL a VI does — the "Reading loop" form group, the per-reading setter dispatch, the loop axis, and the metadata all follow automatically. Contract (machine-enforced by `test_conformance.py`): setters are real methods accepting the parameter under its own name and never change the reading's shape; measurement-VI keys are existing non-bool measurement parameters. |
| **Loop axis** | The real `(n_loop1, n_loop2)` array axis every **DataSchema** measurement scalar/array column carries in HDF5 when a **reading loop** slot is configured — `n_loop1`/`n_loop2` each `>= 1` (`1` = that slot is off/static). A measurement scalar (e.g. a quantity's mean) is stored `(n_sweep_points, n_loop1, n_loop2)`; a measurement array (raw samples) `(n_sweep_points, n_loop1, n_loop2, length)`. Column names are never suffixed — replaces the earlier "multiplexed columns" suffix scheme (`{name}__A{i}__B{j}`). Axis index → physical value lives in the HDF5 metadata as `procedure_params["loop1_values"]` / `["loop2_values"]`; `SweepMeasureProcedure._loop_shape` derives the axis lengths, `measure()` builds the per-datapoint grid, `DataManager` allocates/writes it. A **Raw diagnostic block** is the one exception: it carries this axis only when a reading loop is actually configured (`loop_shape != (1, 1)`), staying bare `(rows, cols)` otherwise. |
| **Station** | L2. The runtime registry of all VIs, built from a config directory by `build_station()`. The only layer that touches both VIs and (via config) driver classes. Dispatches system targets, measurement commands, and safety checks. |
| **Config** | A directory under `cryosoft/configs/<name>/` holding `devices.yaml` (drivers, VIs, wiring, safety limits, trend checks) and `monitor.yaml` (tick interval, error threshold, panels, gateway and spool switches). Configs are the single source of truth for addresses, limits, and mappings — never hardcode these. The YAML-only readers (`read_*()`, the **config-reader standard**: parse one file, return a fully defaulted plain value, never raise, import no class) live in `core/config.py`, the one module that documents every block; building a Station from a config is `core/station.py`'s `build_station()`. |
| **Shipped vs user config** | *Shipped* configs are the git-tracked, read-only baselines under `cryosoft/configs/`; the GUI never edits them (a safe fallback that cannot be corrupted). *User* configs are editable copies under `%APPDATA%/CryoSoft/configs/`, created by copy-on-edit (`ConfigCatalog.fork_shipped`). |
| **Config catalog** | `core.config_catalog.ConfigCatalog` — discovers shipped + user configs, forks shipped→user, and keeps a named **config version** history per user config (save/list/restore). |
| **Config version** | A saved snapshot of a user config under `.versions/<id>/` with a `meta.json` (label + timestamp). Every editor save creates one; restoring copies it back over the active files. |
| **Active config** | The config the app loads on launch, stored in `QSettings` as an identity (`ActiveConfig/name` + `ActiveConfig/source`), re-resolved to a directory at startup so a stale absolute path (e.g. from a deleted git worktree) can't point nowhere. Switching it warns, saves the session, and restarts. |
| **Startup fallback chain** | `build_station_with_fallback()` tries the active config, then its shipped baseline, then the always-loadable `sim_cryostat`, so a corrupted config surfaces a warning instead of crashing startup. Each candidate is checked by `validate_config_dir()` (a dry-run that imports classes and resolves driver refs without instantiating hardware). |
| **Orchestrator** | L3. The state machine that executes a procedure: it ticks, ramps system VIs toward targets, waits, triggers measurements, and enforces safety. Talks only to the Station. Monitoring runs in its tick loop, gated by `start_monitoring()`/`stop_monitoring()` — see **Monitoring (Orchestrator)**. |
| **Procedure** | L4. A declarative measurement sequence (e.g. field sweep, temperature sweep) subclassing `BaseProcedure`. Declares *what* to do via the four-method interface; the Orchestrator decides *how*. Procedures never import drivers or VIs. Most measurement procedures are **generic sweep procedures** (see below), so adding a measurement usually means adding a measurement VI, not a procedure. |
| **Claim** | The set of VI names a running procedure exclusively owns, declared via `claimed_vi_names() -> set[str] \| None` (`BaseProcedure`). The Orchestrator captures it once at run start into `_active_claims` and consults it, through the shared `_manual_action_admissible()` predicate, to decide whether a manual action submitted while the run is active may be admitted: a VI in the claim set is refused (naming the owning run), every other VI stays under manual control exactly as in IDLE. The gate covers both manual routes to an instrument — a front-panel action (`submit_vi_action()`, and the tick's drain of it) and RELEASING it (`Orchestrator.disconnect_instrument()`, which asks the same predicate rather than gating on state, so an unclaimed instrument can be handed back to its own front panel mid-run while a claimed one is refused `BLOCKED_CLAIM`; `connect_instrument()` stays IDLE-only, since a VI joining mid-run has no claim to consult and has bypassed the run's safety review). A VI inside the run's **Ramp scope** is refused a disconnect with its claim: hardware the run is physically moving is owned by it either way. Default `None` means "claim everything" — the safe default every procedure keeps (procedures stay exclusive in this iteration); narrowing is an explicit per-class opt-in, e.g. `TimeSeries` claims only its reading path (measurement VI + loop-slot VIs) so the operator can drive temperature/field by hand for the whole run. `_manual_action_admissible()` checks an **Instrument fault** FIRST, ahead of the claim rules — a faulted VI is refused even in IDLE, regardless of any claim. A second consumer reads the same declaration for a second purpose: `BaseProcedure._claim_initiate_commands()` builds one `initiate()` `Command` per claimed VI (every station VI when `claimed_vi_names()` is `None`), returned in `PhasePlan.claim_commands` and dispatched by `Orchestrator._start_run` before that plan's own `targets`/`commands` — so a claimed VI is always back in its standard operating state (e.g. a temperature controller's heater in closed-loop AUTO) before anything else in the run touches it, exactly as if the operator had pressed Initiate on it first. |
| **Generic sweep procedure** | L4. `core.procedure.SweepMeasureProcedure` — the "sweep one axis, run any measurement method" base, and the two axis procedures on it: `FieldSweep` ("Field Sweep") and `TemperatureSweep` ("Temperature Sweep"). ONE procedure per sweep axis runs ANY station **measurement method**, chosen in the GUI via a **structural** `measurement_vi` parameter whose `choices` come from `Station.measurement_vi_names()`. The base owns measurement-VI selection, station-driven measurement-parameter merging, `DataSchema` assembly, per-datapoint validation, and the four-method loop; a concrete axis procedure supplies only its instrument roles (`role_parameters`, see **Role discovery**), the ramp targets, the axis read-back, and the settle times (its `_initial_system_targets` / `_step_targets` / `_standby_targets` / `_axis_readback` / `_initiate_wait_s` / `_step_wait_s` hooks). Replaces the former one-procedure-per-measurement classes (`FieldSweepDC`, `FieldSweepIV`, `TemperatureSweepDC`). |
| **Data Manager** | L5. Writes measurement data to HDF5 files. Standalone: knows nothing about instruments. Created by procedures in `initiate()`. |
| **Data reader** | L5. `core/data_reader.py` — the read-only analysis side of the file the **Data Manager** writes, and a standalone sibling of it, never a method on it (import-linter contract C17: nothing from the package but `core.events` and `core.exceptions`, so an analysis process imports it alone). `open_run(path)` returns a `RunHandle` context manager answering the **Run source** vocabulary over one run's HDF5 file. Reads stop at the *written prefix* — the writer pre-allocates every dataset to the full sweep length filled with NaN and trims only on a clean close, so the number of non-empty `timestamp` entries (the column the writer stamps last for each point) is the count of points actually measured. Every `ColumnInfo` carries a role from `COLUMN_ROLES`: `sweep_axis`, `measurement`, `raw_block` (see **Raw diagnostic block**), and `loop_axis` — the **reading loop**'s axes, which live in `procedure_params["loop1_values"]`/`["loop2_values"]` rather than in a dataset and are surfaced as the columns `loop1`/`loop2`. |
| **Run source** | The one read vocabulary for a run, wherever the run lives: `core/data_reader.py`'s `RunSource` `Protocol` — `n_points`, `list_columns()` (a frozen `ColumnInfo` per column: name, unit, dtype, role, stored shape, written length, path), `read_slice(column, start, stop, step)` (the leading sweep-point axis only; inner loop/sample/block axes come back whole), `summary_stats(column)` (a frozen NaN-aware `Stats`: count, min, max, mean, population std, first, last) and `read_metadata()` (exactly `RUN_METADATA_KEYS`, empty values rather than missing keys). `ColumnInfo` and `Stats` are JSON-safe both ways (`to_json()`/`from_json()`, a NaN rendering as `null`), so a result travels as a `Verdict.result` payload unchanged. `RunHandle` implements it over a run on disk and the **Run buffer** over the run in flight; a consumer depends on the protocol, never on which source it holds. |
| **Run buffer** | `core/run_buffer.py`'s `RunBuffer` — the run in flight as a **Run source**, so mid-run analysis needs no second API. Fed by the run's control-contract events (`start(RunStarted)`, `append(Datapoint)` per point, `finish(RunFinished)`) and read through the same `ColumnInfo`/`Stats` vocabulary as a finished file. `Datapoint.values` is exactly the `measured_data` mapping `DataManager.save_datapoint()` receives and `Datapoint.index` its `sweep_index`, so the buffer stores every column in the writer's own shapes; it adds the `timestamp` column itself, because the writer stamps that one rather than being handed it. Pure Python — no Qt, no h5py, no Station — and it exists because the writer owns the open HDF5 file: a reader outside the writing process sees only what has been flushed and cannot count on a handle that grows. |
| **Session Manager (L6)** | `cryosoft/session/` — the experiment-management layer between core and the GUI. `ExperimentManager` (the façade, `session/manager.py`) owns the **experiment** lifecycle, records every **run** automatically from the Orchestrator's **run manifests**, installs the experiment's **session envelope** on the Orchestrator, and supplies `experiment_context()` — a two-tier `{"setup": {...}, "experiment": {...}}` dict, see **Setup tier** — for stamping HDF5 files. Single writer of experiment state, exactly as the Orchestrator is the single writer to hardware — including `set_run_eln_link()`, the one path by which the publishing track (`session/eln/`) records a confirmed ELN entry on a run, in the open experiment or in one already closed. Imported by gui/main only; imports core downward (contracts C11/C12). |
| **GUI** | PyQt6 windows (monitor, procedure, instrument panels). Talks to the system only through the Orchestrator and Station APIs; never imports drivers or concrete VIs. |

## Runtime concepts

| Term | Definition |
|---|---|
| **Tick / tick loop** | The Orchestrator's periodic heartbeat (`tick_interval_ms` in `monitor.yaml`). Each tick processes queued GUI actions and advances the state machine/ramps; while **Monitoring (Orchestrator)** is active it also polls VI state and checks safety. |
| **Monitoring (Orchestrator)** | The hardware-touching part of the tick: polling every VI into `states_updated`, stall detection, and stale detection. The **Operational-status record** is NOT part of it — that is written on every tick, monitoring or not. OFF at construction so a fresh launch polls nothing until the instruments are initiated; started/stopped via `Orchestrator.start_monitoring()`/`stop_monitoring()` (the Monitor window's header toggle). `run_procedure()` auto-starts it; stopping is refused outside IDLE/ERROR. `shutdown()` stops the tick timer entirely (app exit / test teardown). |
| **Operational-status record** | The per-tick runtime troubleshooting signal: one JSON object emitted on `Orchestrator.operational_status` and appended as one line to `status.jsonl`, carrying the state and how long it has been held, the active run and setup identity, per-system-VI gap/rate/ETA, the active `Condition`s, a worst-of `RunFaultCode` verdict (whose `CRITICAL_FLAG` code names the DECLARED severity of whatever tripped, never one instrument's status word — see **Critical safety flag**), and the **Actor** and `request_id` of the last command the engine ACCEPTED (`null` until one has been; a refused command never displaces them, because the pair answers "who last got the engine to do something" and a refusal changed nothing). That `request_id` is the join key between this log and a client's own action trail — the same id sits on the **Agent feed**'s command, verdict and event records — so "the station started ramping at 03:12" and "runner-7 asked for it" are one query rather than two guesses. Its **standard** — the field list, the types, the schema version, the rule that an unknown value is `null` and that a field is only ever added — is the module docstring of `core/operational_status.py`; the log is the contract for its readers (`troubleshoot/status_reader.py`, `gui/diagnostics_window.py`). Written on EVERY tick, so a gap in `status.jsonl` means the process stopped ticking and nothing else — the property `troubleshoot status --max-age` gates on. Distinct from **Trend history**, which is a time series of readings rather than a diagnostic verdict. |
| **Trend history** | The tiered, disk-backed store of per-tick station readings, written every tick by `core.tiered_trend_logger.TieredTrendLogger` (called from the Orchestrator's monitoring tick) and queried through `core.trend_history` (`read_window`, `summarize`, `find_crossings`). Distinct from `status.jsonl` (the operational-status record — a diagnostic "why is this stuck" signal, not a time series) and from **MonitorHistory** (the in-RAM ring buffer feeding live plots, bounded to its own retention window, rehydrated from the raw trend tier at GUI startup). Measurement VIs are never persisted to any tier: `Station.last_state_flat()` — the flattener both the tiered writer and `MonitorHistory.record_flat()` consume — excludes them by design, so a trend panel on a measurement-VI key works live but is empty on any disk-backed window (see **MonitorHistory**'s docstring for this and the opposite-running boolean-field asymmetry). |
| **Trend tier** | One fixed-resolution level of the **Trend history** store: `raw` (per tick, ~3 days retention), `3min` (~9 days), `hourly` (~1 year). Downsampling from raw into the two aggregate tiers is live and incremental — `TieredTrendLogger` folds every sample into a pending bucket per tier and flushes it (min/max/mean/std/count) the instant a sample lands in the next bucket, not on a wall-clock timer. Which tier serves a requested time window is decided once, in `trend_history.pick_tier()`, and every caller (GUI trend panel, CLI, future agent tooling) inherits that choice rather than picking its own. |
| **Trend check** | A named temporal judgement over the **Trend history** store (`core/trend_checks.py`): a `TrendCheck` declaration (`name`, `keys`, `window_s`, `severity`, a pure `predicate` function) evaluated by `run_checks()` against `trend_history.summarize()` — never re-deriving mean/std or re-picking a tier, both of which stay `trend_history`'s job. A predicate returns a `CheckOutcome` whose `passed` is `True`/`False`/`None`, where `None` means "cannot tell" (an empty or never-persisted window — see `no_data_outcome()`), distinct from a definite pass or fail. Only a definite failure becomes a `Condition` (`to_condition()`/`conditions_for()`), published under the fourth **System condition** origin, `"trend"` — every check declared so far is `"advisory"` severity, so a trend check can report but never enforce: no VI is stood by, no run fails, and it cannot reach the Monitor banner (`monitor_window.py` filters `severity == "hold"`). It IS visible in two places: `status.jsonl` (every condition of any severity is serialized there, `operational_status.py`) and `DiagnosticsWindow`'s alerts panel — the latter via `build_operational_status()` turning every advisory condition into one `alerts` line generically, not via any trend-specific hook. `declared_checks()` is the standard's single registration point, and it reads its declarations from the CONFIG: each entry of the setup's `trends.checks:` list (`config.read_trends_config()`) becomes one `TrendCheck` through a builder named by its `kind` (`CHECK_KINDS`), so which channel is watched and where its band lies are setup facts in `devices.yaml`; adding a new KIND of judgement means one builder function plus one `CHECK_KINDS` row — no other module changes. Scheduling is deliberately NOT the Orchestrator's job: `cryosoft.core.trend_check_runner.TrendCheckRunner` is a small, independent `QObject` holding only a `Station`, running `declared_checks()` on its own slow timer (default 60 s, `trends.refresh_interval_s`) and publishing through `Station.publish_conditions("trend", ...)` — the Orchestrator learns of the result only by already reading `Station.conditions()` into its per-tick record, exactly as it does for every other origin. The one shipped kind is `channel_within_band(key, low, high, window_s)` — passes while the window's `min`/`max` stay inside the band — and the example config declares one instance on its temperature channel (`temperature_temperature_within_band`). A `predicate` receives both the window's `{key: KeySummary}` aggregates and its `{key: [(t, value), ...]}` series (`WindowedSeries`) — the second argument exists so a rate-of-change check can read `series[0]`/`series[-1]` without a new `KeySummary` field, which would leak a rate-specific need into an aggregate-statistics type. `trend_store_live` — is the store still receiving records at all, checked by reading the live trend-history file's mtime plus its newest record — is declared nowhere in `declared_checks()`: it exists to catch a wedged or crashed application, and a check scheduled on that same process's own timer cannot fire once the process is the thing that is hung, so it is evaluated only from `python -m cryosoft.troubleshoot trends`, a separate process, via `cryosoft.troubleshoot.engine.check_trend_store_live()`. |
| **System targets** | The `targets` field of a `PhasePlan`/`StepPlan`: a `{"vi_name": Target(...)}` mapping telling the Station which system VIs to ramp where. (Pre-Wave-2 this was a nested dict `{"vi_name": {"target": ..., "rate": ...}}`.) |
| **Measurement commands** | The `commands` field of a `PhasePlan`: an ordered `tuple[Command, ...]` the Station dispatches to measurement VIs. (Pre-Wave-2 this was a dict `{"vi_name": {"method": kwargs}}`.) |
| **Plan** | Umbrella term for the typed, frozen-dataclass currency in `core/plan.py` that procedures, the Orchestrator, and the Station exchange, replacing the old untyped dicts/tuples. | **Role discovery** | The standard by which a procedure finds the instruments it drives. A procedure names the *role* it needs — "the magnet this sweeps", "the temperature controller this sets" — never a configured instrument name, and declares each in `role_parameters` as a `core.procedure.RoleParam` (`candidates`, `description`, `required`). The candidates come from the Station's role accessors — `Station.vi_names_by_base(base_cls)` and its named fronts `magnet_vi_names()` / `temperature_vi_names()`, mirroring `measurement_vi_names()`, all in config order — because a procedure is hardware-blind (contract C6) and never imports a VI class. | **DataSchema** | `core/plan.py`. The declared HDF5 layout of one run: `sweep_columns` (dtypes, one value per sweep point, never looped — `unix_time`, system state, the sweep axis), `measurement_scalars` (dtypes, one `(n_loop1, n_loop2)` grid per sweep point — a quantity's mean/error, `n_valid`, …), `measurement_arrays` (per-point lengths, one `(n_loop1, n_loop2, length)` grid per sweep point — raw samples), and `loop_shape` (`(n_loop1, n_loop2)`, default `(1, 1)`; see **Loop axis**). | **Ramp / RampableVI** | Gradual, rate-limited approach to a setpoint (field, temperature, angle). VIs that support it implement the `RampableVI` interface (`start_ramp`, `advance_ramp`, `ramp_status`, `stop_ramp`) plus, optionally, the **ramp-introspection standard** below, the **no-motion phase declaration** (`no_motion_phases: ClassVar[frozenset[str]]`, default empty — the `ramp_phase()` values in which the value is MEANT to hold still while `RAMPING`, e.g. a switch-heater warm-up; carried in `Station.get_ramp_status()` and read by `core/stall_detection.py`, which itself knows no instrument) and `nominal_ramp_rate()` — the DECLARED rate a ramp from rest would use, in the same user units per minute, read from config alone so it can be answered before any run exists (a VI whose rate varies along the ramp reports its slowest, so a **duration estimate** built from it is never optimistic). |
| **Ramp-introspection standard** | `RampableVI`'s five optional, bus-free accessors — `ramp_value()`, `ramp_setpoint()`, `ramp_target()`, `ramp_rate()`, `ramp_phase()` — each with a safe `None` default, aggregated once per tick by `Station.get_ramp_status()`. The two setpoints are deliberately distinct: `ramp_setpoint()` is the **next setpoint**, the intermediate value the generator last commanded to the hardware (a magnet's current ramp-segment boundary, a temperature controller's setpoint for this tick), while `ramp_target()` is the **end setpoint** the ramp finishes at. Implementing the hooks is the ONLY thing a new rampable VI must do to appear on the **Ramp tracker** and in the operational-status record — no GUI or Orchestrator change. `ramp_setpoint()` must read the VI's own record of what it commanded (never poll the instrument) and must be cleared in `stop_ramp()` alongside the target. |
| **Ramp record** | `core/ramps.py`'s `RampRecord` — one frozen, dependency-free value object per ramp that is running RIGHT NOW (`ramp_status() == "RAMPING"`; a `TARGET_REACHED` or `IDLE` VI produces none), built by the pure `build_ramp_records()` from one `Station.get_ramp_status()` snapshot. Carries the VI's setpoint label/unit, current value, next setpoint, end setpoint, rate, sub-phase, the **owning run** (`None` for a manual ramp), a `stoppable` flag plus refusal reason, and a `stale` flag. Published every tick on `Orchestrator.ramps_updated` and cached for `Orchestrator.active_ramps()`. |
| **Ramp scope** | The set of system VIs whose ramps the active run OWNS: every VI it has sent a `Target` to, accumulated across `initiate()` and every `change_sweep_step()` (`Orchestrator._active_system_vis`, read through `_run_ramp_scope()`; `None` when no run is active, meaning the whole station). A run waits for, holds on pause, and stops on abort only the ramps inside its scope — `Station.check_ramps(vi_names)` and `stop_ramps(vi_names)` both take it. For every sweep procedure the scope is invisible: a run can only start from IDLE and a manual ramp leaves IDLE the tick it starts, so nothing outside the scope can be ramping anyway. It exists for a procedure that commands nothing and narrows its **Claim** (`TimeSeries`): the operator keeps ramping field or temperature from the front panel while the run records, and those ramps must neither stall its measurements nor be frozen when it ends. Ramp *advancement* is deliberately NOT scoped — `Station.advance_ramps()` steps every active ramp generator, in or out of scope, and every non-PAUSED state of the tick calls it (directly, or via `check_ramps()`); narrowing the advance would freeze an unwatched ramp mid-flight instead of merely not waiting for it, and a ramp only progresses when something calls it. |
| **Ramp tracker** | The Monitor window's Ramps sub-panel (`gui/ramp_tracker_panel.py`, the top half of the bottom-right quadrant): one row per **ramp record**, each with an Abort button calling `Orchestrator.stop_ramp(vi_name)` — the per-instrument counterpart of `abort_procedure()`, which holds that one instrument where it is and leaves every other ramp running. A ramp a procedure claims shows its owner and its Abort is disabled: stopping one VI mid-run would strand the run waiting on a setpoint it can never reach, so aborting the run is the correct stop there. |
| **`@monitored` / `@control`** | Decorators from `core/decorators.py` marking VI methods. `@monitored`: read-only, polled every tick into `get_state()`. `@control`: user-callable action, rendered as a button/input in the GUI instrument panel. Both are bare-or-parametrized and carry the **declaration** the GUI and the capability manifest read: `@monitored(unit=, description=, group=)` and `@control(scope=, params=, panel=, group=)`. Values are stored as plain strings on the function (contract C1 forbids `decorators.py` from importing `plan`); the VI base class resolves and type-checks them at class creation. |
| **Capability scope** | The tier a VI `@control` method belongs to: `"measurement"` (may appear in any plan) or `"operation"` (may appear only in operation plans; still a GUI control as before). Declared on the decorator, enforced at dispatch, conformance-checked. |
| **Declaration standard** | The rule that a VI describes its whole capability surface on its own decorators, because one declaration feeds the GUI widget, the tooltip, and the capability manifest an agent reads. Every `@monitored` method declares a `unit=` (SI unit label; `""` only for a genuinely dimensionless, boolean or string reading — never omitted, `None` means undeclared) and a one-sentence `description=`; every `@control` method that takes parameters declares a `ParamSpec` per parameter in `params=`. A measurement VI gets its two parameter-bearing controls for free: `MeasurementInstrumentBase.__init_subclass__` installs `measurement_parameters` as `initiate_measurement`'s specs and the matching single spec on each `reading_setters` setter, so the front panel renders the same units and drop-downs the procedure form does. Machine-enforced for every VI, present and future, by `test_conformance.py`'s `test_capability_manifest_is_complete`, which carries no exemption list. |
| **UI group** | `core/plan.py`'s `UIGroup` (`key`, `title`, `description`, `members`): one titled group of ONE VI's own capabilities, declared in the VI's `ui_groups` class attribute and optionally tagged per method with `@monitored(group=...)` / `@control(group=...)`. `members` is an explicit ordered tuple of the VI's `@monitored`/`@control` method names — the order IS the render order, and it doubles as the workflow order an agent reads out of the manifest. Declared order is group order. Distinct from **ParamGroup**, which groups the parameters of one *procedure run*; a UI group groups the *methods of one instrument*. Presentation and description ONLY: nothing about a group crosses the action queue, a control is still submitted alone by method name with flat scalar kwargs, and a group implies no atomicity and no ordering guarantee. Validated by `BaseVirtualInstrument.__init_subclass__` at import — unique keys, every member a real capability of the class, every tag naming a declared group, tag and membership agreeing — so a renamed or moved method cannot leave a dangling tag. |
| **Control declaration** | The optional GUI metadata on `@control`: `params={name: ParamSpec}` (widget shape, unit, bounds, choices — validated against the signature at import) and `panel=` (default monitor-card placement; `False` = front-panel only). A VI whose valid values only exist after construction (e.g. a controller's instrument-reported calibration curves) overrides the instance hook `control_param_specs(method_name)` to inject dynamic choices; the GUI consults the hook, not the raw decorator metadata. Display-only — safety stays with `control_limits`. Conformance-checked. |
| **Panel control** | A `@control` shown on a VI's compact monitor card. The set is the VI's `panel=True` declarations, overridable per setup by the `panels:` block in `monitor.yaml`; every control, panel or not, appears in the instrument's front panel. |
| **Instrument front panel** | `gui/instrument_front_panel.py`. A per-VI child window (opened from the sliders icon on a card or device row) rendering the VI's complete surface: every `@monitored` value live and every `@control`, including panel-hidden ones. The GUI bench-test surface; all actions still flow through `Orchestrator.submit_vi_action()`. |
| **Shared-instrument mode discipline** | The standard (full text in `virtual_instruments/measurement/README.md`) for a driver whose public API spans more than one mutually exclusive operating mode (e.g. the Keithley 6221's plain DC output vs. its bipolar delta engine), when more than one measurement VI can be wired to the same physical driver instance in `devices.yaml`. The mode-establishing method MUST be idempotent and self-recovering — it unconditionally reasserts its own required mode (`Keithley6221.set_current()`'s `:SOUR:CURR:MODE FIX`) rather than assuming the instrument is already compatible, so a VI's `initiate()` never depends on a previous VI's `standby()` having run correctly. Teardown methods (`stop_delta_mode()`) still restore a documented idle baseline as defense-in-depth. A sim driver modeling more than one such mode tracks it (e.g. `SimKeithley6221._mode`) so skipping the defensive reassertion fails in tests instead of on hardware. |
| **Control-validation standard** | The binding contract (full text in `BaseVirtualInstrument`'s docstring) that every user-facing `@control` action is validated before hardware is touched and always yields an explicit verdict. (1) Numeric bounds: the VI declares `control_limits = {method: {param: limit_name}}` and its `__init__` populates `self._limits[limit_name] = (lo, hi)` from the config's `init_params` — limits are setup properties (e.g. `max_temperature_K`, `max_ramp_rate_K_per_min`, `max_current`), so a new cryostat changes YAML, not code. Enforcement is inherited: `__init_subclass__` wraps every `@control` method; an out-of-range call raises `CryoSoftSafetyError` with the reason. Subclasses adding limits must merge (`{**Parent.control_limits, ...}`). (2) Semantic rules that aren't ranges (e.g. never energise the switch heater across a PSU/coil current mismatch) are explicit checks at the top of the method, raising `CryoSoftSafetyError`. (3) Verdict: the Orchestrator emits `action_succeeded(vi, method)` or `action_failed(vi, method, reason)` for every submitted action; `MonitorWindow` shows failures in the notification banner and successes as a transient status-bar message. Machine-enforced by the `test_conformance.py` control-validation tests: declared limits must name real `@control` methods/params, must be populated by every sim-buildable config, and must actually reject an out-of-range call. Coverage is enforced too, which is what makes the standard binding rather than opt-in: every numeric `@control` parameter on every discovered VI must appear in `control_limits` or in `CONTROL_LIMIT_EXEMPTIONS` with a one-line physical rationale (`test_every_numeric_control_param_is_bounded_or_exempt`), and an exemption that no longer names an unbounded parameter fails as stale. |
| **Direct action path** | `Orchestrator.submit_vi_action()` → the per-tick queue drain → `Station.execute_vi_action()`: the route a MANUAL action (a GUI click on an instrument panel, an agent call) takes to one VI, as opposed to a procedure's `Target`s and `Command`s, which go through `Station.process_system_targets()`/`send_measurement_commands()`. Five independent checks refuse a call before any hardware command is sent, each with its own reason: a private (underscore-prefixed) name and a method that is neither `@control` nor a lifecycle action (`initiate`/`standby`) are refused by the Station as `CryoSoftPrivateActionError`/`CryoSoftUndeclaredActionError`; a capability whose **Capability scope** exceeds the caller's `allowed_scope` (default `"measurement"`; the Orchestrator's manual path opts into `"operation"` via `MANUAL_ACTION_SCOPE`) as `CryoSoftActionScopeError`; an out-of-range value by the **Control-validation standard**'s limit wrapper; and a setpoint outside the active **Session envelope** by the Orchestrator, at submission and again at drain. Every refusal is a `CryoSoftSafetyError` — nothing reached the instrument — and surfaces as `action_blocked(reason)` or `action_failed(vi, method, reason)`. |
| **Setpoint-parameter convention** | `core/plan.py`'s `SETPOINT_PARAM_PREFIX` (`"target_"`): a `@control` parameter whose name starts with it carries its VI's enveloped quantity — the same quantity `RampableVI.start_ramp(target)` takes and a `Target` commands (`set_field(target_T)`, `set_temperature(target_K)`, `set_sample_angle(target_deg)`). It is what lets the **Session envelope** bind a manual action on the **Direct action path** with no per-VI table in the Orchestrator: `Station.setpoint_parameters(vi, method)` names the keyword argument to check. A rampable VI declares exactly one, on one capability, and that parameter must itself be bounded by `control_limits` (an envelope narrows a setup limit, so a limit must exist to narrow) — machine-checked by `test_conformance.py`. `Station.envelope_variables()` is the read side: per VI, the setpoint capability plus the setup's own bounds, which the Start Experiment dialog's envelope editor pre-fills from. |
| **Emergency standby** | `Orchestrator.emergency_standby(reason)`: the unconditional safe-off route, permitted in EVERY state — including EMERGENCY and ERROR, where every other manual route is refused and where making the machine safe matters most. Deliberately outside the manual-action admission predicate (an admission gate on the stop button is a gate on the wrong thing), it routes into the same emergency flow a **Critical safety flag** takes (abort the run, `run_finished`, EMERGENCY, `standby_all()`) — carrying its reason into the one CRITICAL record `_enter_emergency()` writes for every EMERGENCY entry, manual or tick-observed alike — and runs on the caller's stack like `stop_ramp()`. Accepted latency: single-threaded cooperative scheduling means a call arriving mid-tick lands after the current `measure()` returns. |
| **vi_type (class)** | Class attribute of a VI describing its device role: `magnet`, `temperature`, `measurement`. Set by the typed base classes. |
| **vi_type (config/registry)** | The *registry* role a VI plays in a Station, set in `devices.yaml`: `system` (rampable, receives system targets) or `measurement` (receives measurement commands). Distinct from the class `vi_type`. |
| **Connection lifecycle** | The standard separating who *owns* an instrument from what the instrument is *doing*, binding on every driver and VI (full text in `BaseVirtualInstrument`'s docstring). Two axes: `connect`/`disconnect` own the bus session, `initiate()`/`standby()` own instrument state. Three rules: (1) **construction is silent** — a driver's or VI's `__init__` sends no command that changes what the instrument is doing, so the only command `build_station()` issues per instrument is an identity query (`BaseVirtualInstrument.ping()`, via `_identity_check()`); a setup command belongs in `initiate()`. (2) **disconnecting is not standing down** — `Station.disconnect_instrument()` releases the session and leaves a magnet at field, a heater on its setpoint; pressing Standby first is the operator's choice. (3) a disconnected instrument **degrades exactly like an Offline instrument**, into the same registry, tagged `"operator"` in the **Availability tag** vocabulary — `Station.availability()` reports it `state="absent"`, exactly like a VI that never connected. Drivers implement `close()` (release the session, return the instrument to LOCAL where it has that concept, never raise); VIs inherit `ping()` and the `disconnect()` release hook. A narrower, VI-internal sibling — the declared `detach_when_idle` standard (see **Availability**) — lets a single-client VI release its OWN session automatically between runs with no operator action; that VI stays enumerable and controllable (`state="detached"`), never lands in the offline registry, and is a different mechanism from this one. The GUI pair is one `ConnectionButton` per card (`gui/lifecycle_toggle.py`), next to the Initiate/Standby toggle. Distinct from **Instrument fault**, which is an instrument that stopped answering while CryoSoft still held it. |
| **Lifecycle state** | L1, rendered by every client. What an instrument is *doing*, as an observed fact that travels the contract: `"idle"` (not initiated), `"initiated"` or `"standby"` — the `LifecycleState` vocabulary declared in `core/events.py`. The **lifecycle-state standard** (full text in `BaseVirtualInstrument`'s docstring) is the operating half of the **Connection lifecycle** turned into data, and exists to stop a client inferring the state from the actions it happened to witness: before it, an emergency's blanket `Station.standby_all()` emitted no per-VI action, so every instrument card went on showing "initiated" for hardware that had actually been stood down. Three rules, none of which a VI author writes anything to obey. (1) **The verbs own the fact** — `initiate()` records `"initiated"`, `standby()` records `"standby"`, `disconnect()` resets to `"idle"`, and a measurement VI's `initiate_measurement()` (its own arming verb; its plain `initiate()` is only a connection check) records `"initiated"` too — each written only after the call returns without raising, by the same `__init_subclass__` wrap the standby-provenance standard uses. (2) **The read is pure** — `BaseVirtualInstrument.lifecycle_state()` answers from the cached value and sends nothing on the bus, because `Station.lifecycle_states()` reads it for every VI while assembling every `StatusSnapshot`. (3) **Hardware may correct it** — a VI whose instrument reports what it is doing overrides `observe_lifecycle_state()`, which the monitor cycle consults once per poll off the values it already read; that refreshes the cache, it never becomes the read. It reaches clients on `StatusSnapshot.instruments[vi]["lifecycle"]` (mirror read: `StatusMirror.lifecycle_state(vi_name)`), and the Monitor window's Initiate/Standby toggle renders it on every snapshot — an action's `action_succeeded` may flip the toggle optimistically, but the next snapshot confirms or corrects it. Distinct from the standby-provenance standard (`BaseVirtualInstrument.standby_status()`, read by **Hold enforcement**), which answers the narrower "is this VI at, or converging on, its own safe idle state?" for hold enforcement, and from **Availability**, which answers "why can't I use this instrument?" |
| **Driver error-reporting standard** | Every driver method that programs a mode or a setpoint must verify its write and document how: SCPI error queue, IEEE-488.2 status byte, protocol acknowledgement, or explicit readback (full text plus the per-driver table in `drivers/README.md`). A bus write returning without an exception proves only that the bytes left the computer — most of these instruments accept a command they cannot execute and record the refusal somewhere only a deliberate read will find, which is how a real 6221 rejected every DC current-set call for a whole session (2026-07-22) with nothing in `cryosoft.log`. A verified refusal is raised as `CryoSoftInstrumentError`, carrying the instrument's own `code` and `instrument_message` verbatim plus the `context` (the driver call refused); it subclasses `CryoSoftCommunicationError`, so layers that already treat driver calls as fallible are unaffected. Two guard rails: the checker never fails a working call (a bus failure while reading the queue is swallowed), and recovery paths drain the queue rather than raise, so an abandoned sequence's error is never charged to the next command. Sim twins raise the same typed error with the same code for the same wrong sequence, and model only refusals the hardware actually produces. |
| **Safe shutdown** | `safe_shutdown()` on every driver, real and sim: one unconditional, argument-free call that leaves the instrument in a documented safe idle state, so anything abandoning a sequence — a failed procedure, an emergency stop, an agent that stopped answering — has one call to make on every instrument without knowing which it is. Idempotent, never raises, callable from any leftover state, and each driver documents what it recovers from. **Safe is not off**: safe idle means the instrument stops being able to do harm, which is instrument-specific — a magnet's is HOLD, not zero field (a fast dump is how magnets quench); a Lakeshore's leaves the setpoint alone but takes the heater range to OFF. Duck-typed like `get_idn()`/`close()`, with no `DriverBase`: `tests/test_conformance.py` is the contract, and each sim declares its landing state as a private `_is_in_safe_state()` predicate the test asserts. Distinct from a VI's `standby()`, which is the supervised, instrument-aware stand-down the operator (or a procedure) asks for, and from `close()`, which under the **Connection lifecycle** releases the bus session and changes no instrument state at all. |
| **Station info** | L2. The frozen, JSON-safe snapshot of everything a station DECLARES — the static half of the picture, whose live half is the per-tick `StatusSnapshot`. `StationInfo` (`core/events.py`) carries the setup's identity, its tick period, and one `InstrumentInfo` per configured VI, live and offline alike: name, VI class, `role` (the registry `vi_type (config/registry)`), `kind` (the class `vi_type (class)`), the **Availability tag**s standing at snapshot time, its `@monitored` readings (`MonitoredInfo`: unit, description, group, return type), its `@control` actions (`ControlInfo`: scope, `panel` flag, group, and each parameter's `ParamSpec` rendered as kind/unit/description/default/min/max/choices), the configured bounds of its `control_limits`, its `ui_groups` (`GroupInfo`, members in declared order) and its merged `safety_flags`. Three modules, three jobs: `core/events.py` DEFINES the shape and imports nothing (import-linter contract C16); `Station.station_info()` BUILDS it, because only the Station holds both the VI declarations and the config the bounds come from; `core/capability_manifest.py` RENDERS it (see **Capability manifest**). Built from declarations and config ALONE — no bus traffic, ever — which is what lets it describe an unreachable instrument as fully as a live one and lets a client read it outside the tick loop; the matching obligation on the VI layer is `control_param_specs()`'s purity rule. Cached and rebuilt whenever the station's membership changes (every connect and disconnect), so `seq` counts real rebuilds. Both clients build their instrument surface from this — the GUI into panels with titled group boxes, an agent gateway into its **Capability manifest** — so neither carries a hand-written description of any instrument. |
| **Status snapshot** | The live half of the picture whose static half is **Station info**: `core/events.py`'s frozen, JSON-safe `StatusSnapshot`, emitted on the **Event stream** once per tick and on every state change. Its standard is that it carries the engine's WHOLE read surface — one field per read-only accessor the Orchestrator exposes, named after that accessor (`state`, `run`, `is_monitoring`, `pause_pending`, `active_run_kind`, `override_active`, `manual_override_expires_at`, `held_vi_names`, `active_ramps`, `availabilities`, `vi_faults`, `offline_reason`, `envelope_variables`, **Attendance** and the **Kill switch**'s `agent_gate`), plus `instruments`, the per-VI merge of the same facts for a client that renders one panel per instrument. `tests/test_conformance.py` diffs the two surfaces, so an accessor added to the engine without a field here fails the harness — which is what keeps "no client calls the engine to read" achievable rather than aspirational. Frozen and emitted as a copy, so it crosses the **Instrument thread** as data nobody still owns; a client keeps the last one in its **Status mirror** and every read it answers is one event-loop hop stale by construction. |
| **Capability manifest** | The JSON rendering of **Station info**: `capability_manifest.build_manifest(station)`, the machine-readable answer to "what can this system do?", generated from the same declarations that drive the rest of CryoSoft and never hand-maintained. It adds no fact of its own, only an arrangement — each instrument's capabilities resolved into its declared `ui_groups` (`groups`, in declared order, each naming its `monitored`/`controls` members) with everything no group claims after them (`ungrouped`), and the flat `monitored`/`controls` detail lists ordered to match, so a renderer walking either sees the same order. `MANIFEST_SCHEMA` is a real JSON Schema draft 2020-12 document describing exactly that output; `validate_manifest()` checks against it with a small structural validator over the subset the document uses, since `jsonschema` is deliberately not a project dependency (a consumer that has it can use the schema directly). `python -m cryosoft.core.capability_manifest <config_dir>` prints one, building a Station and nothing else. Issues no bus traffic, for the same reasons **Station info** does not. |
| **Availability** | L2. The single answer to "why can't I use this instrument?" for one VI (`cryosoft.core.availability`, GLOSSARY entry point for the standard also described under **Offline instrument** / **Instrument fault** / the `detach_when_idle` half of **Connection lifecycle**): a closed **Availability tag** vocabulary plus a declared policy table (`TAG_POLICY`) resolve to one of four mutually exclusive `AVAILABILITY_STATES` — `"live"` (no tags, fully usable), `"detached"` (in the live registry, session released by the `detach_when_idle` declaration, reacquires on arm), `"faulted"` (live but carries `not_responding`), `"absent"` (not in the live registry at all). | **Availability tag** | The closed vocabulary (`AVAILABILITY_TAGS`, `cryosoft.core.availability`) a VI's **Availability** record carries, a `frozenset[str]` — several can hold at once (e.g. `{"operator", "connect_failed"}`, an operator-released VI whose reconnect then fails on hardware — see **Offline instrument**), unlike the single derived state that vocabulary implies: `"connect_failed"` — hardware unreachable, at build time or on a failed reconnect; `"operator"` — the operator released it via the **Connection lifecycle**; `"not_responding"` — held but stale/disconnected, a comm-origin `Condition` (see **Instrument fault**); `"detached"` — a `detach_when_idle` VI's session is released between uses, reacquires on arm. | **Offline instrument** | A configured VI whose hardware failed to *connect* when `build_station()` ran (driver `__init__` raised, or the VI's own bring-up raised a communication error), or one the operator released via the **Connection lifecycle**. | **System condition** | The standard unifying every "something is wrong" signal in CryoSoft: a `Condition` (`core/conditions.py`) is origin × severity, and scope follows from severity alone — never from which origin reported it. Exactly four producers: `"comm"` (a VI's poll going stale/disconnected — `Station._record_comm_condition()`, see **Instrument fault**), `"safety"` (a VI's `evaluate_safety()` flag — `Station.update_conditions()`, see **Safety hold** / **Critical safety flag**), `"envelope"` (an `ExperimentEnvelope.check_state()` violation — `core.conditions.envelope_conditions()`, see **Session envelope**), and `"trend"` (a failing named judgement over the trend-history store — see **Trend check**), the only origin published through the generic `Station.publish_conditions(origin, conditions)` rather than an origin-specific producer method. The pure policy — the `Condition`/`Verdict` value objects and the deterministic `decide(conditions, watched_vis, run_active) -> Verdict` function — lives in `core/conditions.py` with no dependency on `Station` or `Orchestrator` (import-linter contract C13), so it is unit-testable standalone. | **Severity ladder** | The three values a `Condition.severity` (see **System condition**) may take, each with fixed enforcement — a flag's or fault's severity, never which VI reports it, decides scope: `"advisory"` — reported, no enforcement (every `"trend"`-origin condition uses this rung — see **Trend check** — no other origin has published one yet); `"hold"` — scoped to `affected_vis` (a non-empty `frozenset`, required by `Condition.__post_init__`): those VIs are driven to standby and KEPT there for as long as the hold persists and is not acknowledged, a LEVEL-TRIGGERED invariant re-checked every tick rather than a one-shot onset action (`Orchestrator._enforce_safety_holds()` — see **Hold enforcement**), refused manual control by `_manual_action_admissible()`, and fail any run watching one of them; `"critical"` — station-wide by construction (`affected_vis` MUST be `None`, also enforced by `__post_init__`): every critical condition lands in `decide()`'s `Verdict.emergency`, driving `_enter_emergency()`'s blanket `standby_all()` and refusing every manual action station-wide until `Orchestrator.acknowledge()` unlocks the override (see **Hold acknowledge** — the SAME control also unlocks a hold-severity condition, without ever entering EMERGENCY). `quench` (critical) is the only safety flag declared today — see **Safety-flag manifest**. |
| **Instrument fault** | A comm-origin, hold-severity `Condition` (see **System condition**) on a VI that DID connect at build time and has since gone stale/disconnected during polling — the runtime sibling of **Offline instrument**, which never connected at all. `Station._record_comm_condition()` builds it, scoped (`affected_vis`) to just that one VI, in the same pass `get_state()` already computes `_stale`/`_disconnected`. It surfaces through two adapters over the same condition: `Station.availability(vi_name)` (see **Availability**) folds it into the unified record as the `not_responding` **Availability tag** (`state="faulted"`, `enumerable=True`, `controllable=False` per `TAG_POLICY`), and `vi_faults()` remains the permanent, comm-specific GUI adapter synthesizing one `FaultRecord` (`vi_name`, `kind` — `"stale"`/`"disconnected"`, `message`, `since`, `acknowledged`) per comm-origin condition — fields (kind, acknowledged) the unified record deliberately does not carry, since acknowledge/retry are comm-specific actions. `clear_fault()` removes the condition entirely on the next successful poll (acknowledged or not — a recovered VI has nothing left to acknowledge). Three failure tiers by blast radius: a fault on an UNCLAIMED VI (no run using it, or a run that does not claim it) quarantines only that VI — controls disabled, a fault badge, no state change, a warning-severity `ErrorEvent`; a fault on the active run's CLAIMED (watched) VI additionally fails the run (`run_finished` status `"failed"`, the machine returns to IDLE — not global ERROR — and the queue does NOT auto-continue); a tripped **Critical safety flag** is a DIFFERENT, safety-origin condition entirely — never a comm-origin fault — and forces station-wide EMERGENCY via `decide()`'s `emergency` field regardless of any VI's fault state. Global ERROR survives only for an unhandled tick-boundary exception (unknown blast radius). `_manual_action_admissible()` refuses a faulted VI outright, before every other admission rule (including a safety hold), in every state including IDLE — see **Claim** — by reading the `not_responding` tag off `Station.availability(vi_name)` against `TAG_POLICY["not_responding"].controllable`, not a hardcoded origin check; the table carries no override column for this tag, which is what makes the refusal unconditional where a safety hold's is bypassable via the EMERGENCY manual override. `core.events.ErrorEvent` is the structured signal payload (`vi_name`, `kind` — `"fault"`/`"run_failure"`/`"safety"`/`"safety_hold"`/`"internal"` — `severity`, `message`, `timestamp`) carried on `Orchestrator.error_event`, emitted alongside the compat `error_occurred(str)` for everything except a plain per-VI fault warning or a routine `"safety_hold"` re-assertion (both `severity="warning"`, both fire `error_event` only, to avoid banner noise in windows still on the compat signal). `"safety_hold"` (see **Hold enforcement**) is the Orchestrator re-asserting, or failing to re-assert, `standby()` on a VI held by a hold-severity safety condition — VI-scoped by construction, deliberately NOT the station-wide `"safety"` tier above it: an escalation after repeated failed attempts still fires only for the one VI concerned, never a blast radius beyond it. |
| **Fault acknowledge** | docs/plans/archive/operation-concurrency-and-error-scoping.md §3. `Station.acknowledge_fault(vi_name)` / `Orchestrator.acknowledge_fault(vi_name)` mark an active **Instrument fault** record acknowledged, calming the Monitor's per-VI badge/banner without changing anything else — the fault still refuses manual actions and still shows on the panel until it clears. Distinct from `Orchestrator.acknowledge()` (see **Hold acknowledge** — the unified, time-boxed EMERGENCY/hold-severity override, single home on the Monitor window's top bar — moved off `ProcedureWindow`; its private `_acknowledge_emergency()` helper carries the EMERGENCY-only two-stage state-recovery logic). An acknowledged-but-recovered fault simply disappears on the next successful poll (`clear_fault()`) — there is nothing left to acknowledge once the instrument responds again. The paired recovery action is `retry_fault()` (`Station`/`Orchestrator`): resets the error counter and forces one fresh poll — never rebuilds a driver, unlike `connect_instrument()` for an **Offline instrument**. |
| **Safety-flag manifest** | `BaseVirtualInstrument.safety_flags: ClassVar[dict[str, str]]` (the System-Condition standard's producer-side declaration, full text in `BaseVirtualInstrument`'s docstring): every flag a VI's `evaluate_safety()` can report, mapped to its severity — `"advisory"` (no enforcement, reserved), `"hold"` (scoped to the VIs whose **Safety concern** names it), or `"critical"` (station-wide by definition — see **Critical safety flag**). Declared on the category base that owns the flag's physical semantics (`MagnetBase` → `{"quench": "critical"}`), never on each concrete VI. Subclass manifests are merged over the MRO by `merged_safety_flags()` (same merge discipline as `control_limits`) — a subclass adds flags, it never contradicts a base's declared severity for one it inherits. Contrasts with `safety_concerns()`: this is the PRODUCER side (what a VI can report and how severe it is), `safety_concerns()` is the CONSUMER side (which — necessarily hold-severity — flags a VI depends on to keep operating). Critical severity is station-wide scope by construction (the System-Condition standard, `core/conditions.py`), so no derived "critical subset" accessor is needed — `Station.active_critical_conditions()` reads the live condition registry directly. |
| **Safety concern** | `BaseVirtualInstrument.safety_concerns() -> set[str]`. A static declaration of which HOLD-severity safety flags (see **Severity ladder**) — named exactly like `evaluate_safety()`'s keys — a VI depends on to operate safely, independent of whether THIS VI is the one that reports them: the VI that reports a coolant-low flag via `evaluate_safety()` need not itself be concerned with it (it keeps reading regardless of what it reports); a magnet is concerned with it but never reports it. No shipped VI overrides the empty-set default; every category base (`MagnetBase`, `TemperatureControllerBase`, `MeasurementInstrumentBase`) keeps it — none is concerned with `quench`: `quench` is critical severity and therefore station-wide by construction (see **Critical safety flag**), so naming it in any VI's `safety_concerns()` would be meaningless — EMERGENCY has already stopped every VI, concerned or not, the instant it trips. `Station.get_concerned_vis(flag)` is the read side (every VI whose declaration names *flag*), consulted by `Station.update_conditions()` to scope a hold-severity flag's `Condition.affected_vis`. |
| **Critical safety flag** | A flag declared `"critical"` in its producer's `safety_flags` manifest (see **Safety-flag manifest**) — station-wide by construction: its `Condition` always has `affected_vis=None` (enforced by `Condition.__post_init__`), so no VI declares (and per the manifest standard, none may declare) a concern for it in `safety_concerns()` — a per-VI hold would be meaningless once EMERGENCY has already stopped everything. `quench`, declared on `MagnetBase`, is the only critical flag today. `core.conditions.decide()` collects every critical-severity condition (from any origin) into `Verdict.emergency`; the Orchestrator's tick enters EMERGENCY (`_enter_emergency()` — always a blanket `standby_all()`, since there is no concerned subset to narrow to; the single entry path, so a tick-observed quench logs the same one CRITICAL record naming cause and actor that an **Emergency standby** does) the instant `emergency` is non-empty and the machine isn't already there, and `_manual_action_admissible()`'s EMERGENCY rule refuses every manual action station-wide until `acknowledge()` unlocks the override (see **Hold acknowledge**). Never tolerable: **Tolerated safety flags** filters hold-severity flags only, so a critical flag's condition is built unconditionally regardless of any operation's tolerance. |
| **Safety hold** | A hold-severity, safety-origin `Condition` (see **System condition**): scope follows from severity, so it is scoped (`affected_vis`) to every VI whose `safety_concerns()` names a currently-tripped, non-tolerated flag (see **Tolerated safety flags**). Built once per tick by `Station.update_conditions(safety, tolerated_flags=...)` from the SAME `check_safety()` snapshot the tick already computed, into the ONE unified registry alongside every comm- and envelope-origin condition (`Station._conditions`, read via `conditions()`/`active_critical_conditions()`). `Condition`s still share this one registry — that part is unchanged — but a hold-severity condition now DOES have an enforcement-affecting override, `Orchestrator.acknowledge()` (see **Hold acknowledge**), distinct from the display-only `Station.acknowledge_condition(key)` (marks `Condition.acknowledged`, calms a UI badge, never consulted by the admission gate). A held VI is refused manual control by `_manual_action_admissible()` (regardless of Orchestrator state, exactly like an **Instrument fault**, unless `acknowledge()` has unlocked it) and fails any run that claims/watches it (`_fail_run_for_fault()`, the machine returns to IDLE, every other instrument stays usable) — but clears itself automatically the moment the flag recovers or becomes tolerated, with no retry action (there is no hardware to retry, only a physical condition to wait out). For as long as a VI appears in `affected_vis`, `Orchestrator._enforce_safety_holds()` keeps it AT standby — a LEVEL-TRIGGERED invariant, re-checked every tick, not the one-shot onset dispatch this replaced (see **Hold enforcement** for the mechanism, including why an onset-only dispatch left a hold that outlived an acknowledge-then-expire cycle permanently unenforced) — never a blanket `standby_all()`: an unconcerned VI (e.g. temperature control while only the magnets are held for a coolant flag) is left running untouched. Distinct from a **Critical safety flag**, whose condition is always station-wide (`affected_vis=None`) by construction — a critical flag is never named in any VI's `safety_concerns()`, so it never produces a Safety hold, only EMERGENCY. |
| **Hold enforcement** | `Orchestrator._enforce_safety_holds()` (`core/orchestrator.py`), called every tick over `verdict.held_vis`, once `decide()` has run: the **Safety hold** standard's enforcement, made LEVEL-TRIGGERED rather than the edge-triggered onset dispatch it replaced. For as long as a VI is held and not acknowledged (`override_active(vi_name)` — an acknowledged hold is skipped, exactly like `_manual_action_admissible()` treats it), the VI is re-checked and, if needed, re-commanded to standby EVERY tick, not just once when the hold began — which is what closes the gap the onset-only dispatch left open: an operator who acknowledges to unlock manual control, moves the VI during the window, and lets the window lapse got the UI back in "held" state with the hardware never driven back down, because expiry revokes manual PERMISSION, it does not by itself re-command hardware. Evidence comes from `BaseVirtualInstrument.standby_status()` (the standby-provenance standard, `virtual_instruments/base.py`), never a physical read: `"reached"` — at safe idle, nothing to enforce this tick; `"converging"` — a `standby()` is already in flight and will arrive, so it must NOT be re-issued (re-issuing unconditionally every tick is the naive-fix bug this guards against: rebuilding a `RampableVI`'s ramp generator from scratch on every tick restarts the ramp from scratch every time, and the magnet never arrives); `"away"` — no standby command is in flight, so `standby()` is (re-)issued now, rate-limited to at most one attempt per VI per `hold_enforcement_interval_s` (`devices.yaml`'s `safety:` block, `config.read_safety_config()`, default 10s — a VI with no recorded attempt yet fires immediately, which is what makes hold ONSET and hold RE-ASSERTION the same code path). Command provenance is not physical verification — `standby_status()` knows the standby command was issued and its ramp finished, not that the hardware actually arrived, so a PSU silently ignoring a ramp still reads `"reached"` here. Generality is deliberate (CLAUDE.md's "standards over one-off code"): this method reads only `Condition.severity == "hold"` and `affected_vis` — both already resolved by `core.conditions.decide()` — and never names a flag, so a hold-severity flag a setup declares inherits enforcement automatically, with zero Orchestrator change; the one non-general part is that `standby()` is the only safe response this contract models, so a future flag needing a different safe action is a declaration on the VI itself, never a special case here. A VI whose `standby()` keeps raising past `hold_enforcement_max_attempts` consecutive attempts (default 3) is escalated exactly ONCE per episode — a CRITICAL-level log line plus a `kind="safety_hold"`, `severity="error"` `ErrorEvent` — WITHOUT transitioning the state machine to EMERGENCY, since that remains a separate decision made elsewhere; a routine re-assertion instead announces itself with only a `severity="warning"` `ErrorEvent` (never silent, since re-asserting standby moves hardware the operator did not just ask for). `"safety_hold"` is a VI-scoped `ErrorEvent.kind` tier (see **Instrument fault** for the full enumeration), deliberately distinct from the station-wide `"safety"` tier: it never carries a blast radius beyond the one VI it names. Do not call this mechanism a "watchdog" — `cryosoft/core/watchdog.py` is an unrelated ramp-stall detector; this is the Safety hold standard's enforcement. |
| **Hold acknowledge** | `Orchestrator.acknowledge()` (`core/orchestrator.py`): the single GUI entry point unlocking manual control of ANY currently held VI — a **Safety hold** or a station-wide EMERGENCY alike — for a fixed, configurable window (`safety.manual_override_timeout_s` in `devices.yaml`, `config.read_safety_config()`, default 300s), not a standing bypass. Generalizes what was previously EMERGENCY-only (`acknowledge_emergency()`, now the private `_acknowledge_emergency()` helper `acknowledge()` delegates to while in EMERGENCY) to the `hold` severity too, since `hold` is the severity that fires in ordinary degraded operation and previously had no override path at all. Two independent expiry stores on the Orchestrator: `_emergency_override_until: float \| None` (one global window) and `_hold_override_until: dict[str, float]` (`Condition.key` → expiry, one entry per acknowledged hold). `_manual_action_admissible()` reads both live via a `time.time()` comparison — enforcement is the comparison lapsing on its own, never a tick-driven "re-lock" event. Pruning (once per tick, in `_tick_body()`) is by EXPIRY ONLY, deliberately never because the condition disappeared from `verdict.held_vis` — a flag flapping right at its threshold (a level flag hovering near its warning value is exactly this in practice) would otherwise force a fresh acknowledge on every re-trip within the same window, defeating the point of the cooldown; the accepted trade-off is that a stale acknowledgment can silently cover a NEW, unrelated trip of the same flag within the leftover window, bounded by the timeout. Expiry itself no longer just returns a VI to a refused-control state: `Orchestrator._enforce_safety_holds()` (see **Hold enforcement**) is level-triggered, so the very next eligible tick after an override lapses re-asserts `standby()` on any VI still in `verdict.held_vis` and found away from it — the operator-visible consequence being that a field moved during an acknowledge window is driven back down once the window closes, not left wherever it was last put. The hold override deliberately reaches through claim-protection (rule 4 of `_manual_action_admissible()`) exactly like the EMERGENCY override already did — both return `True` before the claim check is ever reached — which is what lets it work identically under `PAUSED` with no PAUSED-specific code anywhere; this is also the source of a known, accepted gap: `resume_procedure()` unconditionally re-dispatches `_last_system_targets` on resume, with no way to know a claimed VI was manually moved via an active override during the pause (deferred, not fixed, by explicit design decision — a future change would need to track manually-touched claimed VIs and have `resume_procedure()` refuse or confirm). A hold-override never admits while the Orchestrator is in EMERGENCY or ERROR (the state guard in rule 0b) — EMERGENCY requires its own override acknowledged fresh (closing a leak where an already-acknowledged hold would otherwise admit action through a LATER, unacknowledged EMERGENCY on the same VI), and ERROR means unknown blast radius, never a known condition a human can safely act around. `_enter_emergency()` also unconditionally clears both stores on every fresh EMERGENCY entry, as defense in depth alongside the state guard. Public accessors: `held_vi_names()`, `override_active(vi_name=None)`, `manual_override_expires_at()` — the GUI's top-bar "Acknowledged (mm:ss)" countdown and tests should read through these, never the private timestamp fields directly. Distinct from `Station.acknowledge_condition(key)`/`Condition.acknowledged` (display-only, never consulted here) and from **Tolerated safety flags** (`OperationBase.tolerated_safety_flags` prevents a `Condition` from being built at all for a tolerant operation's duration — a different mechanism solving a different problem: the sanctioned, supervised `HeliumFillOperation` path vs. ad hoc manual control). |
| **Tolerated safety flags** | A run's `tolerated_safety_flags: frozenset[str]`, resolved ONCE per tick by the Orchestrator (a run that declares none, or an idle station, tolerates nothing) and passed into `Station.update_conditions(safety, tolerated_flags=...)`. Filters HOLD-severity safety flags ONLY, applied at the single point a hold-severity flag's `Condition` would otherwise be constructed (`Station.update_conditions()`): a tolerated flag simply gets no condition built for it that tick — no hold, no run failure. Never applied to a critical or advisory flag's own condition — severity alone decides whether tolerance is even consulted (see **Severity ladder**), and a critical/advisory condition is built unconditionally. This is what lets a run whose whole purpose is to fix a tripped condition (declaring that flag in `tolerated_safety_flags`) run to completion instead of being held on — and having its own run failed for — the very condition it exists to fix. `Orchestrator._operation_end_state()` mirrors this at finish: only a still-non-empty `Station.active_critical_conditions()` sends a finishing operation back to EMERGENCY instead of IDLE — a merely tolerated hold-only flag does not, since it was never why EMERGENCY would have been entered in the first place. |
| **`Gate`** | `core/gates.py`. A tick-driven wait primitive: an optional one-shot `action` callable, followed by an optional `check` predicate that must hold True continuously for `window_s` seconds before `step()` reports satisfied (any `False` resets the stability clock; polled once per Orchestrator tick, mirroring `RampableVI.advance_ramp()`/`ramp_status()`'s generator-per-tick idiom). `check_once()` is the one-shot alternative — runs `action` once and reads `check()` a single time, ignoring `window_s` entirely — used for a **Postcondition gate**'s immediate-finish evaluation; never combined with `step()` on the same instance. |
| **`initiation_gates()` / `reading_gates()`** | `BaseProcedure` hooks (empty-tuple no-op default) returning `tuple[Gate, ...]`: gates that must all be satisfied before the Orchestrator proceeds from a completed ramp to a measurement. `initiation_gates()` governs the run's first RAMPING→MEASURING transition (right after `initiate()`); `reading_gates()` governs every one after (after each `change_sweep_step()`). | **`INITIATION_GATE` / `READING_GATE`** | `OrchestratorState` members entered from `RAMPING` once all system targets are reached and the active procedure declared gates for this transition; the Orchestrator steps every pending `Gate` once per tick until all are satisfied, then proceeds to `MEASURING`. | **Pause boundary** | The one place a pause is allowed to *wait* instead of taking effect at once. `Orchestrator.pause_procedure()` normally pauses immediately, from any run state, holding the hardware where it stands (`Station.stop_ramps()` — a magnet PSU ramps autonomously to its last setpoint, so a software-only pause would leave the field moving) and freezing the `wait_s` clock, which `resume_procedure()` restores so a half-elapsed settle still completes. `MEASURING` is the single exception, and the reason this term exists: that is the one state where a point is ramped, settled and gated but not yet read, so pausing there would strand it and resume would take its reading after an arbitrarily long hold. A pause requested in `MEASURING` is therefore DEFERRED — `_pause_requested` is raised (public read: `pause_pending`), the status line says "Pause requested" and a fresh `StatusSnapshot` goes out on the spot — so a client's **Status mirror** carries `{state: MEASURING, pause_pending: True}` for the whole interval, which the Monitor's status bar renders as `MEASURING · Pausing` and the Procedure window's Pause button as `Pausing…` — `measure()` saves its datapoint on the next tick, and the `SWEEPING` branch of `_tick_body()` calls `_enter_paused()` the moment the point is complete; resume then returns to `SWEEPING`, whose next act is the ramp to the next point. The **Reading loop** itself is never at risk: `measure()` runs synchronously inside one tick, so a click can only arrive between ticks, never between two readings of one datapoint. `resume_procedure()` called while a request is still pending withdraws it, broadcasting a snapshot for that too so the indicator comes down as promptly as it went up; the request is cleared on every run lifecycle boundary (`_start_run()`, `_abort_active_procedure()`, `_finish_run()`) so it can never outlive its run. Distinct from **abort**, which is always immediate and ends the run (`abort_procedure()` runs off the click, not the tick, and is unaffected by a pending request). Monitoring, the condition registry, **Hold enforcement** and EMERGENCY all continue through a pause unchanged — they run ahead of the state-machine dispatch in `_tick_body()`; only `run_failure` is suspended, since `run_active` excludes `PAUSED`. |
| **PSU status** | `SuperconductingMagnetVI.magnet_status()`'s return value: the raw hardware status string reported by the PSU driver — `HOLD`, `RAMPING`, `QUENCH`, or `CLAMPED` (the last never actually produced by any driver in this codebase today; the sim driver models clamping as a raised `CryoSoftSafetyError` from `set_current_setpoint()` rather than a status string — kept in `magnet_status()`'s contract and `magnet_state()`'s `"clamped"` branch for a future driver that does report it). A pure passthrough of the driver's own report — never the VI's interpretation. See **Magnet state**. |
| **Magnet state** | `magnet_state()`'s return value: the magnet VI's logical interpretation of **PSU status** plus the live current readings, distinct from the raw hardware report. One of `"standby"`, `"ramping"`, `"holding"`, `"quenched"`, `"clamped"`. PSU status is the source of truth for "is a ramp/park sequence active" — `"ramping"` is returned whenever PSU status is not `HOLD`/`CLAMPED` OR the VI's ramp generator has not yet exhausted (`ramp_status() == "RAMPING"`), so a tick where the PSU momentarily reads `HOLD` mid-sequence (between ramp segments) is never misreported as `"standby"`/`"holding"`. Only once PSU status is genuinely at rest do the current-threshold checks decide `"standby"` (PSU ≈ 0 A) vs `"holding"`. Callers that need "is this magnet actually idle" read `magnet_state() == "standby"`, never raw field/current thresholds — the whole reason this state exists is to give every caller one shared, correct answer instead of each one re-deriving it. |
| **VISA / GPIB** | The instrument-communication standard (PyVISA library) and the bus most lab instruments use. A "resource string" like `GPIB0::19::INSTR` addresses one instrument. |
| **SI units rule** | All APIs use Tesla, Kelvin, Ampere, Volt, second. Display formatting (mK, µA) happens only in the GUI. |
| **Sweep builder** | `core/sweep_builder.py` — reusable sweep-array construction shared by Procedures: `build_piecewise_sweep()` (a `SweepSegment(start, end, step)` list stitched into one array, letting different sub-ranges use different step sizes, e.g. coarse outside a region and fine inside it), `load_custom_sweep_csv()` (arbitrary non-uniform sweep from a single-column CSV), and `apply_hysteresis()` (extends a one-directional sweep into a forward+backward loop). See **Sweep axis** for the declarative way most Procedures use these three. |
| **Measurement root** | `cryosoft.core.paths.measurement_root()` — the fixed, machine-level, admin-set root of the whole measurement-data hierarchy (`<measurement_root>/users.json`, `<measurement_root>/maintenance/<config_name>/...`, `<measurement_root>/sessions/<user_id>/<session_id>/...`). Resolved by precedence — the `CRYOSOFT_MEASUREMENT_ROOT` env var, else the `measurement_root` key in a machine-level settings file (`App-config.yaml` under `%ProgramData%\CryoSoft` on Windows, `/etc/cryosoft` elsewhere) — with no further fallback: an unconfigured installation refuses to start (`RuntimeError`) rather than inventing a default. Deliberately not GUI-editable and not per-user, unlike the QSettings-backed `sessions_root()`/`set_sessions_root()` it replaces, so it stays fixed across a station's lifetime instead of drifting via live settings. `paths.py` is import-linter contract C1 foundation (stdlib only), the same module `log_directory()` lives in. |
| **Session** | The tier between **Measurement root** and an **Experiment**: a named, resumable, per-user folder holding multiple experiments (`Session`, `session/models.py`; persisted as `<measurement_root>/sessions/<user_id>/<session_id>/session.json` by `SessionStore`, `session/store.py`). One user can own several sessions — a session is not identified by its owner alone. Experiment-directory containment under the active session is hard-enforced — a folder name containing a path separator, `.`/`..`, or colliding with an existing one is refused outright by `ExperimentManager.start_experiment()`, not just warned. | **Guest user** | The fixed roster identity (`session.models.GUEST_USER_ID = "guest"`, `GUEST_USER_NAME = "Guest"`) used whenever nobody has logged in (`app_settings.current_user_id()` returns `None`). Auto-registered into `users.json` at every startup (`cryosoft.main._ensure_guest_user_registered`, idempotent — never clobbers an existing, possibly admin-customized, Guest entry), so a logged-out operator always has a real roster entry to own sessions under `sessions/guest/` and to satisfy `ExperimentManager.start_experiment()`'s roster-membership check. A logged-out bootstrap session (`cryosoft.main._resolve_active_session`) is named `"guest"`. |
| **Experiment** | A named group of **runs** on one sample toward one scientific question, owned by the Session Manager (L6): `ExperimentRecord` holds the **user**, the sample-info snapshot, the config identity, the **session envelope**, the run list, free-text findings, the GUI-authored run `queue` (opaque JSON the session layer stores but never interprets — contract C11), and (publishing track) the ELN linkage. Persisted as `<measurement_root>/sessions/<user_id>/<session_id>/<experiment_id>/experiment.json` — one level inside the **Session** tier's own folder (`SessionStore`, `cryosoft/session/store.py`), itself rooted at `cryosoft.core.paths.measurement_root()` (a fixed, machine-level, admin-set location independent of any GUI form field) — alongside a `gui_state.json` (GUI form/plot state, also opaque to this layer) and a `data/` folder holding the experiment's HDF5 files (sub-folders allowed, e.g. `data/heating_runs/`) — the whole `<experiment_id>/` folder is the complete, portable record. `experiment_id` is also the folder's name, directly under the session folder (flat — no nesting); normally auto-derived (`ExperimentStore.make_experiment_id()`) but may be overridden by the operator at Start Experiment time (`StartExperimentDialog`'s Folder name field → `ExperimentManager.start_experiment(experiment_dirname=...)`), still contained to a single path segment under the session. `RunRecord.data_file` is stored relative to that folder when the file lives inside it (`ExperimentStore.relativize_data_file()`/`resolve_data_file()`), so the folder can be copied or moved and still resolve; a file saved deliberately outside it stays an absolute path. Every persisted file (`experiment.json`, `session.json`, `gui_state.json`, both `active.json` files) carries a top-level `schema_version` (`models.SCHEMA_VERSION`, currently `2`); a value newer than the running app's is loaded tolerantly but treated read-only (never re-saved). The `active.json` pointer resumes the open experiment across restarts; `ExperimentManager.switch_experiment()` moves between several open experiments without closing the one switched away from. ELN granularity is **one entry per run**, not per experiment: the publishing track stamps `RunRecord.eln_link` once the backend confirms an entry (see **ELN adapter** and **Outbox**), because the **run manifest** is the unit handed over and a run's HDF5 file is exactly one attachment. `ExperimentRecord.eln_link` remains in the record model, unwritten so far, for a future coarser parent entry. The Experiment tier — as opposed to the **Setup tier** — is what `ExperimentManager.experiment_context()`'s `"experiment"` key holds; empty (`{}`) when none is open. |
| **Experiment index** | `Session.experiments` (`list[ExperimentIndexEntry]`) — a session's enumeration of its own experiment folders: `experiment_id`, `title`, `user_id`, `status`, `created_utc`, `closed_utc`, self-describing via the fixed `experiment_id + "/data"` convention rather than a stored second copy of the data path. Reconciled by `ExperimentManager._reconcile_session_index()` on `start_experiment()`/`close_experiment()`/`switch_experiment()` — the three points an experiment becomes or stops being the one in view — by rescanning `ExperimentStore.list_experiments()` and reading every `experiment.json` found, then replacing the list wholesale (never edited elsewhere), so a session answers "what experiments do I contain and where" straight from `session.json` with no scan for whatever reads it, while the scan itself only runs at those three points. Because it is a full rebuild rather than a per-entry upsert, an experiment folder moved into or out of a session by hand (e.g. handed off to a different user's session to continue the project) is picked up or dropped the next time any experiment in that session opens or closes, and a session that already had experiments on disk before this index existed backfills them all the same way — no separate "move" step, no permanently-stuck-empty index. Each entry's `user_id` is copied verbatim from its `ExperimentRecord` and never re-derived from the session it currently sits in, so a move never rewrites who actually ran the experiment. Flat-only: no nested subfolders. |
| **Setup tier** | The metadata that describes the rig, not any one experiment: which config is active, each VI's **instrument metadata**, and who's logged in. Changes rarely (switching config/instrument description/user), unlike the Experiment tier which changes per run. Not owned by any one L6 class — it's assembled from `core.station.read_instrument_metadata()` + the config's identity (both cached by `ExperimentManager` at construction) and `app_settings.current_user_id()`/`UserRoster` (GUI-level). Surfaced in the GUI through menus (User, Config), not a docked panel — see **User menu**. `ExperimentManager.experiment_context()`'s `"setup"` key holds it, present even with no experiment open. |
| **Instrument metadata** | An optional `metadata:` block per VI in `devices.yaml` (free-text fields — `role`, `manufacturer`, `model`, `notes`, whatever the setup wants to record about what a VI physically is). A setup property like everything else in `devices.yaml`; edited via the Config Editor, never in the running app. Read by `core.station.read_instrument_metadata(config_path)` — YAML-parse only, never imports a driver/VI class, so it's safe to call from the GUI thread. Displayed read-only in `InstrumentInfoDialog` and stamped into every run's `experiment_info["setup"]["instruments"]`. |
| **Run** | One execution of one procedure, producing exactly one HDF5 file. Typed as `RunRecord` (L6): id, procedure, kind (`run`/`probe`), params, data-file path, timestamps, terminal status (`done`/`failed`/`aborted`), and the **Actor** that started it. Recorded automatically from the Orchestrator's **run manifests**; runs outside an open experiment are not recorded (their HDF5 file still exists, unstamped). The actor is the one fact the manifest does NOT carry — it is taken from the contract's `RunStarted` event, emitted right after the manifest signal — so an agent-started run stays distinguishable from the physicist's long after the process is gone. A record with no readable actor (every run written before actors were stamped) loads as the `OPERATOR` sentinel with `RunRecord.actor_legacy` set: "old file" must never read as "the physicist did it". `RunRecord.params_digest` is the **Params digest** of `params`, stamped from the manifest as the run opens and stored rather than recomputed, so the record fixes what the run actually started with. |
| **User** | The person measuring — identity, not authentication. `User` records (id, name, email, ORCID, ELN identity) live in the setup-local roster `users.json` next to the app settings, managed by `UserRoster`. Experiments reference a roster `user_id`, and the id/name are stamped into every run's HDF5 `experiment_info`. |
| **ELN adapter** | The L6 standard for talking to one electronic lab notebook: a stateless, synchronous wrapper (`cryosoft/session/eln/adapter.py`'s `ElnAdapter`) exposing EXACTLY six methods — `verify`, `list_templates`, `create_entry`, `update_entry`, `attach_file`, `attach_link` — built from a single plain settings mapping (the analogue of the driver contract's one-resource-string rule), declaring a lowercase `backend` id and an `ElnCapabilities` flag set callers branch on instead of the backend name, and raising exactly one exception type, `ElnError`. Queuing, retry, and backoff live in the **Outbox**, never in an adapter; no network I/O exists anywhere else in the application, and none of it is ever reachable from the Orchestrator tick. `elabftw.py` (eLabFTW REST API v2, one injectable transport) is the first backend; because the contract fixes the public API exactly, ONE sim twin (`sim_eln.SimElnAdapter`, modelling offline, transient failure, and refused uploads) stands in for every backend, with a backend's own HTTP dialect faked one level lower at its transport — the `sim_` driver rule, applied to notebooks. Machine-checked by the ELN-adapter conformance tests, so a new backend is one leaf module with zero core changes. |
| **Outbox** | The journal that makes ELN publishing offline-first: `<measurement_root>/sessions/<user_id>/<session_id>/<experiment_id>/outbox.jsonl` (`ExperimentStore.outbox_path()`, read and written by `cryosoft/session/eln/outbox.py`'s `Outbox`). Nothing in CryoSoft publishes directly — a finished **run** is rendered in full and QUEUED as one appended JSON line, and a GUI-side drain later hands one job at a time to an **ELN adapter**. Same append-only, last-line-wins entry-revision discipline as the **Maintenance log**: a job is never rewritten in place or deleted, corrupt lines are skipped with a WARNING, and a crash can lose at most the newest revision. Idempotent by `job_id` (`"publish_run:<run_id>"`), so a duplicate `RunFinished` or a repeated manual export publishes once; the created entry's reference is journaled the instant `create_entry` succeeds, so a retry after a failed attachment resumes at the attachment instead of creating a second entry. Retry state (attempts, last error, next-due time under exponential backoff capped at `retry_max_s`) is persisted, not held in memory, and there is no terminal failure state — an offline week is what it exists for. `drain()` publishes at most one job per call and NEVER raises into its caller, because that caller is a QTimer in the GUI process. |
| **Pending entry** (formerly, and still, **Draft entry**) | One ELN entry waiting for a human to approve it, whatever produced it: `session/eln/drafting.py`'s frozen, JSON-safe `DraftEntry` — a title, an escaped self-contained `body_html`, tags, `attachments` (`{path, comment}`, an **analysed entry**'s figures), `attach_data_file`, extra `metadata` (an analysed entry's `recipe`/`recipe_digest`), a `source` (`model` | `analysis` | `facts`) and the cost line the drafting itself incurred (`model`, `input_tokens`, `output_tokens`, `cost_usd`, `prompt_digest`). It rides on the run record as `RunRecord.pending_eln_draft` (the field name keeps the older word, for the record schema) and is cleared by `ExperimentManager.approve_eln_draft()`, which hands it to `ElnPublisher.export_draft()`, or by `discard_pending_eln_draft()`, which drops it. Three sources park one: LLM **drafting** (`source="model"`, produced by the `draft_eln_entry` **Tool spec** from one run's manifest-shaped facts, its per-column `summary_stats` and the **Station info** / `StatusSnapshot` mirrors, and returned AS DATA through the same **Tool surface** every other action goes through — drafting is a `read`-class action that publishes nothing); the analysis stage (`source="analysis"`, `ElnPublisher.export_report()`); and the facts-only fallback (`source="facts"`, `park_facts_entry()`) parked when a recipe failed, timed out or never ran, so a run is never left with nothing waiting. A model draft's body puts the drafted prose ABOVE the same escaped fact tables a published run gets (`render_draft_body()`), so a reviewer checks every drafted sentence against the numbers beneath it and a useless completion still yields a complete, correct entry; `prompt_digest` is the SHA-256 of the exact prompt's both halves, so two drafts of one run are provably the same question. In an ATTENDED experiment an agent's `publish_eln_entry` is refused (`rule: approval_required`) and the draft is parked instead; UNATTENDED, the `session` role may publish it straight into the **Outbox** (`debug` and `observer` never can) — but with the analysis stage on, EVERY entry is parked, attended or not, because approval is the gate that design chose. |
| **Analysed entry** | The notebook entry the analysis stage produces: one **Analysis report** rendered by `session/eln/templates.py`'s `render_analysed_title()` / `render_analysed_body()` and parked as a **Pending entry** with `source="analysis"` by `ElnPublisher.export_report()`. Its body is what a physicist wants in the notebook, in reading order: the recipe's prose, its derived values (name, value with unit, ± uncertainty, note), its figures as a captioned list NAMING the attached file (never an `<img>` — the body stays self-contained and the PNG travels as an **Outbox** attachment), its own tables, any warnings, the experiment's findings, and last a compact provenance block: experiment, run id, procedure, kind, **Params digest**, start/finish, outcome, data-file name, and the recipe by `name` and source `recipe_digest`. The run's full fact tables are appended ONLY when the report's `include_fact_tables` says so, and the raw data file is attached only when its `attach_data_file` does — the point of the stage is that what reaches the notebook is the result, not the raw facts. A failed report renders its `error` under its own heading rather than an empty entry. Deterministic, escaped and length-capped like every other rendered body. |
| **eLab setup** | The in-app configuration of the notebook and the analysis stage — `cryosoft/gui/eln_settings_dialog.py`'s `ElnSettingsDialog`, reachable from the procedure window's eLab tab and the Monitor window's Setup menu — and the file it writes: the user-level `ElnSettings` resolved by `eln_settings_path()`, written back by `session/eln/settings.py`'s `save_eln_settings()` (atomic temp-file-and-replace, parent directory created, `0o600` on POSIX) and re-read by `load_eln_settings()`. It holds the backend id, base URL, API key, team and template ids, TLS verification, auto-publish, tags and attachment cap, the assistant's own section, and the analysis section (`AnalysisSettings`: `enabled`, `timeout_s`, `include_fact_tables`, `attach_data_file`, and the per-procedure `recipes` preference). NEVER a shipped config and never git-tracked: an ELN account is a property of the person and the installation, and a key must never travel with a config directory. The key is redacted from `repr()` and from `to_dict()` unless a caller explicitly asks for the secret, and it never reaches a label, a tooltip or a log line. Saving hands the record to `ElnPublisher.reload_settings()`, which resolves the backend adapter afresh and starts or stops the drain timer according to `is_configured`. |
| **Draft client** | The one model call the ELN track makes, as an injectable collaborator: `session/eln/drafting.py`'s `DraftClient` protocol — a single synchronous `complete(system, user, max_tokens) -> CompletionResult`, no streaming, no tools, no conversation, raising the same `ElnError` an **ELN adapter** does so a caller has one exception type for either. `FakeDraftClient` is its in-memory twin (the `sim_` driver rule applied to the model: it records every prompt and models the unreachable-model failure), and is what every test runs against — no test ever reaches a network. `AnthropicDraftClient` is the real one; its SDK is the OPTIONAL `assistant` extra, imported lazily so a checkout without it imports the package, renders prompts and passes the suite unchanged, and gets one clear `ElnError` naming the install command only when a real client is constructed. Its model id, token cap, key and per-model price table come from the user-level settings file's `assistant` block (`AssistantSettings`, key redacted from `repr()`/`to_dict()` exactly as the notebook's is, overridable by `CRYOSOFT_ASSISTANT_APIKEY`); an unpriced model reports `cost_usd` of `0.0` and a WARNING rather than a guess. |
| **Analysis recipe** | The code that turns ONE finished **run** into ONE **analysis report**: a plain class subclassing `cryosoft/analysis/base.py`'s `AnalysisRecipe`, declaring a snake_case `name`, a one-line `description` and the procedure CLASS NAMES it serves (`procedures`, or `("*",)` for every run), and implementing `analyse(run, context) -> AnalysisReport`. It reads the run only through the **Run source** vocabulary and makes its figures and tables only through the `AnalysisContext` (`pyplot()`, `figure()`, `table()`), so it needs no file path of its own and closes nothing by hand. Recipes live in two places under one contract: the shipped ones in `cryosoft/analysis/recipes/`, auto-discovered exactly as drivers, VIs and procedures are, and an experiment's own `<experiment>/analysis/recipes/*.py`, loaded BY FILE PATH and overriding a shipped recipe of the same `name` — so a physicist or an agent writes an analysis at runtime without editing the application. `discover_recipes()` returns them in selection order (package recipes by declared `priority`, highest first, then by name) and skips a script that fails to import with a WARNING rather than hiding every other recipe; `recipe_for(procedure, recipes, preferred)` picks the preferred name, else the first recipe naming the procedure, else the first `("*",)` one. A recipe is trusted like a procedure: an agent-written one is a `run_control` action, stamped with the actor and time and recorded in the **Agent feed**. |
| **Analysis report** | Everything one **analysis recipe** produced for one **run**, and the ONLY thing downstream reads: `cryosoft/analysis/report.py`'s frozen, JSON-safe `AnalysisReport` — `summary` (plain-text paragraphs), `results` (`ResultValue` rows: name, value, unit, uncertainty, note), `figures` (`FigureRef`, a file name relative to the report directory so the report travels with its experiment folder), `tables` (capped `TableSpec`s), `tags`, `include_fact_tables`, `attach_data_file`, `warnings`, plus the provenance the runner stamps: `recipe`, `recipe_digest` (SHA-256 of the recipe's source, so an entry says which code produced it), `started_utc`, `duration_s`, `options` — and `status` (`ok`/`failed`) with `error`. Persisted as `report.json` in `<experiment>/analysis/<run_id>/` beside its PNGs, written atomically because a reader may look while the worker is still writing. Every size is capped here rather than at render time (`MAX_TABLE_ROWS`, `MAX_FIGURES`, `MAX_RESULTS`, `MAX_SUMMARY_PARAGRAPHS`, `MAX_TEXT_CHARS`), so a report is always small enough to preview, to journal and to hand to a model; bulk data stays in the HDF5 file, which the report can ask to attach. A FAILED report is a complete answer, not an absence: it carries the recipe, the traceback in `error` and whatever `warnings` accumulated, which is what lets the notebook fall back to a facts-only entry instead of losing the run. |
| **Analysis worker** | The separate process an **analysis recipe** runs in: `python -m cryosoft.analysis run --spec <file>`, started by `session/analysis_runner.py` with `QProcess` and bounded by a settings timeout. Its request is an `AnalysisSpec` (`report.py`) written as JSON — run id, data-file path, run manifest, experiment and setup facts, recipe name, extra recipe directories, output directory, options — carrying no credential and no live object; its answer is `report.json` plus the figures. Out of process for the same reason the **MCP adapter** is: recipe code is user code that may take seconds and may crash, and a process that cannot IMPORT the Station, the Orchestrator, a driver, a VI, a procedure or the session layer (import contract C22, with C23 forbidding the reverse) cannot touch an instrument, edit an experiment record or publish anything — the single hardware thread standard's client-side rule, one step further. It exits 0 even when the analysis failed, because a failed **analysis report** IS the answer and the caller reads the report, not the exit code; exit 2 means there was no answer to write at all (an unreadable spec). matplotlib is the OPTIONAL `analysis` extra it imports lazily with the `Agg` backend, so a checkout without it runs every recipe that draws nothing and turns a figure request into one warning naming `pip install cryosoft[analysis]`. |
| **Agent gateway** | `cryosoft/session/gateway/` — the SECOND adapter of the **Control contract**, not a second API: an autonomous client submits the same `Command`s the GUI does, receives the same **Verdict**s, and sees the same **Event stream**, so each client reflects what the other did for free. What it adds on top of the contract is authority — a declared **Role**, every action's **Action class**, and the human's **Attendance** and **Kill switch** — and nothing else: the Orchestrator's admission rules, the **Control-validation standard**'s limits and the **Session envelope** bind an agent exactly as they bind the human. In-process only (no network, no thread, no socket). Bound by import-linter contracts C11/C12 like the rest of the session layer, which is precisely why attendance and the kill switch reach the enforcement point as pushed-down VALUES rather than as records this layer reads. |
| **Gateway** | `session/gateway/gateway.py`'s `Gateway` — one authorised, identified connection to the engine, and what an autonomous client actually holds. Deliberately thin, because thin IS the design: it stamps `Actor(kind="agent", id=..., role=...)` on every command, runs `authorize()`, and then either forwards to the engine's `submit()` or answers the request itself with a `BLOCKED_ROLE` **Verdict** on the engine's OWN `verdict_emitted` stream — so exactly one verdict answers every request either way, a refused command never reaches the engine, and the human's window sees an agent being refused exactly as it sees it being obeyed. Every read is answered from its local mirror of the latest `StatusSnapshot`/**Station info**, **Attendance** and the **Kill switch** included, following the **Verdict standard**'s rule that a client never calls into the engine for a read. The engine is duck-typed (`EngineClient`: `submit(Command)` plus the two contract streams, reached through `verdict_stream()` / `event_stream()` because a client adapter consumes them as `verdict`/`event` while the engine declares them as `verdict_emitted`/`event_emitted`), so the **Orchestrator proxy** on the GUI thread, the Orchestrator on the instrument thread and a transport proxy later are interchangeable. In-process: no Qt import, no network, no thread. |
| **Gateway server** | `session/gateway/local_server.py`'s `GatewayServer` — the **Agent gateway** reached from ANOTHER PROCESS, over a local socket, with nothing else changed. A `QLocalServer` living on the GUI thread's own event loop, built over the **Orchestrator proxy** like every other client on that thread — a frame is parsed in an ordinary slot that posts its command to the **Instrument thread**, so this adds no thread of its own and no second writer to the bus. Every connection owns exactly ONE **Gateway**, built at its handshake with the **Role** and actor id it declared, so an out-of-process client is authorised by the same matrix, recorded in the same **Agent feed** and seen in the same **Event stream** as an in-process one — the transport adds a wire and nothing else. The wire is newline-delimited JSON-RPC 2.0: `hello {role, actor_id, token}` first (nothing else is answered before it), then `tools/list`, `tools/call {name, args}`, `status`, `station` and `events/subscribe`, which turns the connection into a listener for `event` (`StateChange`/`StatusSnapshot`) and `verdict` notifications. Two things bound what a connection may claim: the per-launch random token, written with the socket name, pid and schema version to `gateway.json` beside the socket with owner-only permissions, and the deployment's ceiling (`monitor.yaml`'s `gateway_max_role`, read cell by cell off `PERMISSION_MATRIX` by `role_within_ceiling()`, so no second ordering of the roles exists). Off unless `monitor.yaml` says `gateway_server: true` — opening a station to autonomous clients is a setup decision, like every limit. Nothing a client writes can raise into the event loop: a partial read is buffered, an oversized frame ends the connection, and malformed JSON, an unknown method and an unexpected failure are all answered as JSON-RPC errors. |
| **MCP adapter** | `cryosoft/mcp/` — the **Gateway server**'s wire translated into the Model Context Protocol, in a SEPARATE PROCESS (`python -m cryosoft.mcp`). It speaks MCP over stdio to an external agent session and newline-delimited JSON-RPC over the local socket to the running app, and does nothing else: it holds no Station, no Orchestrator and no session layer, and import contract C21 allows it exactly one CryoSoft import — `cryosoft.core.events`, the pure contract — so there is no code path from the thing facing the outside world to an instrument, and adding one fails the build rather than a review. Nothing on it is hand-written per tool: `tools/list` is the gateway's own list re-keyed from `input_schema` to MCP's `inputSchema`, `tools/call` is forwarded verbatim in both directions, and each of the three resources (`cryosoft://status`, `cryosoft://station`, `cryosoft://manifest`) is a URI over one of the read tools the **Tool surface** already offers — so a tool added to the app reaches an external session with no change to the adapter. A refusal is a RESULT, not a protocol error: the gateway's own answer, naming the rule that refused, travels where the model can read it (`isError: true`), following the **Verdict standard**'s rule in another protocol; a JSON-RPC error is reserved for an unserved method, unreadable parameters, an unknown URI and a failed connection. `StateChange`, `StatusSnapshot` and `Verdict` travel the other way as the spec-defined `notifications/message`, whole, in `data`. Serves both protocol eras — the handshake-based `initialize` and the stateless `server/discover` — and caches nothing (`ttlMs` 0), because the tool surface grows when an instrument connects. Two framing backends: `shim.py` (stdlib only, the reference backend, the one the tests exercise, and the one that watches stdin and the socket together so an event arrives the moment it is emitted) and `sdk.py` (the optional `mcp` extra, which declines to serve rather than serve partially when the installed package is not the one it was written against). |
| **Role** | The authority a connection to the **Agent gateway** declares for itself, written into `Actor.role` on every command it submits so a refusal, a run record and the action feed all name it: `observer` (reads, changes nothing), `debug` (reads, and takes `recovery` actions ONLY while unattended) and `session` (runs the experiment — recovery and run control, within the envelope the human set). `session/gateway/roles.py`'s `Role`. The human is deliberately NOT a role: `authorize()` returns "permitted" for any actor that is not an `agent`, because a permission model that could refuse the operator at their own cryostat would be a hazard rather than a safeguard. |
| **Action class** | How much authority one action needs, independent of who is asking: `read`, `recovery` (instrument housekeeping that keeps a run alive — pause/resume, VI initiate/standby, re-send config, adjust waits), `run_control` (starts, stops or redirects the measurement, or commands energy into the cryostat) and `envelope` (the **Session envelope**, **Attendance** and the **Kill switch** — the rules the other three are judged by, so no **Role** may change them). Crossed with `Role` in the single `PERMISSION_MATRIX` table that IS the gateway's permission standard. **Where the class comes from** is split by who owns the judgement: a `@control`'s class is DECLARED beside it (`@control(action_class=...)` — the *action-class declaration*, validated at import against `core/decorators.py`'s `VALID_ACTION_CLASSES`, carried to the gateway on `ControlInfo.action_class` and read there by `classify_control()`), because how dangerous an instrument's action is is a judgement about that instrument; the engine's own command surface and the two lifecycle actions (`initiate`/`standby`, which carry no decorator) stay as tables in `session/gateway/action_classes.py`, one row each with the one-line rationale a refusal quotes. The decorator's default is `run_control`, the most restrictive class an agent can ever hold, so a forgotten declaration never widens authority — and conformance requires every shipped control to declare it explicitly anyway. A command with no row, or a capability no instrument declares, is refused by name rather than defaulted. |
| **Tool surface** | What the **Agent gateway** publishes an autonomous client: one **Tool spec** per action it may take, with a JSON Schema for its arguments. `session/gateway/tools.py`'s `render_tools(station_info)`, offered by `Gateway.tools()` / `tool_schemas()` and called through `Gateway.call_tool(name, args)`. Its standard is that a tool is RENDERED, never hand-written: one command tool per `CommandName`, described by the first paragraph of the Orchestrator method's own docstring and shaped by its signature; one capability tool per `(instrument, @control)` the **Station info** snapshot declares, shaped by that control's `ParamSpec`s with the CONFIG's limit as the bound — so an agent reads "-9 to 9 T" off the tool and an out-of-range argument is refused, naming the bound and its unit, before a `Command` is ever built. The four commands whose JSON `args` `Orchestrator.submit()` translates rather than passing straight through are declared once in `COMMAND_ARG_SCHEMAS`, each with the rationale for why it deviates; a command this module cannot render and that has no entry there fails to render rather than being guessed at. Only the SESSION TOOLS are hand-declared, because they are not commands: the reads over the experiment store, the run files (always through `ExperimentStore.resolve_data_file()`, never a caller-supplied path), the operational log and the agent action feed, plus **Run validation**, a **Probe run**, the two that reach the ELN track — `draft_eln_entry` (`read`: it renders one finished run's facts into the draft prompt and returns the **Draft entry** as data, writing and queuing nothing) and `publish_eln_entry` (`run_control`: the only tool that reaches the **Outbox**, refused for every agent while the experiment is ATTENDED, with the draft parked on the run record for the human instead) — and the five that reach the analysis stage: `list_analysis_recipes`, `read_analysis_recipe` and `read_analysis_report` (`read`), and `write_analysis_recipe` / `run_analysis` (`run_control`, `recorded`), which put a recipe on the measurement machine and start the analysis worker that executes it, one stamped with the actor and the UTC time that wrote it and both recorded in the **Agent feed** — the source as its size and digest, since the file is the copy — so a physicist sees the code in the eLab tab before anybody runs it (`session/gateway/README.md`'s trust boundary). `call_tool()` answers every call and raises at none — an unknown tool, a schema violation and an absent collaborator are one `FAILED`-shaped dict whose `detail` names the rule. Conformance diffs the surface against `CommandName` and against every shipped config's **Capability manifest**, both in both directions: the third leg of the three-way test (contract, engine, tool surface). |
| **Tool spec** | One entry of the **Tool surface**: `session/gateway/tools.py`'s frozen, JSON-safe `ToolSpec` — a name, a description in the words of the declaration it was rendered from, a closed object JSON Schema for its arguments (`additionalProperties: false`, every declared control parameter required so no argument can silently fall back to a method default), the **Action class** the permission matrix judges it by, and the routing: EXACTLY one of a `CommandName` (plus the `fixed_args` a capability tool carries — its own `vi_name` and `method_name` — so the caller is never asked for them) or a session-function key. It also declares `recorded`: whether a call is written to the **Agent feed**, which is how a SESSION tool — answered inside the client, where no **Verdict** exists to be found under — leaves a trail at all. Declared per tool rather than derived from the **Action class**, because the two questions differ: a `read` tool an agent polls every tick would drown the trail in observations, while a `read` tool that spends model tokens is exactly what the trail is for. `to_schema()` renders the `{name, description, input_schema}` shape a tool-use API reads, so every client publishes the same list with no rendering code of its own. |
| **Attendance** | Whether a human is watching the running experiment. Owned by the session layer (`ExperimentRecord.attended`, `ExperimentManager.set_attended()`) and pushed DOWN into the engine as a value by `Orchestrator.set_attendance(attended)`, exactly as the **Session envelope** is and for the same reason: import-linter contract C12 forbids anything below the GUI from importing the session layer, so a policy the session record owns cannot be read at the place it has to be enforced. The engine restricts nothing on it — it stores the value and mirrors it on every `StatusSnapshot`, so every client's permission check reads the one fact rather than a copy of its own. It becomes load-bearing in the **Agent gateway**'s permission matrix, where a `debug` **Role** may take **Action class** `recovery` only while UNATTENDED: with a human present the agent diagnoses and reports, and the human decides. Defaults to `True` (attended), the restrictive reading for an agent asking to act alone. |
| **Kill switch** | The human's tri-state control over how much of the engine autonomous actors may reach: `events.AgentGate` — `active` (agents act normally, their **Role** decides), `read_only` (agents may take `read`-class actions only) and `revoked` (agents may take no action at all). Pushed down as a value by `Orchestrator.set_agent_gate(state)`, mirrored on `StatusSnapshot.agent_gate`, and ENFORCED in `Orchestrator.submit()` before any command is dispatched — the single choke point every writer passes, because a gate enforced in the client that submitted the command would only bind a client that chose to be bound. A gated command is answered `BLOCKED_ROLE` with `gate`/`actor_kind`/`actor_id` in the verdict's `detail`. Two exemptions are the point of the design: an `operator` or `system` actor is never checked (flipping the switch must never lock the human out of their own instrument), and `emergency_standby` passes at every setting (nobody who can see a problem may be unable to make the station safe). |
| **Run owner** | The `Actor` that STARTED the run in flight, and the authority over the command that would end it. Stamped by `Orchestrator._start_run()`, published on every **Status snapshot** as `run["owner"]` (the owner's `Actor.ref()` — kind and id) and readable through `StatusMirror.run_owner()`; a run pulled off the **Run queue** is owned by whoever QUEUED it (`RunSpec.actor`, carried onto the built run as `queued_by`), because the decision to run it was theirs and the actor draining the queue may be the tick itself. Ownership is a FACT, never a lease: nothing is reserved, nothing expires, nothing can be left locked and there is no handover protocol — the run ends and the owner is gone with it. It gates exactly four commands, and only for an `agent` **Actor**: `abort_procedure`, `confirm_operation`, `skip_operation_step` and `finish_operation` (`orchestrator.OWNER_SCOPED_COMMANDS`), the ones that end somebody's result or attest that a physical step of it was carried out. An agent that is not the owner is answered `BLOCKED_ROLE` with `detail.rule == "run_owner"` and `detail.owner`, and told how to proceed; the **Kill switch**'s two exemptions apply here in the same words and for the same reasons — an `operator` or `system` actor is never checked, and no safety or recovery command is owner-scoped (`emergency_standby`, `stop_ramp`, `pause_procedure`, `resume_procedure`, the gate and attendance all ignore it), because holding the cryostat where it stands destroys nobody's result. Enforced in the engine, by the `command` decorator's admission rather than by `submit()`, so the **Request spool**, the **Gateway server**'s socket and a direct Python caller all pass it; `roles.authorize()` mirrors the same rule off the snapshot so a tool call is refused at the front door with the same words. |
| **Takeover** | One agent doing an owner-scoped command on another actor's run ON PURPOSE and ON THE RECORD — the override half of the **Run owner** rule, and the reason the rule refuses rather than forbids. A refused command re-sent with `override_owner: true` and a non-empty `reason` is admitted, and every surface then says so: the **Verdict**'s `detail.takeover` carries `{owner, reason}`, a `RunFinished` the takeover caused carries the acting `actor` AND the `overridden_owner` it ended the run over, the **Agent feed**'s verdict record carries the same detail, and the **Agent panel** renders the row distinctly as "took over <owner>'s run: <reason>". An override with no reason is itself refused (`detail.rule == "override_reason_required"`): a takeover whose record cannot say why is exactly the unaccountable act the rule exists to prevent. Not a permission — the acting agent still needs the **Role** for the action; not a transfer — the run keeps the owner it had, and the takeover is what is added beside it. |
| **Request spool** | The file-based write path into a RUNNING application — the first rung of the transport ladder, and the one that adds no thread, no socket and no timer. `cryosoft/core/request_spool.py`'s `RequestSpool`, rooted at `<log directory>/spool/` (`spool_directory()`). A client drops one JSON file per **Command** into `requests/<request_id>.json` — `{schema, role, command}`, written atomically (dot-prefixed temporary file, then rename) and NAMED for its correlation id, which is what lets a request that cannot be parsed at all still be answered. `Orchestrator._tick_body()` drains it at the same point it drains queued manual actions: read, re-validate, `submit()`, delete — so the tick stays the single writer and a request is judged by the state at the moment it is carried out, never by the state when it was written. Two transport rules run before the permission model: a spooled request may not claim the `operator` actor kind (the operator's authority comes from standing at the cryostat, not from a file on disk), and its declared **Role** is capped by the setup's `monitor.yaml` `spool_max_role` (`observer` by default) — a cap that, like the **Kill switch**, only ever subtracts and never applies to **Emergency standby**. Then `session/gateway/roles.py`'s `authorize_spooled()` applies the ordinary matrix, injected as an `Authorizer` hook because contract C12 keeps `core` from importing the session layer. The answering half is three files a client reads instead of asking: `verdicts.jsonl` (every **Verdict** the engine emitted, plus a `"command": null` record for a request that never became a command, so there is exactly one answer per request written), a size-capped `events.jsonl` of `StateChange`/`StatusSnapshot`, and `station.json` holding the latest **Station info** where the cap can never drop it. Off unless `monitor.yaml` says `request_spool: true`. |
| **Reference client** | `python -m cryosoft.ctl` (`cryosoft/ctl/`) — the terminal end of the **Agent gateway**, and the second thing after the GUI to speak the control contract from outside the engine. One JSON object per invocation on stdout, over the same **Tool surface** an in-process agent is offered: `tools`, `schema <tool>` and `call <tool> --args JSON` reach every tool the station publishes, and `status` / `station` / `manifest` / `runs` / `feed` / `pause` / `resume` / `abort` / `emergency-standby --reason` are shorthands for the calls made often enough to deserve a word — so a new command or capability needs no code in the client at all. Two transports, one authority model: `--offline <config_dir>` builds the Station, the engine and the session layer in this process (`InstrumentHost(mode="inline")`) and drives the tick by hand, since a one-shot command has no event loop; **live** (the default) writes one request file into the **Request spool** and reads the verdict the running tick appends, answering its reads from the spool's mirror and the session store on disk. The declared **Role** (`--role`, `observer` by default) and **Actor** id (`--actor`, `ctl:<user>@<host>` by default) travel ON the request and are judged at the engine — live, capped again by `spool_max_role` — so the client decides no refusal of its own. Three exit codes, and they are the API: `0` the answer is `ok`, `1` the request was reached and REFUSED or FAILED (`detail.rule` says which), `2` no engine was reached so nothing was asked (no spool, a verdict that never arrived, a config that would not build). It opens no experiment — `envelope`-class work belongs to no role — and it is a leaf: contract C20 keeps it out of the GUI, the drivers and the VIs, and nothing in `cryosoft` imports it. |
| **Agent feed** | `<measurement_root>/sessions/<user_id>/<session_id>/<experiment_id>/agent_actions.jsonl` (`ExperimentStore.agent_feed_path()`, written and read by `cryosoft/session/agent_feed.py`'s `AgentFeed` / `read_feed()`) — one experiment's accountability trail of everything a NON-operator **Actor** asked for and was told. One JSON object per line, appended and never rewritten; unlike the **Outbox** and the **Maintenance log** (journals of entities, where the last line naming an id wins) this is a journal of facts, ordered by a per-file `seq` that continues where an earlier process left off, and nothing ever supersedes an earlier line. Four record kinds — `command` (what was asked, arguments included), `verdict` (the engine's single answer), `event` (a `StateChange` an agent caused) and `tool` (a call of a **Tool spec** declaring `recorded`, carrying its arguments, its answer and, for a **Draft entry**, the cost line `model`/`input_tokens`/`output_tokens`/`cost_usd`) — the first three joined by `request_id`, which is also the key that joins this trail to the **Operational-status record**'s; a `tool` record carries none, because a session tool is answered inside the client and there is no engine request to join to. Every record carries every key of the standard, `null` where one does not apply (`schema`, `ts`, `seq`, `experiment_id`, `run_id`, `record`, `actor`, `request_id`, `command`, `tool`, `args`, `event`, `detail`, `verdict`). Command and tool records are written by whoever submits or answers them — the **Gateway**, the only place a command's arguments or a session tool's answer are in hand — while verdicts and state changes are read off the engine's own streams (`AgentFeed.attach()`), so an agent that reaches the engine WITHOUT passing through a gateway still leaves a trail: the actor kind travels on the message, not on the connection. Operator traffic is deliberately absent — the physicist's own actions are the rest of the session record, and mixing the two would spoil the question this file exists to answer. Recording never raises into the engine: it sits on the emit path, so a full disk degrades to a WARNING. |
| **Params digest** | `core/plan.py`'s `params_digest(params) -> str` — the stable SHA-256 fingerprint of one parameter set, stored on a **Run** record (`RunRecord.params_digest`, stamped from the run manifest when the run opens). A record saying a run happened or a physical step was confirmed is only evidence if it also says WHAT was confirmed; by then the parameters live in several places (a run manifest, a queue entry, an operation's own defaults) and none of them can prove it is the copy that was in force. Two records agree about the parameters exactly when their digests match, and neither has to carry the other's copy. **The canonicalisation is part of the standard**, not an implementation detail, because a digest nobody can reproduce is not evidence: `json.dumps` with keys sorted, no whitespace, floats as `repr()` gives them, non-ASCII left as itself, and any value JSON cannot render replaced by its `str()`; that UTF-8 text hashed with SHA-256 and returned as 64 lowercase hex characters. Key ORDER therefore never matters and key SPELLING always does; `None` and `{}` give the same digest, because "no parameters" is one fact rather than two. Stored, never recomputed on read — a record amended later must not be able to rewrite what the run started with — so a record written before digests were stamped carries an empty string rather than a digest invented on its behalf. |
| **Run manifest** | The dict the Orchestrator emits on `run_started` (once per run, after a successful `initiate()`) and re-emits on `run_finished` (with `finished_utc`, terminal `status` done/aborted/failed, `reason`, and `summary` added). Carries `run_id`, `procedure`, `kind` (`run`; probe runs carry `probe`), `params`, `data_file` (the HDF5 path, captured at start because the procedure closes its file before the run ends), and `started_utc`. `summary` is the duck-typed `procedure.run_summary()` result — `{}` for a procedure that does not override it — merged in by the Orchestrator; a raising or non-dict override yields `{}` rather than blocking the run. The session layer records runs from these signals; a run whose setup fails emits no manifest. |
| **Session envelope** | `core/plan.py`'s `ExperimentEnvelope` (+ `EnvelopeBound`): per-experiment safety bounds narrower than the config limits, keyed by system VI name. Config `init_params` limits protect the *instrument* (setup property, YAML); the envelope protects the *sample* mounted for one experiment (experiment property, set by the session layer via `Orchestrator.set_experiment_envelope()`). Enforced in the Orchestrator so it binds every writer — targets are validated before dispatch (violation ⇒ the plan is rejected), a manual action on the **Direct action path** is validated the same way on the parameter the **Setpoint-parameter convention** identifies (at submission and again when the tick drains the queue), and each bound with a `state_key` is checked against the VI's live reading every tick: a violation becomes an envelope-origin, critical-severity `Condition` (`core.conditions.envelope_conditions()`, see **System condition**), folded into the same tick's condition list `decide()` consumes, so it drives EMERGENCY unconditionally — exactly like a tripped **Critical safety flag** — since a violation has no per-VI attribution to narrow it to a **Safety hold** instead. |
| **Maintenance log** | The L6 framework for per-setup, human-facing logs of maintenance events (`session/maintenance_log.py`). Each log is one **log kind**; entries are typed records, editable via **entry revisions**, persisted append-only as one JSONL file per kind per setup. Independent of experiments; what technical staff consult and maintain. |
| **Log kind** | One declared maintenance-log table: a key (the shipped one is `"maintenance"`), a title, and an ordered field schema (reusing `ParamSpec`). Adding a log kind for a new setup is a declaration (`LogKindSpec` in `DECLARED_LOG_KINDS`) plus a config reference — the storage, revision handling, table view, and add/edit dialogs all follow automatically. The standards-over-one-off-code move, applied to records. |
| **Entry revision** | How editability and trustworthiness coexist: every maintenance-log entry has a stable `entry_id`; an edit appends a new revision (`revised_utc`, `revised_by`) rather than rewriting; a deletion appends a tombstone. The store presents the latest revision per entry; the full history stays on disk. The file itself is never rewritten. |
| **Sweep axis** | `core/sweep_builder.py`'s `SweepAxis` dataclass + `sweep_axis_param_specs()` + `build_axis_sweep()` — the systematic, low-code way a Procedure gets sweep-shape flexibility (linear range / piecewise segments for a fine subfield / custom CSV, each optionally with hysteresis). A Procedure declares one `sweep_axis = SweepAxis(key=..., unit=..., data_key=..., description=..., default_start=..., default_end=..., default_steps=...)` class attribute (see `FieldSweep`, `TemperatureSweep`); `BaseProcedure.__init_subclass__` merges its seven hidden parameters (`{key}_mode`, `{key}_start`, `{key}_end`, `{key}_steps`, `{key}_segments`, `{key}_csv_path`, `{key}_hysteresis`) into `cls.parameters`, and the default `_build_sweep_array()` delegates to `build_axis_sweep()` — no per-procedure sweep-array code is needed. `gui/sweep_axis_widget.py`'s `SweepAxisWidget` renders the matching mode-selector form (Linear / Segments / CSV + a hysteresis checkbox) automatically in `ProcedureWindow`; a new sweep procedure never needs its own GUI code, only the `sweep_axis` declaration. |
| **Control contract** | The frozen, JSON-safe message families in `core/events.py` that the Orchestrator and its clients exchange: a client sends a `Command`, gets back exactly one `Verdict`, and sees the consequences as `Event`s (`StateChange`, `StatusSnapshot`, `StationInfo`, `Readings`, `Datapoint`, `RunStarted`, `RunFinished`, `QueueChanged` — each carrying `seq`, `ts`, a `kind` discriminator for `event_from_json()`, and where relevant `request_id` and `actor`). The engine has exactly two clients, the GUI and the agent, and the contract is declared ONCE so both are rendered from it — neither can offer an action the other cannot see, and each reflects what the other did, because every message names its **Actor**. Every type is a frozen dataclass with JSON-safe fields and `to_json()`/`from_json()`, round-tripped by conformance, which is what lets the same declaration cross a thread boundary and later a process boundary with no second contract. |
| **Actor** | `core/events.py`. Who acted: `kind` (`operator` \| `agent` \| `system`), `id`, `role`. Carried on every `Command` and on every event it causes, so accountability is a value rather than an ambient fact — the status bar can say "paused by agent", the queue shows who queued a run, and an agent's self-confirmation is never byte-identical to the physicist's. `OPERATOR` is the sentinel every public entry point defaults to, so no existing call site changes. |
| **Command** (control contract) | `core/events.py`. A client's request for the engine to act: `name` (a `CommandName` — the enumeration of every public Orchestrator command, each value the name of the method implementing it), `actor`, JSON-safe `args`, `request_id`, `issued_at`. Distinct from `core/plan.py`'s **Command**, which is one method call a procedure hands the Orchestrator to dispatch on a VI. Conformance diffs `CommandName` against the Orchestrator's public methods in both directions; reads (answered from a client's `StatusSnapshot`) and `shutdown()` (process lifecycle, `main.py`'s) are exempt by name with a rationale each. |
| **Verdict** (control contract) | `core/events.py`. The engine's single answer to one `Command` — every refusal answers, since a broadcast signal is not something an agent can await: `request_id`, `command`, `code` (`OK`, `BLOCKED_STATE`, `BLOCKED_CLAIM`, `BLOCKED_FAULT`, `BLOCKED_LIMIT`, `BLOCKED_ENVELOPE`, `BLOCKED_ROLE`, `FAILED`), `actor`, human-readable `reason`, optional structured `detail`, optional `result`, `seq`, `ts`; `ok` is derived from `code`. A client decides from the code and the `detail` dict, NEVER by parsing `reason` — which is why the `@control` limit wrapper attaches `param`/`value`/`lo`/`hi`/`limit_name` to the `CryoSoftSafetyError` it raises while leaving the message text unchanged for the banner. Distinct from `core/conditions.py`'s **Verdict**, the enforcement decision `decide()` computes from a set of system conditions. |
| **Run queue** | The ordered list of runs waiting to start, held as immutable run *specs* — a procedure class, its validated parameter dict, and the **Actor** who queued it — rather than as live procedure objects, so nothing in the queue holds engine state or bus access (`session/run_queue.py`'s `RunQueue`, headless and Qt-free). Entries are validated when they are added, not when they start: `ExperimentManager.validate_run(procedure_cls, params)` builds the procedure without dispatching anything and returns its findings plus a duration estimate, so a parameter outside a **control-validation standard** limit or the **session envelope** is refused at the moment the operator queues it. The engine *pulls*: `Orchestrator.run_queue()` asks its injected `next_procedure()` callback, and the `RunQueueHost` behind it pops one spec and constructs the one live object that spec describes — so exactly one procedure instance exists, for the run that is about to start, and the engine still decides *when* it starts. That direction is the whole point — a client that watched `state_changed` for the IDLE state and started the next run itself would advance re-entrantly inside the engine's own emit and could not tell a clean finish from a **hold acknowledge**, so it would auto-start a procedure straight after an **emergency standby**. The engine therefore keeps sole authority over *when* a run starts, and every queue change is broadcast as the **control contract**'s `QueueChanged` event naming the actor who caused it. Distinct from `ExperimentRecord.queue`, the opaque GUI-authored JSON the session layer persists but never interprets (contract C11). |
| **Run spec** | `session/run_queue.py`'s `RunSpec` — one entry of the **Run queue**, as data: `kind` (`procedure`), the class `__name__` resolved against the injected *run catalog*, the validated `params`, `sample_info`, `data_directory` and `file_prefix` it was queued with, an optional `probe_spec` (the dict form of a **probe run**'s reduction — procedures only), the **Actor** who queued it, a `spec_id` (how remove/move address it) and `queued_at`. Frozen and JSON-safe end to end, so the same value serves the queue, the **control contract**'s `QueueChanged` event, and the persisted session state. It holds no procedure instance on purpose: a live run owns a data file and a claim on instruments, and neither belongs to something that is only waiting — `session/run_queue.py`'s `build_run()` constructs exactly one live object, for the spec the engine is about to start. |
| **Run validation** | `session/run_queue.py`'s `validate_run()` and its `RunValidation`/`RunFinding` result, reached through `ExperimentManager.validate_run()`. The free, no-hardware, no-consequence check a **Run spec** passes before it may enter the **Run queue**: the run is built headlessly (nothing dispatched, no data file opened) and three things are checked — every supplied value against its `ParamSpec` declaration, the build itself (a procedure legitimately refuses a run its station cannot honour), and every setpoint the built run declares in `planned_targets()` against the setup's `control_limits` bound and the **session envelope**. Findings are structured (`code`, `message`, `param`), so a client decides from the code and never by parsing prose; `duration_estimate_s` is declared but not yet estimated. |
| **Probe run** | A cheap, deliberately reduced execution of a run the operator (or an agent) is about to commit to: the same procedure class, the same instruments and the same code path, cut down so it costs minutes instead of hours and answers "would this actually work, and does the signal look sane?" before the real run starts. Requested as a `probe_spec` — on the `RUN_PROCEDURE`/`QUEUE_PROCEDURE` **Command**, on a **Run spec**, or as `run_builder.build_procedure(probe=...)` — and derived by `BaseProcedure.apply_probe()` from the built run, so a probe is only ever a reduction of a run the procedure already accepted. `core/plan.py`'s `ProbeSpec` docstring is the written standard; its four rules are: the sweep is subsampled to at most `n_points` points, evenly spaced and ALWAYS keeping the first and the last (that is where a limit or a quench shows up); every declared parameter whose `ParamSpec` unit is `"s"` is capped at `max_wait_s`; every declared repeat count is capped at `averaging`, identified by declaration (the parameter that shortens one of the measurement VI's `data_arrays()` lengths) rather than by name; and the reduced run declares `run_kind = "probe"` and records the spec as its `probe_spec` parameter. Nothing else changes — same targets, same claim, same setup limits and **session envelope**. The kind travels the whole way: the run manifest and `RunStarted` event carry `kind == "probe"`, the session layer's run record carries `kind`, and `DataManager` writes `/metadata.run_kind` so `data_reader.read_metadata()` tells an analyst a file is a probe. Probe data is never science data. |
| **Duration estimate** | How long a proposed run is expected to take, with the per-phase breakdown and the assumptions behind it: `core/plan.py`'s `DurationEstimate` (`total_s`, `phases` — `setup`/`ramp`/`settle`/`measure` — and `assumptions`), computed by `core/estimates.py`'s `estimate_duration(run, ramp_rates)` and returned by **Run validation**, so "may I run this?" and "how long will it take?" are one answer from one headless build. Assembled from exactly two contributions, each side owning what it knows: the RUN declares its per-point cost through the single hook `estimate_step_seconds() -> StepCost` (points, setup wait, per-point settle, measurement time — `SweepMeasureProcedure` derives it from the same `_initiate_wait_s()`/`_step_wait_s()`/`_loop_shape` hooks the tick loop uses, so a new axis procedure gets an estimate for free), and the SETUP declares its nominal ramp rates (`Station.nominal_ramp_rates()`, from each VI's `nominal_ramp_rate()`), which turn the run's `planned_targets()` into a time. Two modelling choices are stated as assumptions on every estimate: ramps on different instruments run concurrently (so the ramp time is the slowest instrument's, not the sum), and the approach from wherever the hardware stands now to the first setpoint is not counted (it cannot be known without reading hardware). **Assumptions are explicit, never silently zero** — a VI with no declared rate, a measurement whose duration nothing declares, or a run with no cost model is named in `assumptions` rather than counted as instant, because an estimate a reader cannot qualify reads as a promise. |
| **Verdict standard** | `core/orchestrator.py` (full text in the `Orchestrator` class docstring). Every command a client submits is answered exactly once. `submit(Command) -> request_id` returns immediately and the answer arrives on `verdict_emitted` as one **Verdict** carrying that id: `OK` when the command was accepted and carried out, else the code naming the rule that refused — `BLOCKED_STATE` (the state machine), `BLOCKED_CLAIM` (a run claims the instrument), `BLOCKED_FAULT` (the instrument is not controllable: a comm fault or an active **Safety hold**), `BLOCKED_LIMIT` (refused before any hardware call, with the `CryoSoftSafetyError`'s `param`/`value`/`lo`/`hi`/`limit_name` in `detail`), `BLOCKED_ENVELOPE` (the **Session envelope**), `BLOCKED_ROLE` (**Capability scope**, the **Kill switch** closed against a submitting agent, or — one layer up — the **Agent gateway**'s **Role** matrix) or `FAILED`. Two rules make it single and complete: every refusal goes through one of `_action_blocked()` / `_action_failed()` / `_action_succeeded()`, which emit the legacy `action_*` signal AND close the pending verdict; and a method that returns having emitted no refusal is an acceptance, so silence is `OK`. The code is produced next to the rule that decides it (`_manual_action_admission()` returns it beside its reason), so a client decides from the code and never from the prose. One asynchronous case: `submit_vi_action()` queues for the tick, the single hardware writer, so its verdict is emitted when the drain runs it and carries the call's return value in `Verdict.result`. Nothing raises at the caller — a malformed payload or arguments the method rejects are answered `FAILED`. |
| **Event stream** | `Orchestrator.event_emitted` — the ONE channel every consequence goes out on, carrying the **Control contract**'s `Event` union: `StateChange` (every transition, with a `cause` — the command name, or `tick`/`emergency`/`fault`/`error`/`procedure_finished`/`pause_boundary` — and the **Operator sentinel**'s actor), `StatusSnapshot` (once per tick and on every state change; one field per engine read, so a client answers every query from its own mirror instead of calling in), `StationInfo` (at construction and after every connect/disconnect, iff the Station declares `station_info()`), `Readings` (each monitored poll), `Datapoint` (each measured point) and `RunStarted`/`RunFinished`. One monotonic `seq` orders the stream together with the verdicts, so a client can put everything the engine said in order from two signals. Every emitted payload is a copy, and the existing per-purpose signals (`states_updated`, `state_changed`, `run_started`, …) keep emitting unchanged beside it, so no widget has to move to gain the stream. |
| **Status mirror** | A client's local copy of everything the engine last said about itself, and the reason no client ever reads the engine synchronously. `core/status_mirror.py`'s `StatusMirror` is fed the **Event stream**'s `StatusSnapshot`, `StateChange` and `StationInfo` (plus the **Operational-status record**, which travels on its own signal) and answers every read — `state`, `is_monitoring()`, `active_run_kind()`, `availabilities()`, `held_vi_names()`, `vi_faults()`, `active_ramps()`, `pause_pending()`, `station_info()`, `instrument_info()`, … — off the last one it saw, each named after the engine accessor it replaces and each returning a copy rather than a live container. Two consequences the design depends on: a read costs nothing and can never block on an engine that is forty seconds deep inside `measure()`, and every client-side guard clause becomes ADVISORY rather than authoritative — the client asks and the engine refuses, and a mirror one event-loop hop stale can never be the authority. The stream is a broadcast, so a mirror built after the engine missed the declaration emitted at construction: the **Instrument host** takes the three priming reads (`Orchestrator.station_info()`, `status_snapshot()`, `get_operational_status()`) on the engine's own thread and hands the client a mirror already primed. In `core/` rather than `gui/` because the GUI is not its only client — the **Orchestrator proxy** owns one, and the session layer holds a proxy (contract C11 forbids that layer from importing `cryosoft.gui`). `tests/test_conformance.py` enforces both halves: every read under `gui/` is a mirror read, and the priming reads are taken nowhere else. |
| **Orchestrator proxy** | `core/orchestrator_proxy.py`'s `OrchestratorProxy` — the **Control contract** rendered for a Python client, and what a Python client on the GUI thread holds instead of the engine: every widget and the `ExperimentManager` attach to a proxy. Three surfaces: one typed method per `CommandName`, each building a `Command` with the **Operator sentinel** and handing it to `Orchestrator.submit()`, returning the `request_id` its `Verdict` will carry; one Qt signal per event type (suffixed `_event`, so `run_started_event` carrying a `RunStarted` never collides with the engine's legacy `run_started(dict)`) plus the union `event` and `verdict`; and the engine's own per-purpose signals re-exposed 1:1 under their own names, which is what lets a widget be written against the engine's own vocabulary while holding a client adapter. Every read is answered from the **Status mirror** it owns, never by calling in. Two commands are the deliberate exception: `run_procedure` and `queue_procedure` carry a built run OBJECT, which `Command.args` cannot hold (it is JSON by contract), so those forward to the engine method with the same actor — the direct-handover path for a caller that already built a run, beside the **Run queue**'s ordinary path where the client adds a spec and the engine builds it. Across the **Instrument thread** every command is POSTED and returns the client-generated `request_id` at once — including `submit(Command)`, the engine's own port offered unchanged to a client that stamps its own actor, which is what makes the proxy satisfy the **Gateway**'s `EngineClient` and lets the **Gateway server** attach to it rather than to the engine. `tests/test_conformance.py` diffs `CommandName` against the proxy's methods and the engine's, and their parameter lists against each other; the agent gateway's tool list is the third leg of that check. |
| **Instrument host** | `core/instrument_host.py`'s `InstrumentHost` — the one place that decides which THREAD owns the instrument stack. It takes a station *factory* (not a built Station, because in threaded mode it must run inside the thread that will own every pyvisa `ResourceManager` and serial port), builds the Orchestrator beside it, builds each declared **station companion** on that same thread, captures `client_state()` — the **Status mirror**'s three priming values, taken on the engine's own thread — and hands the client an **Orchestrator proxy** through `build_proxy()`. Two modes: `inline` builds everything on the caller's thread, which is the single-threaded behaviour with the decision named; `threaded` builds it inside the **Instrument thread**. The two modes differ in where `start()` runs and in nothing a client can see — the same proxy, the same primed mirror, the same signals — which is why one GUI suite runs against both. `shutdown()` is the counterpart: it stops the tick timer on whichever thread owns it and, threaded, joins with a bound. |
| **Instrument thread** | The one thread that touches hardware, and the invariant behind it: in `InstrumentHost(mode="threaded")` exactly one thread ever touches a driver, a **Virtual instrument**, the `Station`, the `Orchestrator` or the `DataManager`. Enforced by construction rather than by a lock — the station factory and the Orchestrator constructor both run inside the `QThread`, so every VISA session is opened by the thread that will use it and the tick `QTimer` inherits that affinity — and crossed in exactly four ways. **Client to engine**: every command is *posted* through `ThreadBridge.post()`, queued and non-blocking, with the `request_id` generated on the caller's side by `Command`'s own constructor, so an **Orchestrator proxy** method returns at once even while the engine is forty seconds deep inside `measure()`; the answering **Verdict** arrives later on the **Event stream**, exactly as it does inline. **Engine to client**: every engine signal travels a Qt auto connection, which resolves to a queued delivery precisely because emitter and receiver live on different threads, so the payload lands on the client's event loop one hop later and never inside the engine's emit; the relays are ordinary slots, because a signal-to-signal connection cannot be delivered across a queued hop. **The signal payload rule**: what leaves the engine is a copy the engine never touches again (`states_updated` rebuilds the per-VI dicts it otherwise shares with `Station`'s stale-value cache; the **Operational-status record** is copied), so no client holds a container the engine still mutates. **The queue-crossing rule**: the **Run queue**'s two pull seams cross differently, wired by `OrchestratorProxy.install_run_queue()` — `queue_snapshot` is a snapshot PUSH (the client pushes immutable JSON entries on its own thread before each `QueueChanged` broadcast, and the engine reads a local cache with no crossing at all), while `next_procedure` is marshalled WITH A RESULT and split in two, popping the spec on the client's thread (it mutates the client's queue) and building the run on the engine's (it touches the `Station`). Reads need no crossing at all: they are answered from the **Status mirror**. Shutdown is bounded and never a hang: the stop and the `quit()` travel as one posted call so the timer is stopped by the thread that owns it, and the join gives up after `join_timeout_ms` with a `CRITICAL` record naming the read the `Station` was in the middle of (`Station.polling_vi()`), leaving the instrument exactly where a process kill would. A thread-level exception boundary restarts the event loop if it ever raises, because a dead loop is a `shutdown()` that can never be delivered. It is the DEFAULT and needs no config line: `monitor.yaml`'s `instrument_thread` (`config.read_instrument_thread()`) exists to REFUSE it — `false` selects the temporary **Inline mode** — and `CRYOSOFT_INSTRUMENT_THREAD=0` does the same for one launch, both resolved by `instrument_host.resolve_mode()`. One GUI suite runs against both modes (`tests/instrument_modes.py`, threaded by default, `make test-instrument-inline` for the other leg), which is the only way "nothing above the boundary can tell" stays true. |
| **Inline mode** | `InstrumentHost(mode="inline")`: the **Instrument thread**'s design with the engine on the caller's thread instead of its own — the same `OrchestratorProxy`, the same host-primed **Status mirror**, the same signals, the same tick and the same generator ramps, with every crossing collapsing to a direct call because there is nothing to cross. **Temporary.** It is the way back for a rack whose VISA layer misbehaves under a second thread (`instrument_thread: false` for one setup, `CRYOSOFT_INSTRUMENT_THREAD=0` for one launch) and is kept for ONE RELEASE after `threaded` became the default, removed at the end of it if no hardware regression has been filed against the default. Until then it is a tested mode, not a deprecated path: `make test-instrument-inline` is CI's second leg and `tests/test_orchestrator_proxy.py` is its suite. Do not write code that only holds inline — a GUI handler that assumes the mirror already reflects the command it just sent is a bug that inline hides. |
| **Station companion** | An object that holds the `Station` and runs on its own timer beside the Orchestrator rather than inside it — `core/trend_check_runner.py`'s `TrendCheckRunner`, scheduling the **Trend check** standard, is the only one today. Because it holds the `Station` it must live wherever the `Station` does, so it is declared to the **Instrument host** as a factory (`station_companions=`), built with the built Station on the engine's own thread, and — if it offers `stop()` — stopped there at shutdown, before the tick timer. Declaring one is how a new Station-holding scheduler gets the right thread affinity without the **Instrument thread**'s invariant growing an exception. |
| **Operator sentinel** | `events.OPERATOR` — the `Actor` every public Orchestrator command assumes is calling when nobody says otherwise (`kind="operator"`, `id="operator"`). It is what let accountability become a value without touching a single existing call site: the `command` decorator in `core/orchestrator.py` gives every method `CommandName` enumerates a keyword-only `actor=OPERATOR` and holds it, with the command's own name, for the call's duration, so `_change_state()` and every **Verdict** record who asked and what for. An actor left at the sentinel never displaces one already acting, so a command that internally calls another stays attributed to whoever started it. Its counterpart is `orchestrator.SYSTEM_ACTOR` (`kind="system"`), which every transition the engine makes on its own — a tick, a tripped flag, a run ending — is attributed to. Machine-checked: `test_conformance.py` asserts every `CommandName` method takes the keyword and defaults it to the sentinel. |

## Development harness

| Term | Definition |
|---|---|
| **Layer contracts (C1–C12)** | The machine-checked import rules in `pyproject.toml` `[tool.importlinter]`. Run with `make contracts`. A broken contract means the change crosses a layer boundary — route through the proper interface instead of editing the contract. C9/C10 isolate the troubleshoot toolbox in both directions; C11/C12 place the session layer (L6) between core and the GUI. |
| **Troubleshoot toolbox** | `cryosoft/troubleshoot/` — the diagnostic package (engine + CLI) for commissioning and debugging a setup. A leaf entry point beside the stack, like `main.py`: it may import drivers and the Station's config helpers; nothing in cryosoft imports it. Run while the main app is closed (serial ports are exclusive-open). CLI: `python -m cryosoft.troubleshoot scan/probe/check/methods/idn/read/write/query/send`, each one-shot with `--json` and exit code 0/1; `write`/`query`/`send` are the permission-gated verbs. Every invocation appends to the transcript `cryosoft/logs/troubleshoot.jsonl`. |
| **Fault taxonomy / FaultCode** | The stable machine-readable outcome codes every troubleshoot probe returns (`OK`, `CONFIG_INVALID`, `ADDRESS_NOT_ON_BUS`, `OPEN_FAILED`, `NO_RESPONSE`, `WRONG_IDN`, `GARBLED_RESPONSE`, `DRIVER_ERROR`). Codes are API for the triage skill: never renamed, only extended. |
| **Config preflight** | `check_config()` in the troubleshoot engine: for every `real_drivers` entry, verify bus presence, construct the driver, call `get_idn()`, and optionally match the config's `expect_idn` substring. The "is everything connected?" check run before a cooldown. |
| **Driver bench** | `DriverBench` in the troubleshoot engine: wraps one driver instance for method introspection, read/write-gated calls, and raw SCPI query/send. The primitive behind driver development and per-instrument debugging. |
| **`expect_idn`** | Optional key on a `real_drivers` entry in `devices.yaml`: a case-insensitive substring the instrument's `get_idn()` reply must contain. Lets the preflight detect swapped addresses/cables (`WRONG_IDN`). |
| **`get_idn()` (driver contract)** | Every driver — sim and real — exposes `get_idn()` taking no arguments, returning an identification string. Pre-SCPI Oxford instruments implement it with their native `V` command. Enforced by conformance. |
| **setup.md** | Per-config ground-truth document (`<config dir>/setup.md`): instrument purposes, wiring notes, dated known quirks, per-setup safe-testing limits. Written once during commissioning (human-confirmed), maintained by agents after every diagnosis. Template in `.claude/skills/setup-commission/references/`. |
| **Safe-testing ladder** | The excitation discipline for diagnostics (`.claude/skills/setup-supervisor/references/safe-testing.md`): L0 passive → L1 zero-excitation set/read-back → L2 minimal excitation (≤10 mA magnet lead current, ≤1 nA precision sources) → L3 operational values (human-confirmed state only). Instruments are not code: damage is irreversible. |
| **Incident report** | `cryosoft/logs/incidents/YYYY-MM-DD-<slug>.md` — the structured "cannot conclude" exit of the setup-supervisor skill (evidence table, layers ruled out, hypothesis with confidence, recommended next steps). A good report is a successful outcome; a guess is not. |
