# CryoSoft Glossary

Canonical definitions of project terms. When a human and an agent (or two
agents) talk about CryoSoft, these are the meanings in force. If a term is
used in code, docs, or conversation with a different meaning than defined
here, the glossary wins; if a new recurring term appears, add it here in the
same commit that introduces it.

## Architecture layers (bottom to top)

| Term | Definition |
|---|---|
| **Layer (L0–L6)** | The layered architecture: L0 Driver → L1 Virtual Instrument → L2 Station/Config → L3 Orchestrator → L4 Procedure → L5 Data Manager → L6 Session Manager, with the GUI on top. Lower layers never import higher ones; the machine-checked rules live in `pyproject.toml` under `[tool.importlinter]`. |
| **Driver (real driver)** | L0. A Python class that talks to one physical instrument over PyVISA (GPIB/serial). Constructor takes exactly one required argument: the VISA resource string. Lives in `cryosoft/drivers/`, imports nothing from CryoSoft except `core.exceptions`. |
| **Sim driver** | A drop-in simulated twin of a real driver (`sim_` filename prefix), used for all testing without hardware. Must expose exactly the same public API as its real twin — enforced by `tests/test_conformance.py`. |
| **Virtual Instrument (VI)** | L1. A device-role abstraction (magnet, temperature controller, level meter, measurement) built on one or more drivers. VIs never import drivers; the Station constructs driver objects and injects them into the VI constructor as a `drivers` dict (dependency injection). All VIs subclass `BaseVirtualInstrument` and use `__init__(self, drivers, **init_params)`. |
| **Measurement method** | L1. A self-describing measurement VI (subclass of `MeasurementInstrumentBase`) that declares its own GUI knobs and output shape and implements one uniform lifecycle, so a generic procedure can run any of them without knowing the instrument or protocol. Self-description: `measurement_parameters` (name→`ParamSpec`, the single owner of the knobs), `measurement_data_keys` (the raw-sample array names `take_reading()` returns, each ending `_array` — see **Measurement quantity**), and `measurement_scalar_columns` (the mean/error pair per quantity, plus optional extras like `n_valid`). Lifecycle: `data_arrays(params)` (declared array lengths for the same params `initiate_measurement` receives), `initiate_measurement(**params)` (arm the hardware; `@control(panel=False)` where GUI-exposed; deliberately not named `initiate` — the plain lifecycle `initiate()` on a measurement VI is a harmless connection check, so Initiate-All can never start a source current), the argument-less `take_reading()` (one datapoint: for every quantity, the raw-sample array padded to the declared length plus its mean and standard error, always exactly the declared keys — a VI that can return fewer points pads with `float("nan")` and reports the true count in a scalar column), `standby()` (safe-off), and the optional **`reading_setters`** declaration (default `{}`; see **Reading loop**). `DCMeasurementBase` fixes the DC-resistance shape (`readings_per_point` samples of `voltage_V`/`current_A`); the full written standard lives in `MeasurementInstrumentBase`'s docstring and is machine-enforced by `test_conformance.py` (declaration validity, lifecycle presence, sim round-trip, the mean/error/array convention). |
| **Measurement quantity** | L1. The mean/error/array naming convention every measurement VI follows for each quantity it reports (e.g. `"voltage_V"`), derived mechanically by `MeasurementInstrumentBase.quantity_columns()`: the raw samples under `"{quantity}_array"` (in `measurement_data_keys`), the mean under the bare `"{quantity}"` — what the GUI plots — and the standard error of the mean under `"{quantity}_error"` (both in `measurement_scalar_columns`, dtype `"float"`). The VI computes the mean/SEM itself, over the valid (non-NaN) samples, via the shared `MeasurementInstrumentBase.mean_and_sem()` helper (`n=1` → SEM `0.0`; `n=0` → both NaN) — never the GUI, which only plots the scalar it's handed. `test_conformance.py` enforces the triple for every `_array` key on every measurement VI, and rejects a base quantity name that already ends `_array`/`_error`. |
| **Raw diagnostic block** | L1. A second, orthogonal self-description on `MeasurementInstrumentBase` for an instrument that returns far more raw data per reading than any single physical quantity, where the **measurement quantity** mean/error/array convention does not apply (no single mean makes sense across many mixed-unit channels). A VI declares `measurement_raw_blocks: ClassVar[dict[str, list[str]]]` (block name → ordered channel-label list, fixing the channel axis) and overrides `raw_block_row_counts(params) -> dict[str, int]` (row count per block, mirroring `data_arrays()`'s params-dependent role); `take_reading()` returns the block as a nested `rows x channels` list, NaN-padded on the row axis only when the instrument under-delivers (the channel axis never pads). The block's own `rows x channels` matrix is deliberately excluded from `measurement_data_keys`/`measurement_scalar_columns` so it never itself appears in a GUI plot-axis dropdown — a diagnostic/provenance record, not a plotted quantity. Its declared CHANNELS are, however, independently plottable: `SweepMeasureProcedure` derives one scalar column per channel (row axis reduced by a NaN-safe mean — the same "N readings at one measurement point" treatment `mean_and_sem` gives a quantity's own array column), added automatically to `live_plot_measurement_keys()` and `DataSchema.measurement_scalars`, with zero VI-side code — see `SweepMeasureProcedure._raw_block_channel_columns`/`measure()`. The one exception to the **loop axis** convention: `DataSchema.measurement_blocks` carries the `(n_loop1, n_loop2)` axis only when a reading loop is actually configured (`loop_shape != (1, 1)`) — with no reading loop, HDF5 storage is bare `(rows, cols)`, not `(1, 1, rows, cols)`; `SweepMeasureProcedure.measure()` squeezes the trivial axis away before saving, while a VI's own `take_reading()` always returns the block as a flat `rows x channels` list regardless. First adopted by `TensormeterRTM2MeasurementVI`'s `raw_channels_block` (all 44 raw driver columns, alongside the operator-selected `res_a_ohm`/`res_b_ohm` pair). Self-description travels all the way to disk: `DataManager` writes the declared label list as the block dataset's own `channel_names` HDF5 attribute (column index → channel name) plus an `axes` attribute naming every dimension in order (e.g. `"sweep_point, row, channel"`, or `"sweep_point, loop1, loop2, row, channel"` when a reading loop is active) — a reader never needs to parse the `metadata` group's JSON `data_config` to know what a column means. Full text: `MeasurementInstrumentBase`'s docstring, "Raw diagnostic blocks", and `virtual_instruments/measurement/README.md`. |
| **Externally configured** | L1. A `configured_externally: bool` init param (default `False`) on `MeasurementInstrumentBase` (`devices.yaml`'s `init_params`, no per-subclass boilerplate) that splits ownership of an instrument's configuration between the vendor's own tool and CryoSoft: the external tool owns excitation, analysis, and routing parameters — `initiate_measurement()` MUST NOT write any of them, only accept the now-inert `measurement_parameters` (logged, never rejected) — while CryoSoft still owns the data path, triggering, reading, and saving (verifying connectivity with a true round trip, arming buffers/channel selection, reading back any value its own timing/decoding depends on). `standby()` MUST NOT overwrite the externally-owned source state; it only resets CryoSoft's internal arming state. Pairs with the declared `detach_when_idle` standard on `BaseVirtualInstrument` (`detach_when_idle` property, `is_attached()`, `_attach()`/`_detach()` — see **Availability**): an externally configured VI narrows `detach_when_idle` to `return self._configured_externally`, one line, and the base does the rest — born detached at the end of `__init__` (`self._detach()`), `ping()` (and so the inherited `initiate()`) verify-and-release automatically (reattach → true round trip → release), `initiate_measurement()` reacquires the session for the measurement window, and `standby()`'s `__init_subclass__`-wrapped release hands the session back the instant the VI's own safe-off commands return — so the operator can attach the vendor tool at any time between runs, with no VI-specific lifecycle code beyond the one-line declaration. Motivated by single-client instrument firmware (vendor tool and CryoSoft are mutually exclusive at the instrument); the full normative text lives in `BaseVirtualInstrument`'s docstring ("Detach-when-idle declaration"), `MeasurementInstrumentBase`'s docstring, and `virtual_instruments/measurement/README.md`. A supporting VI declares `externally_owned_parameters: ClassVar[frozenset[str]]` naming exactly the `measurement_parameters` the external tool owns; the `active_measurement_parameters` property (what the procedure form renders) and `reading_parameters` (what the reading-loop registry offers) both subtract it automatically whenever `configured_externally` is true, so a form never shows — and a reading loop can never write to — an inert excitation/analysis/routing knob, with zero per-VI GUI code. |
| **Rotator VI** | L1. A VI over a motorized sample-rotation stage (class `vi_type = "rotator"`, registry `vi_type: system`), used with a uniaxial or 2D magnet to set the sample's orientation relative to the field. `RotatorVI` exposes exactly two controls/properties — `set_sample_angle(target_deg)` / `get_sample_angle()` and `set_rate_sample_angle(rate_deg_per_min)` / `get_rate_sample_angle()` — both bounded by the **control-validation standard** (`min_angle_deg`/`max_angle_deg`/`max_rate_deg_per_min` in config). Implements `RampableVI` with a status-driven ramp identical in shape to `SuperconductingMagnetVI`'s (waits for the driver to report `HOLD` before sending the next setpoint), so a rotator is a valid **system target** like a magnet or temperature controller. |
| **Switch VI** | L1. A VI over a matrix-switch / scanner driver (e.g. the Keithley 705) that multiplexes measurement channels by **route**. `SwitchMatrixVI` (class `vi_type = "switch"`, registry `vi_type: switch`) implements the **exclusive-mux policy**: at most one route is connected at a time, so `select_route(route)` always calls the driver's `open_all()` first and then closes the route's channels. `routes()` lists route names in config order; `@control select_route` / `@control open_all`; `get_state()` reports `active_route` (str, `""` when none) and `active_route_index` (int, `-1` when none). Route table and `settle_time_s` are validated at construction (`CryoSoftConfigError` naming the offender). A future true-matrix policy (multiple routes closed at once) would be a config flag, not a code fork. Participates in the **reading loop** via `reading_setters = {"route": "select_route"}` and `reading_safe_off = "open_all"`. |
| **Route** | A named connection on a **Switch VI**, its name taken verbatim from config, mapping to a list of instrument-format channel specs (e.g. `Mux-Ch1 -> ["1!1"]`). Route names must be non-empty, unique, and contain neither `__` (the column-label separator) nor `/` (illegal in an HDF5 dataset name). The route is the switch VI's loopable parameter (`reading_setters = {"route": "select_route"}`): put it in a **Reading loop** slot and tick the per-route pick checkboxes to measure several channels per sweep point, exactly like looping any other parameter. |
| **Reading loop** | The per-datapoint iteration a **generic sweep procedure** runs inside `measure()`: up to TWO generic **slots**, each a loopable parameter (see **`reading_setters`** — the switch VI's `route` and a measurement VI's `current_A` are the same concept) plus an ordered value list. Slot 1 (loop1) is axis 0 (outer), slot 2 (loop2) axis 1 (inner) of every measurement column's real **loop axis**. The auto-rendered "Reading loop" form group (shown above the measurement VI's parameter group whenever the station's reading path offers anything loopable) carries one structural `{slot}_parameter` drop-down per slot plus that parameter's values input — per-choice `{slot}_pick_{value}` checkboxes when the spec is enumerated (routes), a `{slot}_values` comma-separated text field otherwise (currents). A slot with ONE value is a static setting (dispatched once at `initiate()`, trivial length-1 axis); with two or more it loops: the setter is dispatched as a `Command` through the Station before every reading at that axis index. Axis index → physical value is recorded in the run's HDF5 metadata as `procedure_params["loop1_values"]` / `["loop2_values"]`. Non-measurement VIs that took part get their `reading_safe_off` (e.g. the switch's `open_all`) at standby/abort. A setup with no switch and no setters simply has no loopable parameters — no group, no special case. |
| **`reading_setters`** | The VI-level declaration behind the **reading loop**: a `BaseVirtualInstrument` class attribute mapping a parameter name to the cheap setter method that reprograms just that quantity between readings (e.g. the DC VI's `{"current_A": "set_source_current"}`, the switch VI's `{"route": "select_route"}`), paired with `reading_parameters` (the ParamSpec per loopable parameter — enumerated specs render as pick checkboxes, free specs as a value-list text field; a measurement VI inherits an implementation reading its `measurement_parameters`) and optional `reading_safe_off` (a method dispatched at standby/abort when a non-measurement VI took part, e.g. `open_all`). Declaring an entry is ALL a VI does — the "Reading loop" form group, the per-reading setter dispatch, the loop axis, and the metadata all follow automatically. Contract (machine-enforced by `test_conformance.py`): setters are real methods accepting the parameter under its own name and never change the reading's shape; measurement-VI keys are existing non-bool measurement parameters. |
| **Loop axis** | The real `(n_loop1, n_loop2)` array axis every **DataSchema** measurement scalar/array column carries in HDF5 when a **reading loop** slot is configured — `n_loop1`/`n_loop2` each `>= 1` (`1` = that slot is off/static). A measurement scalar (e.g. a quantity's mean) is stored `(n_sweep_points, n_loop1, n_loop2)`; a measurement array (raw samples) `(n_sweep_points, n_loop1, n_loop2, length)`. Column names are never suffixed — replaces the earlier "multiplexed columns" suffix scheme (`{name}__A{i}__B{j}`). Axis index → physical value lives in the HDF5 metadata as `procedure_params["loop1_values"]` / `["loop2_values"]`; `SweepMeasureProcedure._loop_shape` derives the axis lengths, `measure()` builds the per-datapoint grid, `DataManager` allocates/writes it. A **Raw diagnostic block** is the one exception: it carries this axis only when a reading loop is actually configured (`loop_shape != (1, 1)`), staying bare `(rows, cols)` otherwise. |
| **Station** | L2. The runtime registry of all VIs, built from a config directory by `build_station()`. The only layer that touches both VIs and (via config) driver classes. Dispatches system targets, measurement commands, and safety checks. |
| **Config** | A directory under `cryosoft/configs/<name>/` holding `devices.yaml` (drivers, VIs, wiring, safety limits) and `monitor.yaml` (tick interval, error threshold). Configs are the single source of truth for addresses, limits, and mappings — never hardcode these. |
| **Shipped vs user config** | *Shipped* configs are the git-tracked, read-only baselines under `cryosoft/configs/`; the GUI never edits them (a safe fallback that cannot be corrupted). *User* configs are editable copies under `%APPDATA%/CryoSoft/configs/`, created by copy-on-edit (`ConfigCatalog.fork_shipped`). |
| **Config catalog** | `core.config_catalog.ConfigCatalog` — discovers shipped + user configs, forks shipped→user, and keeps a named **config version** history per user config (save/list/restore). |
| **Config version** | A saved snapshot of a user config under `.versions/<id>/` with a `meta.json` (label + timestamp). Every editor save creates one; restoring copies it back over the active files. |
| **Active config** | The config the app loads on launch, stored in `QSettings` as an identity (`ActiveConfig/name` + `ActiveConfig/source`), re-resolved to a directory at startup so a stale absolute path (e.g. from a deleted git worktree) can't point nowhere. Switching it warns, saves the session, and restarts. |
| **Startup fallback chain** | `build_station_with_fallback()` tries the active config, then its shipped baseline, then the always-loadable `sim_cryostat`, so a corrupted config surfaces a warning instead of crashing startup. Each candidate is checked by `validate_config_dir()` (a dry-run that imports classes and resolves driver refs without instantiating hardware). |
| **Orchestrator** | L3. The state machine that executes a procedure: it ticks, ramps system VIs toward targets, waits, triggers measurements, and enforces safety. Talks only to the Station. Monitoring runs in its tick loop, gated by `start_monitoring()`/`stop_monitoring()` — see **Monitoring (Orchestrator)**. |
| **Procedure** | L4. A declarative measurement sequence (e.g. field sweep, temperature sweep) subclassing `BaseProcedure`. Declares *what* to do via the four-method interface; the Orchestrator decides *how*. Procedures never import drivers or VIs. Most measurement procedures are **generic sweep procedures** (see below), so adding a measurement usually means adding a measurement VI, not a procedure. |
| **Operation** | A multi-step cryostat-servicing action (subclass of `OperationBase`, L4): helium fill, sample change. Declarative like a procedure (returns plans, never touches VIs directly), but with operation-scope command access, tolerated safety flags, verified postconditions, an optional (not required) data file, and higher submission priority. Not listed among measurement procedures. |
| **Claim** | The set of VI names a running procedure/operation exclusively owns, declared via `claimed_vi_names() -> set[str] \| None` (`BaseProcedure`/`OperationBase`, docs/plans/archive/operation-concurrency-and-error-scoping.md §1). The Orchestrator captures it once at run start into `_active_claims` and consults it, through the shared `_manual_action_admissible()` predicate, to decide whether a manual front-panel action submitted while the run is active may be admitted: a VI in the claim set is refused (naming the owning run), every other VI stays under manual control exactly as in IDLE. Default `None` means "claim everything" — the safe default every procedure keeps (procedures stay exclusive in this iteration); narrowing is an explicit per-class opt-in, e.g. `HeliumFillOperation` claims only its level meter, and `TimeSeries` claims only its reading path (measurement VI + loop-slot VIs) so the operator can drive temperature/field by hand for the whole run. `_manual_action_admissible()` checks an **Instrument fault** FIRST, ahead of the claim rules — a faulted VI is refused even in IDLE, regardless of any claim. A second consumer reads the same declaration for a second purpose: `BaseProcedure._claim_initiate_commands()` builds one `initiate()` `Command` per claimed VI (every station VI when `claimed_vi_names()` is `None`), returned in `PhasePlan.claim_commands` and dispatched by `Orchestrator._start_run` before that plan's own `targets`/`commands` — so a claimed VI is always back in its standard operating state (e.g. a temperature controller's heater in closed-loop AUTO) before anything else in the run touches it, exactly as if the operator had pressed Initiate on it first. |
| **Hard status separation** | docs/plans/archive/operation-concurrency-and-error-scoping.md §2: the Procedure window must never react to an operation's run-scoped chatter, and vice versa. The Orchestrator routes by the active run's kind — `status_message`/`procedure_progress`/`procedure_finished`/`measurement_ready` fire ONLY for a procedure run; `operation_status`/`operation_progress` fire instead for an operation run, consumed by the Operations panel's `OperationCard`, never the Procedure window. `Orchestrator.active_run_kind() -> "operation" \| "procedure" \| None` is the public, duck-type-free accessor GUI code uses to gate its own run-dependent widgets (e.g. the Procedure window's Abort button must not act on a running operation). Signals not tied to one run (`state_changed`, `error_occurred`, `operational_status`) are unaffected. |
| **Generic sweep procedure** | L4. `core.procedure.SweepMeasureProcedure` — the "sweep one axis, run any measurement method" base, and the two axis procedures on it: `FieldSweep` ("Field Sweep") and `TemperatureSweep` ("Temperature Sweep"). ONE procedure per sweep axis runs ANY station **measurement method**, chosen in the GUI via a **structural** `measurement_vi` parameter whose `choices` come from `Station.measurement_vi_names()`. The base owns measurement-VI selection, station-driven measurement-parameter merging, `DataSchema` assembly, per-datapoint validation, and the four-method loop; a concrete axis procedure supplies only the ramp targets, the axis read-back, and the settle times (its `_initial_system_targets` / `_step_targets` / `_standby_targets` / `_axis_readback` / `_initiate_wait_s` / `_step_wait_s` hooks). Replaces the former one-procedure-per-measurement classes (`FieldSweepDC`, `FieldSweepIV`, `TemperatureSweepDC`). |
| **Data Manager** | L5. Writes measurement data to HDF5 files. Standalone: knows nothing about instruments. Created by procedures in `initiate()`. |
| **Data reader** | L5. `core/data_reader.py` — the read-only analysis side of the file the **Data Manager** writes, and a standalone sibling of it, never a method on it (import-linter contract C16: nothing from the package but `core.events` and `core.exceptions`, so an analysis process imports it alone). `open_run(path)` returns a `RunHandle` context manager answering the **Run source** vocabulary over one run's HDF5 file. Reads stop at the *written prefix* — the writer pre-allocates every dataset to the full sweep length filled with NaN and trims only on a clean close, so the number of non-empty `timestamp` entries (the column the writer stamps last for each point) is the count of points actually measured. Every `ColumnInfo` carries a role from `COLUMN_ROLES`: `sweep_axis`, `measurement`, `raw_block` (see **Raw diagnostic block**), and `loop_axis` — the **reading loop**'s axes, which live in `procedure_params["loop1_values"]`/`["loop2_values"]` rather than in a dataset and are surfaced as the columns `loop1`/`loop2`. |
| **Run source** | The one read vocabulary for a run, wherever the run lives: `core/data_reader.py`'s `RunSource` `Protocol` — `n_points`, `list_columns()` (a frozen `ColumnInfo` per column: name, unit, dtype, role, stored shape, written length, path), `read_slice(column, start, stop, step)` (the leading sweep-point axis only; inner loop/sample/block axes come back whole), `summary_stats(column)` (a frozen NaN-aware `Stats`: count, min, max, mean, population std, first, last) and `read_metadata()` (exactly `RUN_METADATA_KEYS`, empty values rather than missing keys). `ColumnInfo` and `Stats` are JSON-safe both ways (`to_json()`/`from_json()`, a NaN rendering as `null`), so a result travels as a `Verdict.result` payload unchanged. `RunHandle` implements it over a run on disk; a consumer depends on the protocol, never on which source it holds. |
| **Session Manager (L6)** | `cryosoft/session/` — the experiment-management layer between core and the GUI. `ExperimentManager` (the façade, `session/manager.py`) owns the **experiment** lifecycle, records every **run** automatically from the Orchestrator's **run manifests**, installs the experiment's **session envelope** on the Orchestrator, and supplies `experiment_context()` — a two-tier `{"setup": {...}, "experiment": {...}}` dict, see **Setup tier** — for stamping HDF5 files. Single writer of experiment state, exactly as the Orchestrator is the single writer to hardware. Imported by gui/main only; imports core downward (contracts C11/C12). |
| **GUI** | PyQt6 windows (monitor, procedure, instrument panels). Talks to the system only through the Orchestrator and Station APIs; never imports drivers or concrete VIs. |

## Runtime concepts

| Term | Definition |
|---|---|
| **Tick / tick loop** | The Orchestrator's periodic heartbeat (`tick_interval_ms` in `monitor.yaml`). Each tick processes queued GUI actions and advances the state machine/ramps; while **Monitoring (Orchestrator)** is active it also polls VI state and checks safety. |
| **Monitoring (Orchestrator)** | The hardware-touching part of the tick: polling every VI into `states_updated`, stall detection, and stale detection. The **Operational-status record** is NOT part of it — that is written on every tick, monitoring or not. OFF at construction so a fresh launch polls nothing until the instruments are initiated; started/stopped via `Orchestrator.start_monitoring()`/`stop_monitoring()` (the Monitor window's header toggle). `run_procedure()` auto-starts it; stopping is refused outside IDLE/ERROR. `shutdown()` stops the tick timer entirely (app exit / test teardown). |
| **Operational-status record** | The per-tick runtime troubleshooting signal: one JSON object emitted on `Orchestrator.operational_status` and appended as one line to `status.jsonl`, carrying the state and how long it has been held, the active run and setup identity, per-system-VI gap/rate/ETA, the active `Condition`s, and a worst-of `RunFaultCode` verdict. Its **standard** — the field list, the types, the schema version, the rule that an unknown value is `null` and that a field is only ever added — is the module docstring of `core/operational_status.py`; the log is the contract for its readers (`troubleshoot/status_reader.py`, `gui/diagnostics_window.py`). Written on EVERY tick, so a gap in `status.jsonl` means the process stopped ticking and nothing else — the property `troubleshoot status --max-age` gates on. Distinct from **Trend history**, which is a time series of readings rather than a diagnostic verdict. |
| **Trend history** | The tiered, disk-backed store of per-tick station readings, written every tick by `core.tiered_trend_logger.TieredTrendLogger` (called from the Orchestrator's monitoring tick) and queried through `core.trend_history` (`read_window`, `summarize`, `find_crossings`). Distinct from `status.jsonl` (the operational-status record — a diagnostic "why is this stuck" signal, not a time series) and from **MonitorHistory** (the in-RAM ring buffer feeding live plots, bounded to its own retention window, rehydrated from the raw trend tier at GUI startup). Measurement VIs are never persisted to any tier: `Station.last_state_flat()` — the flattener both the tiered writer and `MonitorHistory.record_flat()` consume — excludes them by design, so a trend panel on a measurement-VI key works live but is empty on any disk-backed window (see **MonitorHistory**'s docstring for this and the opposite-running boolean-field asymmetry). |
| **Trend tier** | One fixed-resolution level of the **Trend history** store: `raw` (per tick, ~3 days retention), `3min` (~9 days), `hourly` (~1 year). Downsampling from raw into the two aggregate tiers is live and incremental — `TieredTrendLogger` folds every sample into a pending bucket per tier and flushes it (min/max/mean/std/count) the instant a sample lands in the next bucket, not on a wall-clock timer. Which tier serves a requested time window is decided once, in `trend_history.pick_tier()`, and every caller (GUI trend panel, CLI, future agent tooling) inherits that choice rather than picking its own. |
| **Trend check** | A named temporal judgement over the **Trend history** store (`core/trend_checks.py`): a `TrendCheck` declaration (`name`, `keys`, `window_s`, `severity`, a pure `predicate` function) evaluated by `run_checks()` against `trend_history.summarize()` — never re-deriving mean/std or re-picking a tier, both of which stay `trend_history`'s job. A predicate returns a `CheckOutcome` whose `passed` is `True`/`False`/`None`, where `None` means "cannot tell" (an empty or never-persisted window — see `no_data_outcome()`), distinct from a definite pass or fail. Only a definite failure becomes a `Condition` (`to_condition()`/`conditions_for()`), published under the fourth **System condition** origin, `"trend"` — every check declared so far is `"advisory"` severity, so a trend check can report but never enforce: no VI is stood by, no run fails, and it cannot reach the Monitor banner (`monitor_window.py` filters `severity == "hold"`). It IS visible in two places: `status.jsonl` (every condition of any severity is serialized there, `operational_status.py`) and `DiagnosticsWindow`'s alerts panel — the latter via `build_operational_status()` turning every advisory condition into one `alerts` line generically, not via any trend-specific hook. `declared_checks()` is the standard's single registration point: adding a check means adding a `TrendCheck` literal there, reading its threshold(s) out of `Station.read_trends_config()`'s `trends:` config block — no other module changes. Scheduling is deliberately NOT the Orchestrator's job: `cryosoft.core.trend_check_runner.TrendCheckRunner` is a small, independent `QObject` holding only a `Station`, running `declared_checks()` on its own slow timer (default 60 s, `trends.refresh_interval_s`) and publishing through `Station.publish_conditions("trend", ...)` — the Orchestrator learns of the result only by already reading `Station.conditions()` into its per-tick record, exactly as it does for every other origin. `declared_checks()` ships `sample_temperature_stable` (std/range over the sample-temperature key) and `helium_consumption_normal` (implied boil-off rate, percent-per-hour, from the helium-level key's windowed endpoints). A `predicate` receives both the window's `{key: KeySummary}` aggregates and its `{key: [(t, value), ...]}` series (`WindowedSeries`) — the second argument exists so a rate-of-change check can read `series[0]`/`series[-1]` without a new `KeySummary` field, which would leak a rate-specific need into an aggregate-statistics type. `trend_store_live` — is the store still receiving records at all, checked by reading the live trend-history file's mtime plus its newest record — is declared nowhere in `declared_checks()`: it exists to catch a wedged or crashed application, and a check scheduled on that same process's own timer cannot fire once the process is the thing that is hung, so it is evaluated only from `python -m cryosoft.troubleshoot trends`, a separate process, via `cryosoft.troubleshoot.engine.check_trend_store_live()`. |

| **Capability scope** | The tier a VI `@control` method belongs to: `"measurement"` (may appear in any plan) or `"operation"` (may appear only in operation plans; still a GUI control as before). Declared on the decorator, enforced at dispatch, conformance-checked. |
| **Declaration standard** | The rule that a VI describes its whole capability surface on its own decorators, because one declaration feeds the GUI widget, the tooltip, and the capability manifest an agent reads. Every `@monitored` method declares a `unit=` (SI unit label; `""` only for a genuinely dimensionless, boolean or string reading — never omitted, `None` means undeclared) and a one-sentence `description=`; every `@control` method that takes parameters declares a `ParamSpec` per parameter in `params=`. | **Shared-instrument mode discipline** | The standard (full text in `virtual_instruments/measurement/README.md`) for a driver whose public API spans more than one mutually exclusive operating mode (e.g. the Keithley 6221's plain DC output vs. its bipolar delta engine), when more than one measurement VI can be wired to the same physical driver instance in `devices.yaml`. The mode-establishing method MUST be idempotent and self-recovering — it unconditionally reasserts its own required mode (`Keithley6221.set_current()`'s `:SOUR:CURR:MODE FIX`) rather than assuming the instrument is already compatible, so a VI's `initiate()` never depends on a previous VI's `standby()` having run correctly. A sim driver modeling more than one such mode tracks it (e.g. `SimKeithley6221._mode`) so skipping the defensive reassertion fails in tests instead of on hardware. |
| **Control-validation standard** | The binding contract (full text in `BaseVirtualInstrument`'s docstring) that every user-facing `@control` action is validated before hardware is touched and always yields an explicit verdict. (1) Numeric bounds: the VI declares `control_limits = {method: {param: limit_name}}` and its `__init__` populates `self._limits[limit_name] = (lo, hi)` from the config's `init_params` — limits are setup properties (e.g. `max_temperature_K`, `max_ramp_rate_K_per_min`, `max_current`), so a new cryostat changes YAML, not code. Enforcement is inherited: `__init_subclass__` wraps every `@control` method; an out-of-range call raises `CryoSoftSafetyError` with the reason. Subclasses adding limits must merge (`{**Parent.control_limits, ...}`). (2) Semantic rules that aren't ranges (e.g. never energise the switch heater across a PSU/coil current mismatch) are explicit checks at the top of the method, raising `CryoSoftSafetyError`. (3) Verdict: the Orchestrator emits `action_succeeded(vi, method)` or `action_failed(vi, method, reason)` for every submitted action; `MonitorWindow` shows failures in the notification banner and successes as a transient status-bar message. Machine-enforced by the `test_conformance.py` control-validation tests: declared limits must name real `@control` methods/params, must be populated by every sim-buildable config, and must actually reject an out-of-range call. Coverage is enforced too, which is what makes the standard binding rather than opt-in: every numeric `@control` parameter on every discovered VI must appear in `control_limits` or in `CONTROL_LIMIT_EXEMPTIONS` with a one-line physical rationale (`test_every_numeric_control_param_is_bounded_or_exempt`), and an exemption that no longer names an unbounded parameter fails as stale. |
| **Direct action path** | `Orchestrator.submit_vi_action()` → the per-tick queue drain → `Station.execute_vi_action()`: the route a MANUAL action (a GUI click on an instrument panel, an agent call) takes to one VI, as opposed to a procedure's `Target`s and `Command`s, which go through `Station.process_system_targets()`/`send_measurement_commands()`. Five independent checks refuse a call before any hardware command is sent, each with its own reason: a private (underscore-prefixed) name and a method that is neither `@control` nor a lifecycle action (`initiate`/`standby`) are refused by the Station as `CryoSoftPrivateActionError`/`CryoSoftUndeclaredActionError`; a capability whose **Capability scope** exceeds the caller's `allowed_scope` (default `"measurement"`; the Orchestrator's manual path opts into `"operation"` via `MANUAL_ACTION_SCOPE`) as `CryoSoftActionScopeError`; an out-of-range value by the **Control-validation standard**'s limit wrapper; and a setpoint outside the active **Session envelope** by the Orchestrator, at submission and again at drain. Every refusal is a `CryoSoftSafetyError` — nothing reached the instrument — and surfaces as `action_blocked(reason)` or `action_failed(vi, method, reason)`. |
| **Setpoint-parameter convention** | `core/plan.py`'s `SETPOINT_PARAM_PREFIX` (`"target_"`): a `@control` parameter whose name starts with it carries its VI's enveloped quantity — the same quantity `RampableVI.start_ramp(target)` takes and a `Target` commands (`set_field(target_T)`, `set_temperature(target_K)`, `set_sample_angle(target_deg)`). It is what lets the **Session envelope** bind a manual action on the **Direct action path** with no per-VI table in the Orchestrator: `Station.setpoint_parameters(vi, method)` names the keyword argument to check. A rampable VI declares exactly one, on one capability, and that parameter must itself be bounded by `control_limits` (an envelope narrows a setup limit, so a limit must exist to narrow) — machine-checked by `test_conformance.py`. `Station.envelope_variables()` is the read side: per VI, the setpoint capability plus the setup's own bounds, which the Start Experiment dialog's envelope editor pre-fills from. |
| **Emergency standby** | `Orchestrator.emergency_standby(reason)`: the unconditional safe-off route, permitted in EVERY state — including EMERGENCY and ERROR, where every other manual route is refused and where making the machine safe matters most. Deliberately outside the manual-action admission predicate (an admission gate on the stop button is a gate on the wrong thing), it routes into the same emergency flow a **Critical safety flag** takes (abort the run, `run_finished`, EMERGENCY, `standby_all()`), logs the reason at CRITICAL, and runs on the caller's stack like `stop_ramp()`. Accepted latency: single-threaded cooperative scheduling means a call arriving mid-tick lands after the current `measure()` returns. |
| **vi_type (class)** | Class attribute of a VI describing its device role: `magnet`, `temperature`, `measurement`, `level`, `rotator`. Set by the typed base classes. |
| **vi_type (config/registry)** | The *registry* role a VI plays in a Station, set in `devices.yaml`: `system` (rampable, receives system targets), `measurement` (receives measurement commands), `level` (safety monitoring), or `switch` (a **Switch VI** that multiplexes measurement channels by route). Distinct from the class `vi_type`. |
| **Hot switching / cold switching** | The order `SwitchMatrixVI._connect_exclusive()` uses when an exclusive connect (`select_route`/`close_channel`) changes which channel(s) are closed, controlled by the runtime-toggleable `hot_switching` setting (default on). **Hot**: close the new channel(s) first, then open the stale ones (make-before-break) — there is never a moment with nothing closed, so a live current source can't see an open load and trip compliance; trade-off is a brief instant with both old and new channels connected. **Cold**: open first, then close (break-before-make) — classic exclusive-mux, never two channels connected at once, at the cost of a brief open circuit on every change. `open_channel()` (opening one channel, nothing new made active) has no ordering concern either way. |
| **`scanner_enabled`** | A `Station`-owned availability bit (`Station.set_scanner_enabled()`/`scanner_enabled()`) controlling whether the switch VI's loopable parameters are offered to the **reading loop**. Off by default. `Orchestrator.set_scanner_enabled()`/`scanner_enabled()` is the public toggle surface (a no-op, logged, when the station has no switch VI) — the bit lives on the Station because `SweepMeasureProcedure` only ever holds a `Station` reference, never an `Orchestrator` one. With the scanner disabled, a switch-VI-equipped station behaves to procedures exactly as if it had none: the route never appears in the loop-slot drop-downs. |
| **Connection lifecycle** | The standard separating who *owns* an instrument from what the instrument is *doing*, binding on every driver and VI (full text in `BaseVirtualInstrument`'s docstring). Two axes: `connect`/`disconnect` own the bus session, `initiate()`/`standby()` own instrument state. Three rules: (1) **construction is silent** — a driver's or VI's `__init__` sends no command that changes what the instrument is doing, so the only command `build_station()` issues per instrument is an identity query (`BaseVirtualInstrument.ping()`, via `_identity_check()`); a setup command belongs in `initiate()`. (2) **disconnecting is not standing down** — `Station.disconnect_instrument()` releases the session and leaves a magnet at field, a heater on its setpoint; pressing Standby first is the operator's choice. (3) a disconnected instrument **degrades exactly like an Offline instrument**, into the same registry, tagged `"operator"` in the **Availability tag** vocabulary — `Station.availability()` reports it `state="absent"`, exactly like a VI that never connected. Drivers implement `close()` (release the session, return the instrument to LOCAL where it has that concept, never raise); VIs inherit `ping()` and the `disconnect()` release hook. A narrower, VI-internal sibling — the declared `detach_when_idle` standard (see **Availability**) — lets a single-client VI release its OWN session automatically between runs with no operator action; that VI stays enumerable and controllable (`state="detached"`), never lands in the offline registry, and is a different mechanism from this one. The GUI pair is one `ConnectionButton` per card (`gui/lifecycle_toggle.py`), next to the Initiate/Standby toggle. Distinct from **Instrument fault**, which is an instrument that stopped answering while CryoSoft still held it. |
| **Driver error-reporting standard** | Every driver method that programs a mode or a setpoint must verify its write and document how: SCPI error queue, IEEE-488.2 status byte, protocol acknowledgement, or explicit readback (full text plus the per-driver table in `drivers/README.md`). A bus write returning without an exception proves only that the bytes left the computer — most of these instruments accept a command they cannot execute and record the refusal somewhere only a deliberate read will find, which is how a real 6221 rejected every DC current-set call for a whole session (2026-07-22) with nothing in `cryosoft.log`. A verified refusal is raised as `CryoSoftInstrumentError`, carrying the instrument's own `code` and `instrument_message` verbatim plus the `context` (the driver call refused); it subclasses `CryoSoftCommunicationError`, so layers that already treat driver calls as fallible are unaffected. Two guard rails: the checker never fails a working call (a bus failure while reading the queue is swallowed), and recovery paths drain the queue rather than raise, so an abandoned sequence's error is never charged to the next command. Sim twins raise the same typed error with the same code for the same wrong sequence, and model only refusals the hardware actually produces. |
| **Safe shutdown** | `safe_shutdown()` on every driver, real and sim: one unconditional, argument-free call that leaves the instrument in a documented safe idle state, so anything abandoning a sequence — a failed procedure, an emergency stop, an agent that stopped answering — has one call to make on every instrument without knowing which it is. Idempotent, never raises, callable from any leftover state, and each driver documents what it recovers from. **Safe is not off**: safe idle means the instrument stops being able to do harm, which is instrument-specific — a magnet's is HOLD, not zero field (a fast dump is how magnets quench); a level meter's is pulsed refresh, not off (the level is a safety input); a Lakeshore's leaves the setpoint alone but takes the heater range to OFF. Duck-typed like `get_idn()`/`close()`, with no `DriverBase`: `tests/test_conformance.py` is the contract, and each sim declares its landing state as a private `_is_in_safe_state()` predicate the test asserts. Distinct from a VI's `standby()`, which is the supervised, instrument-aware stand-down the operator (or a procedure) asks for, and from `close()`, which under the **Connection lifecycle** releases the bus session and changes no instrument state at all. |
| **Availability** | L2. The single answer to "why can't I use this instrument?" for one VI (`cryosoft.core.availability`, GLOSSARY entry point for the standard also described under **Offline instrument** / **Instrument fault** / the `detach_when_idle` half of **Connection lifecycle**): a closed **Availability tag** vocabulary plus a declared policy table (`TAG_POLICY`) resolve to one of four mutually exclusive `AVAILABILITY_STATES` — `"live"` (no tags, fully usable), `"detached"` (in the live registry, session released by the `detach_when_idle` declaration, reacquires on arm), `"faulted"` (live but carries `not_responding`), `"absent"` (not in the live registry at all). State is always *derived* from tags by `state_for()`, never set by hand — enforced by `Availability.__post_init__`, which also rejects an out-of-vocabulary tag, the same construction-time invariant discipline `Condition.__post_init__` uses for scope-follows-severity (see **System condition**). `Station.availability(vi_name)` / `availabilities()` assemble the record as a DERIVED VIEW over the Station's existing sources of truth — the offline registry for absence, the comm-origin slice of the unified condition registry for `not_responding`, the VI's own `is_attached()` for `detached` — never a fourth registry to keep in sync; `Orchestrator.availability()`/`availabilities()` re-export both for the GUI. `decide_availability(tags)` returns the winning `TagPolicy` (or `None` for a live VI) via `TAG_PRECEDENCE` when more than one tag applies. Replaces three previously separate lookups — `OfflineInstrument.origin`, the comm-origin condition via `vi_faults()`, and the RTM2's unobservable detached-idle window — with one accessor and one declared policy table, so a future degraded mode is a new tag plus a policy row, never a fourth mechanism. Pure policy (stdlib-only, no `Station`/`Orchestrator` import) isolated by import-linter contract C14, mirroring C13's isolation of `conditions.py`. |
| **Availability tag** | The closed vocabulary (`AVAILABILITY_TAGS`, `cryosoft.core.availability`) a VI's **Availability** record carries, a `frozenset[str]` — several can hold at once (e.g. `{"operator", "connect_failed"}`, an operator-released VI whose reconnect then fails on hardware — see **Offline instrument**), unlike the single derived state that vocabulary implies: `"connect_failed"` — hardware unreachable, at build time or on a failed reconnect; `"operator"` — the operator released it via the **Connection lifecycle**; `"not_responding"` — held but stale/disconnected, a comm-origin `Condition` (see **Instrument fault**); `"detached"` — a `detach_when_idle` VI's session is released between uses, reacquires on arm. Each tag's row in `TAG_POLICY` (a frozen `TagPolicy`) declares its `state`, `enumerable`, `controllable`, `fails_claimed_run`, `raises_error_event`, and `recovery` (`"connect"` / `"retry"` / `""` = automatic) — the first time these policies are written down rather than implied by which registry a VI landed in. `TAG_PRECEDENCE` (most-restrictive-first: `connect_failed`, `operator`, `not_responding`, `detached`) is what `decide_availability()` uses to pick the single governing row when more than one tag applies. |
| **Offline instrument** | A configured VI whose hardware failed to *connect* when `build_station()` ran (driver `__init__` raised, or the VI's own bring-up raised a communication error), or one the operator released via the **Connection lifecycle**. Recorded as an `OfflineInstrument` (name, registry `vi_type`, human-readable reason, failed driver aliases, a `since` timestamp, and `tags: frozenset[str]` drawn from the **Availability tag** vocabulary's absence tags, `{"connect_failed"}` and/or `{"operator"}`) in the Station's offline registry (`register_offline_vi()`, `offline_vi_names()`, `get_offline_info()`) instead of aborting the build — the degraded build. Both tags can hold at once: a reconnect attempt on an operator-released VI that then fails on hardware carries `{"operator", "connect_failed"}`, so the card renders both facts instead of one silently overwriting the other. Invisible to the live enumerators (`get_vi_names()` etc.), so the Orchestrator, procedures, and safety evaluation see a smaller station; the GUI renders a control-free card (`gui/offline_panel.py`) whose wording is keyed off `tags`, whose detail window offers the one reconnect action, `Orchestrator.connect_instrument()` → `Station.connect_instrument()` (IDLE-only, explicit verdict, rebuilds drivers, then re-runs the identity check). `Station.availability(vi_name)` (see **Availability**) reports every offline VI as `state="absent"`, `enumerable=False`, `controllable=False` — the same single accessor that answers for a live or faulted VI. Distinct from **Instrument fault** (a VI that DID connect and has since gone stale/disconnected during polling — the RUNTIME sibling of this build-time registry, carrying `not_responding` instead, `state="faulted"`). Config errors are not offline instruments: they still abort the build and trigger the startup fallback chain. |
| **System condition** | The standard unifying every "something is wrong" signal in CryoSoft: a `Condition` (`core/conditions.py`) is origin × severity, and scope follows from severity alone — never from which origin reported it. Exactly four producers: `"comm"` (a VI's poll going stale/disconnected — `Station._record_comm_condition()`, see **Instrument fault**), `"safety"` (a VI's `evaluate_safety()` flag — `Station.update_conditions()`, see **Safety hold** / **Critical safety flag**), `"envelope"` (an `ExperimentEnvelope.check_state()` violation — `core.conditions.envelope_conditions()`, see **Session envelope**), and `"trend"` (a failing named judgement over the trend-history store — see **Trend check**), the only origin published through the generic `Station.publish_conditions(origin, conditions)` rather than an origin-specific producer method. All four land in ONE registry, `Station._conditions` (`{key: Condition}`), read via `conditions()` / `active_critical_conditions()` and acknowledged via `acknowledge_condition(key)` — there is no per-origin store any more. The pure policy — the `Condition`/`Verdict` value objects and the deterministic `decide(conditions, watched_vis, run_active) -> Verdict` function — lives in `core/conditions.py` with no dependency on `Station` or `Orchestrator` (import-linter contract C13), so it is unit-testable standalone. The Orchestrator is the sole EXECUTOR: each tick it calls `check_safety()` once, feeds the result to `Station.update_conditions()`, merges in this tick's `envelope_conditions()` (skipped once already in EMERGENCY), diffs the resulting condition-key set against last tick's to fire onset actions (a fault event for a new comm condition — the ONLY remaining onset action, since a hold's `standby()` is no longer edge-triggered here but re-asserted every tick by `_enforce_safety_holds()`, see **Hold enforcement**), calls `decide()` once over the merged list, and executes its `Verdict` (`emergency` → `_enter_emergency()`, `run_failure` → `_fail_run_for_fault()`). See **Severity ladder** for what each severity enforces. |
| **Severity ladder** | The three values a `Condition.severity` (see **System condition**) may take, each with fixed enforcement — a flag's or fault's severity, never which VI reports it, decides scope: `"advisory"` — reported, no enforcement (every `"trend"`-origin condition uses this rung — see **Trend check** — no other origin has published one yet); `"hold"` — scoped to `affected_vis` (a non-empty `frozenset`, required by `Condition.__post_init__`): those VIs are driven to standby and KEPT there for as long as the hold persists and is not acknowledged, a LEVEL-TRIGGERED invariant re-checked every tick rather than a one-shot onset action (`Orchestrator._enforce_safety_holds()` — see **Hold enforcement**), refused manual control by `_manual_action_admissible()`, and fail any run watching one of them; `"critical"` — station-wide by construction (`affected_vis` MUST be `None`, also enforced by `__post_init__`): every critical condition lands in `decide()`'s `Verdict.emergency`, driving `_enter_emergency()`'s blanket `standby_all()` and refusing every manual action station-wide until `Orchestrator.acknowledge()` unlocks the override (see **Hold acknowledge** — the SAME control also unlocks a hold-severity condition, without ever entering EMERGENCY). `quench` (critical) and `helium_low` (hold) are the only safety flags declared today — see **Safety-flag manifest**. |
| **Instrument fault** | A comm-origin, hold-severity `Condition` (see **System condition**) on a VI that DID connect at build time and has since gone stale/disconnected during polling — the runtime sibling of **Offline instrument**, which never connected at all. `Station._record_comm_condition()` builds it, scoped (`affected_vis`) to just that one VI, in the same pass `get_state()` already computes `_stale`/`_disconnected`. It surfaces through two adapters over the same condition: `Station.availability(vi_name)` (see **Availability**) folds it into the unified record as the `not_responding` **Availability tag** (`state="faulted"`, `enumerable=True`, `controllable=False` per `TAG_POLICY`), and `vi_faults()` remains the permanent, comm-specific GUI adapter synthesizing one `FaultRecord` (`vi_name`, `kind` — `"stale"`/`"disconnected"`, `message`, `since`, `acknowledged`) per comm-origin condition — fields (kind, acknowledged) the unified record deliberately does not carry, since acknowledge/retry are comm-specific actions. `clear_fault()` removes the condition entirely on the next successful poll (acknowledged or not — a recovered VI has nothing left to acknowledge). Three failure tiers by blast radius: a fault on an UNCLAIMED VI (no run using it, or a run that does not claim it) quarantines only that VI — controls disabled, a fault badge, no state change, a warning-severity `ErrorEvent`; a fault on the active run's CLAIMED (watched) VI additionally fails the run (`run_finished` status `"failed"`, the machine returns to IDLE — not global ERROR — and the queue does NOT auto-continue); a tripped **Critical safety flag** is a DIFFERENT, safety-origin condition entirely — never a comm-origin fault — and forces station-wide EMERGENCY via `decide()`'s `emergency` field regardless of any VI's fault state. Global ERROR survives only for an unhandled tick-boundary exception (unknown blast radius). `_manual_action_admissible()` refuses a faulted VI outright, before every other admission rule (including a safety hold), in every state including IDLE — see **Claim** — by reading the `not_responding` tag off `Station.availability(vi_name)` against `TAG_POLICY["not_responding"].controllable`, not a hardcoded origin check; the table carries no override column for this tag, which is what makes the refusal unconditional where a safety hold's is bypassable via the EMERGENCY manual override. `core.events.ErrorEvent` is the structured signal payload (`vi_name`, `kind` — `"fault"`/`"run_failure"`/`"safety"`/`"safety_hold"`/`"internal"` — `severity`, `message`, `timestamp`) carried on `Orchestrator.error_event`, emitted alongside the compat `error_occurred(str)` for everything except a plain per-VI fault warning or a routine `"safety_hold"` re-assertion (both `severity="warning"`, both fire `error_event` only, to avoid banner noise in windows still on the compat signal). `"safety_hold"` (see **Hold enforcement**) is the Orchestrator re-asserting, or failing to re-assert, `standby()` on a VI held by a hold-severity safety condition — VI-scoped by construction, deliberately NOT the station-wide `"safety"` tier above it: an escalation after repeated failed attempts still fires only for the one VI concerned, never a blast radius beyond it. |
| **Fault acknowledge** | docs/plans/archive/operation-concurrency-and-error-scoping.md §3. `Station.acknowledge_fault(vi_name)` / `Orchestrator.acknowledge_fault(vi_name)` mark an active **Instrument fault** record acknowledged, calming the Monitor's per-VI badge/banner without changing anything else — the fault still refuses manual actions and still shows on the panel until it clears. Distinct from `Orchestrator.acknowledge()` (see **Hold acknowledge** — the unified, time-boxed EMERGENCY/hold-severity override, single home on the Monitor window's top bar — moved off `ProcedureWindow`; its private `_acknowledge_emergency()` helper carries the EMERGENCY-only two-stage state-recovery logic). An acknowledged-but-recovered fault simply disappears on the next successful poll (`clear_fault()`) — there is nothing left to acknowledge once the instrument responds again. The paired recovery action is `retry_fault()` (`Station`/`Orchestrator`): resets the error counter and forces one fresh poll — never rebuilds a driver, unlike `connect_instrument()` for an **Offline instrument**. |
| **Safety-flag manifest** | `BaseVirtualInstrument.safety_flags: ClassVar[dict[str, str]]` (the System-Condition standard's producer-side declaration, full text in `BaseVirtualInstrument`'s docstring): every flag a VI's `evaluate_safety()` can report, mapped to its severity — `"advisory"` (no enforcement, reserved), `"hold"` (scoped to the VIs whose **Safety concern** names it), or `"critical"` (station-wide by definition — see **Critical safety flag**). Declared on the category base that owns the flag's physical semantics (`MagnetBase` → `{"quench": "critical"}`, `LevelMeterBase` → `{"helium_low": "hold"}`), never on each concrete VI. Subclass manifests are merged over the MRO by `merged_safety_flags()` (same merge discipline as `control_limits`) — a subclass adds flags, it never contradicts a base's declared severity for one it inherits. Contrasts with `safety_concerns()`: this is the PRODUCER side (what a VI can report and how severe it is), `safety_concerns()` is the CONSUMER side (which — necessarily hold-severity — flags a VI depends on to keep operating). Critical severity is station-wide scope by construction (the System-Condition standard, `core/conditions.py`), so no derived "critical subset" accessor is needed — `Station.active_critical_conditions()` reads the live condition registry directly. |
| **Safety concern** | `BaseVirtualInstrument.safety_concerns() -> set[str]`. A static declaration of which HOLD-severity safety flags (see **Severity ladder**) — named exactly like `evaluate_safety()`'s keys — a VI depends on to operate safely, independent of whether THIS VI is the one that reports them: the level meter reports `helium_low` via `evaluate_safety()` but is not itself concerned with it (it keeps reading regardless of the level it reports); a magnet is concerned with it but never reports it. Only `MagnetBase` overrides the empty-set default, declaring `{"helium_low"}`; every other category base (`TemperatureControllerBase`, `RotatorBase`, `LevelMeterBase`, `MeasurementInstrumentBase`, a switch VI) keeps the default — none is concerned with `quench`: `quench` is critical severity and therefore station-wide by construction (see **Critical safety flag**), so naming it in any VI's `safety_concerns()` would be meaningless — EMERGENCY has already stopped every VI, concerned or not, the instant it trips. `Station.get_concerned_vis(flag)` is the read side (every VI whose declaration names *flag*), consulted by `Station.update_conditions()` to scope a hold-severity flag's `Condition.affected_vis`. |
| **Critical safety flag** | A flag declared `"critical"` in its producer's `safety_flags` manifest (see **Safety-flag manifest**) — station-wide by construction: its `Condition` always has `affected_vis=None` (enforced by `Condition.__post_init__`), so no VI declares (and per the manifest standard, none may declare) a concern for it in `safety_concerns()` — a per-VI hold would be meaningless once EMERGENCY has already stopped everything. `quench`, declared on `MagnetBase`, is the only critical flag today. `core.conditions.decide()` collects every critical-severity condition (from any origin) into `Verdict.emergency`; the Orchestrator's tick enters EMERGENCY (`_enter_emergency()` — always a blanket `standby_all()`, since there is no concerned subset to narrow to) the instant `emergency` is non-empty and the machine isn't already there, and `_manual_action_admissible()`'s EMERGENCY rule refuses every manual action station-wide until `acknowledge()` unlocks the override (see **Hold acknowledge**). Never tolerable: **Tolerated safety flags** filters hold-severity flags only, so a critical flag's condition is built unconditionally regardless of any operation's tolerance. |
| **Safety hold** | A hold-severity, safety-origin `Condition` (see **System condition**): scope follows from severity, so it is scoped (`affected_vis`) to every VI whose `safety_concerns()` names a currently-tripped, non-tolerated flag (see **Tolerated safety flags**). Built once per tick by `Station.update_conditions(safety, tolerated_flags=...)` from the SAME `check_safety()` snapshot the tick already computed, into the ONE unified registry alongside every comm- and envelope-origin condition (`Station._conditions`, read via `conditions()`/`active_critical_conditions()`). `Condition`s still share this one registry — that part is unchanged — but a hold-severity condition now DOES have an enforcement-affecting override, `Orchestrator.acknowledge()` (see **Hold acknowledge**), distinct from the display-only `Station.acknowledge_condition(key)` (marks `Condition.acknowledged`, calms a UI badge, never consulted by the admission gate). A held VI is refused manual control by `_manual_action_admissible()` (regardless of Orchestrator state, exactly like an **Instrument fault**, unless `acknowledge()` has unlocked it) and fails any run that claims/watches it (`_fail_run_for_fault()`, the machine returns to IDLE, every other instrument stays usable) — but clears itself automatically the moment the flag recovers or becomes tolerated, with no retry action (there is no hardware to retry, only a physical condition to wait out). For as long as a VI appears in `affected_vis`, `Orchestrator._enforce_safety_holds()` keeps it AT standby — a LEVEL-TRIGGERED invariant, re-checked every tick, not the one-shot onset dispatch this replaced (see **Hold enforcement** for the mechanism, including why an onset-only dispatch left a hold that outlived an acknowledge-then-expire cycle permanently unenforced) — never a blanket `standby_all()`: an unconcerned VI (e.g. temperature control while only the magnets are held for low helium) is left running untouched. Distinct from a **Critical safety flag**, whose condition is always station-wide (`affected_vis=None`) by construction — a critical flag is never named in any VI's `safety_concerns()`, so it never produces a Safety hold, only EMERGENCY. |
| **Hold enforcement** | `Orchestrator._enforce_safety_holds()` (`core/orchestrator.py`), called every tick over `verdict.held_vis`, once `decide()` has run: the **Safety hold** standard's enforcement, made LEVEL-TRIGGERED rather than the edge-triggered onset dispatch it replaced. For as long as a VI is held and not acknowledged (`override_active(vi_name)` — an acknowledged hold is skipped, exactly like `_manual_action_admissible()` treats it), the VI is re-checked and, if needed, re-commanded to standby EVERY tick, not just once when the hold began — which is what closes the gap the onset-only dispatch left open: an operator who acknowledges to unlock manual control, moves the VI during the window, and lets the window lapse got the UI back in "held" state with the hardware never driven back down, because expiry revokes manual PERMISSION, it does not by itself re-command hardware. Evidence comes from `BaseVirtualInstrument.standby_status()` (the standby-provenance standard, `virtual_instruments/base.py`), never a physical read: `"reached"` — at safe idle, nothing to enforce this tick; `"converging"` — a `standby()` is already in flight and will arrive, so it must NOT be re-issued (re-issuing unconditionally every tick is the naive-fix bug this guards against: rebuilding a `RampableVI`'s ramp generator from scratch on every tick restarts the ramp from scratch every time, and the magnet never arrives); `"away"` — no standby command is in flight, so `standby()` is (re-)issued now, rate-limited to at most one attempt per VI per `hold_enforcement_interval_s` (`devices.yaml`'s `safety:` block, `Station.read_safety_config()`, default 10s — a VI with no recorded attempt yet fires immediately, which is what makes hold ONSET and hold RE-ASSERTION the same code path). Command provenance is not physical verification — `standby_status()` knows the standby command was issued and its ramp finished, not that the hardware actually arrived, so a PSU silently ignoring a ramp still reads `"reached"` here. Generality is deliberate (CLAUDE.md's "standards over one-off code"): this method reads only `Condition.severity == "hold"` and `affected_vis` — both already resolved by `core.conditions.decide()` — and never names a flag, so a future hold-severity flag beyond `helium_low` inherits enforcement automatically, with zero Orchestrator change; the one non-general part is that `standby()` is the only safe response this contract models, so a future flag needing a different safe action is a declaration on the VI itself, never a special case here. A VI whose `standby()` keeps raising past `hold_enforcement_max_attempts` consecutive attempts (default 3) is escalated exactly ONCE per episode — a CRITICAL-level log line plus a `kind="safety_hold"`, `severity="error"` `ErrorEvent` — WITHOUT transitioning the state machine to EMERGENCY, since that remains a separate decision made elsewhere; a routine re-assertion instead announces itself with only a `severity="warning"` `ErrorEvent` (never silent, since re-asserting standby moves hardware the operator did not just ask for). `"safety_hold"` is a VI-scoped `ErrorEvent.kind` tier (see **Instrument fault** for the full enumeration), deliberately distinct from the station-wide `"safety"` tier: it never carries a blast radius beyond the one VI it names. Do not call this mechanism a "watchdog" — `cryosoft/core/watchdog.py` is an unrelated ramp-stall detector; this is the Safety hold standard's enforcement. |
| **Hold acknowledge** | `Orchestrator.acknowledge()` (`core/orchestrator.py`): the single GUI entry point unlocking manual control of ANY currently held VI — a **Safety hold** or a station-wide EMERGENCY alike — for a fixed, configurable window (`safety.manual_override_timeout_s` in `devices.yaml`, `Station.read_safety_config()`, default 300s), not a standing bypass. Generalizes what was previously EMERGENCY-only (`acknowledge_emergency()`, now the private `_acknowledge_emergency()` helper `acknowledge()` delegates to while in EMERGENCY) to the `hold` severity too, since `hold` is the severity that actually fires in ordinary low-helium operation and previously had no override path at all. Two independent expiry stores on the Orchestrator: `_emergency_override_until: float \| None` (one global window) and `_hold_override_until: dict[str, float]` (`Condition.key` → expiry, one entry per acknowledged hold). `_manual_action_admissible()` reads both live via a `time.time()` comparison — enforcement is the comparison lapsing on its own, never a tick-driven "re-lock" event. Pruning (once per tick, in `_tick_body()`) is by EXPIRY ONLY, deliberately never because the condition disappeared from `verdict.held_vis` — a flag flapping right at its threshold (helium_low hovering near the warning level is exactly this in practice) would otherwise force a fresh acknowledge on every re-trip within the same window, defeating the point of the cooldown; the accepted trade-off is that a stale acknowledgment can silently cover a NEW, unrelated trip of the same flag within the leftover window, bounded by the timeout. Expiry itself no longer just returns a VI to a refused-control state: `Orchestrator._enforce_safety_holds()` (see **Hold enforcement**) is level-triggered, so the very next eligible tick after an override lapses re-asserts `standby()` on any VI still in `verdict.held_vis` and found away from it — the operator-visible consequence being that a field moved during an acknowledge window is driven back down once the window closes, not left wherever it was last put. The hold override deliberately reaches through claim-protection (rule 4 of `_manual_action_admissible()`) exactly like the EMERGENCY override already did — both return `True` before the claim check is ever reached — which is what lets it work identically under `PAUSED` with no PAUSED-specific code anywhere; this is also the source of a known, accepted gap: `resume_procedure()` unconditionally re-dispatches `_last_system_targets` on resume, with no way to know a claimed VI was manually moved via an active override during the pause (deferred, not fixed, by explicit design decision — a future change would need to track manually-touched claimed VIs and have `resume_procedure()` refuse or confirm). A hold-override never admits while the Orchestrator is in EMERGENCY or ERROR (the state guard in rule 0b) — EMERGENCY requires its own override acknowledged fresh (closing a leak where an already-acknowledged hold would otherwise admit action through a LATER, unacknowledged EMERGENCY on the same VI), and ERROR means unknown blast radius, never a known condition a human can safely act around. `_enter_emergency()` also unconditionally clears both stores on every fresh EMERGENCY entry, as defense in depth alongside the state guard. Public accessors: `held_vi_names()`, `override_active(vi_name=None)`, `manual_override_expires_at()` — the GUI's top-bar "Acknowledged (mm:ss)" countdown and tests should read through these, never the private timestamp fields directly. Distinct from `Station.acknowledge_condition(key)`/`Condition.acknowledged` (display-only, never consulted here) and from **Tolerated safety flags** (`OperationBase.tolerated_safety_flags` prevents a `Condition` from being built at all for a tolerant operation's duration — a different mechanism solving a different problem: the sanctioned, supervised `HeliumFillOperation` path vs. ad hoc manual control). |
| **Tolerated safety flags** | `OperationBase.tolerated_safety_flags: frozenset[str]` (see `core/operation.py`), resolved ONCE per tick by the Orchestrator (only for a running operation; a plain procedure or IDLE tolerates nothing) and passed into `Station.update_conditions(safety, tolerated_flags=...)`. Filters HOLD-severity safety flags ONLY, applied at the single point a hold-severity flag's `Condition` would otherwise be constructed (`Station.update_conditions()`): a tolerated flag simply gets no condition built for it that tick — no hold, no run failure. Never applied to a critical or advisory flag's own condition — severity alone decides whether tolerance is even consulted (see **Severity ladder**), and a critical/advisory condition is built unconditionally. This is what lets `HeliumFillOperation` (`tolerated_safety_flags = frozenset({"helium_low"})`), which claims and ramps every magnet to zero, run to completion instead of being held on (and having its own run failed for) the very condition it exists to fix. `Orchestrator._operation_end_state()` mirrors this at finish: only a still-non-empty `Station.active_critical_conditions()` sends a finishing operation back to EMERGENCY instead of IDLE — a merely tolerated hold-only flag does not, since it was never why EMERGENCY would have been entered in the first place. |
| **`Gate`** | `core/gates.py`. A tick-driven wait primitive: an optional one-shot `action` callable, followed by an optional `check` predicate that must hold True continuously for `window_s` seconds before `step()` reports satisfied (any `False` resets the stability clock; polled once per Orchestrator tick, mirroring `RampableVI.advance_ramp()`/`ramp_status()`'s generator-per-tick idiom). `check_once()` is the one-shot alternative — runs `action` once and reads `check()` a single time, ignoring `window_s` entirely — used for a **Postcondition gate**'s immediate-finish evaluation; never combined with `step()` on the same instance. |
| **`initiation_gates()` / `reading_gates()`** | `BaseProcedure` hooks (empty-tuple no-op default) returning `tuple[Gate, ...]`: gates that must all be satisfied before the Orchestrator proceeds from a completed ramp to a measurement. `initiation_gates()` governs the run's first RAMPING→MEASURING transition (right after `initiate()`); `reading_gates()` governs every one after (after each `change_sweep_step()`). When a procedure declares any gates for a transition, they fully replace that `PhasePlan`/`StepPlan`'s `wait_s` dwell timer for that transition — a procedure with no gates behaves identically to today's flat `wait_s` wait. |
| **`INITIATION_GATE` / `READING_GATE`** | `OrchestratorState` members entered from `RAMPING` once all system targets are reached and the active procedure declared gates for this transition; the Orchestrator steps every pending `Gate` once per tick until all are satisfied, then proceeds to `MEASURING`. Included in the same pausable/stale-checked state groups as `RAMPING`/`MEASURING`. |
| **Pause boundary** | The one place a pause is allowed to *wait* instead of taking effect at once. `Orchestrator.pause_procedure()` normally pauses immediately, from any run state, holding the hardware where it stands (`Station.stop_ramps()` — a magnet PSU ramps autonomously to its last setpoint, so a software-only pause would leave the field moving) and freezing the `wait_s` clock, which `resume_procedure()` restores so a half-elapsed settle still completes. `MEASURING` is the single exception, and the reason this term exists: that is the one state where a point is ramped, settled and gated but not yet read, so pausing there would strand it and resume would take its reading after an arbitrarily long hold. A pause requested in `MEASURING` is therefore DEFERRED — `_pause_requested` is raised (public read: `pause_pending`), the status line says "Pause requested", `measure()` saves its datapoint on the next tick, and the `SWEEPING` branch of `_tick_body()` calls `_enter_paused()` the moment the point is complete; resume then returns to `SWEEPING`, whose next act is the ramp to the next point. The **Reading loop** itself is never at risk: `measure()` runs synchronously inside one tick, so a click can only arrive between ticks, never between two readings of one datapoint. `resume_procedure()` called while a request is still pending withdraws it; the request is cleared on every run lifecycle boundary (`_start_run()`, `_abort_active_procedure()`, `_finish_run()`) so it can never outlive its run. Distinct from **abort**, which is always immediate and ends the run (`abort_procedure()` runs off the click, not the tick, and is unaffected by a pending request). Monitoring, the condition registry, **Hold enforcement** and EMERGENCY all continue through a pause unchanged — they run ahead of the state-machine dispatch in `_tick_body()`; only `run_failure` is suspended, since `run_active` excludes `PAUSED`. |
| **Postcondition gate** | A `Gate` an operation declares via `postcondition_gates()`: evaluated by the Orchestrator exactly ONCE, immediately, as the run ends (`Gate.check_once()` — no holding, no timeout; docs/plans/archive/operation-concurrency-and-error-scoping.md §2, "immediate finish"). An unmet gate never blocks completion — it is named in the run manifest's `postconditions_unmet` list and logged at WARNING. The difference between "the commands ran" and "the cryostat is verifiably in the promised state", surfaced as a warning rather than a wait. |
| **Persistent mode** | Superconducting-magnet operating mode where the field is held by a closed superconducting loop and the switch heater is off. Handled by `SuperconductingMagnetPersistentVI`. `start_ramp(target, persistent=True)`: `persistent=True` (default) ends the ramp by cooling the switch and parking the PSU at zero with the coil holding the field — for a single set-and-hold. `persistent=False` leaves the switch heater energised and the PSU holding the target directly — for a sequence of many ramps (e.g. a field sweep) that should only pay the heater warmup once. `magnet_field_T()`/`magnet_current()` read the coil current instead of the PSU current whenever the driver reports persistent mode. |
| **PSU status** | `SuperconductingMagnetVI.magnet_status()`'s return value: the raw hardware status string reported by the PSU driver — `HOLD`, `RAMPING`, `QUENCH`, or `CLAMPED` (the last never actually produced by any driver in this codebase today; the Oxford Mercury iPS-M's `CLMP` action state maps to `HOLD` instead, and the sim driver models clamping as a raised `CryoSoftSafetyError` from `set_current_setpoint()` rather than a status string — kept in `magnet_status()`'s contract and `magnet_state()`'s `"clamped"` branch for a future driver that does report it). A pure passthrough of the driver's own report — never the VI's interpretation. See **Magnet state**. |
| **Magnet state** | `magnet_state()`'s return value: the magnet VI's logical interpretation of **PSU status** plus the live current readings, distinct from the raw hardware report. One of `"standby"`, `"ramping"`, `"holding"`, `"quenched"`, `"clamped"`, plus `"persistent"` on `SuperconductingMagnetPersistentVI` (heater off, coil holding a nonzero field). PSU status is the source of truth for "is a ramp/park sequence active" — `"ramping"` is returned whenever PSU status is not `HOLD`/`CLAMPED` OR the VI's ramp generator has not yet exhausted (`ramp_status() == "RAMPING"`), so a tick where the PSU momentarily reads `HOLD` mid-sequence (between ramp segments, or during `SuperconductingMagnetPersistentVI`'s matching/warmup/cooldown/parking sub-phases) is never misreported as `"standby"`/`"holding"`/`"persistent"`. Only once PSU status is genuinely at rest do the current-threshold checks decide `"standby"` (PSU ≈ 0 A, and on the persistent VI also coil ≈ 0 A with the heater off) vs `"persistent"` vs `"holding"`. Operations (`SampleLoadOperation`, `SampleUnloadOperation`, `HeliumFillOperation`) gate readiness on `magnet_state() == "standby"`, never on raw field/current thresholds — the whole reason this state exists is to give every caller one shared, correct answer to "is this magnet actually idle" instead of each one re-deriving it from thresholds. |
| **VISA / GPIB** | The instrument-communication standard (PyVISA library) and the bus most lab instruments use. A "resource string" like `GPIB0::19::INSTR` addresses one instrument. |
| **Analysis Mode** | The Tensormeter RTM2's onboard tensor-computation engine (`TensormeterRTM2.set_analysis_mode()`, vendor TCP Commands §3.12): Auto, Kelvin, Zero-Offset Hall, Van-der-Pauw, Ratiometric, or Differential. Set alongside a switch-matrix state sequence (`set_switch_states()`) and a source current/voltage, the firmware itself computes the resistance tensor — CryoSoft never reimplements van-der-Pauw math for this instrument, it only configures the mode and reads the result back (see **Res A / Res B**). |
| **Res A / Res B** | The two resistance-tensor output columns the Tensormeter RTM2's data array reports each row (DC value plus 1st/2nd/3rd-harmonic Re/Im, vendor TCP Commands §3.1), named after the firmware's own terms rather than CryoSoft-asserted "sheet"/"Hall" semantics — which physical quantity each represents depends on the operator's chosen switch-state sequence and **Analysis Mode**, exactly as on the real instrument. `TensormeterRTM2MeasurementVI` surfaces these as its `res_a_ohm` / `res_b_ohm` measurement quantities. |
| **SI units rule** | All APIs use Tesla, Kelvin, Ampere, Volt, second. Display formatting (mK, µA) happens only in the GUI. |
| **Sweep builder** | `core/sweep_builder.py` — reusable sweep-array construction shared by Procedures: `build_piecewise_sweep()` (a `SweepSegment(start, end, step)` list stitched into one array, letting different sub-ranges use different step sizes, e.g. coarse outside a region and fine inside it), `load_custom_sweep_csv()` (arbitrary non-uniform sweep from a single-column CSV), and `apply_hysteresis()` (extends a one-directional sweep into a forward+backward loop). See **Sweep axis** for the declarative way most Procedures use these three. |
| **Measurement root** | `cryosoft.core.paths.measurement_root()` — the fixed, machine-level, admin-set root of the whole measurement-data hierarchy (`<measurement_root>/users.json`, `<measurement_root>/servicing/<config_name>/...`, `<measurement_root>/sessions/<user_id>/<session_id>/...`). Resolved by precedence — the `CRYOSOFT_MEASUREMENT_ROOT` env var, else the `measurement_root` key in a machine-level settings file (`App-config.yaml` under `%ProgramData%\CryoSoft` on Windows, `/etc/cryosoft` elsewhere) — with no further fallback: an unconfigured installation refuses to start (`RuntimeError`) rather than inventing a default. Deliberately not GUI-editable and not per-user, unlike the QSettings-backed `sessions_root()`/`set_sessions_root()` it replaces, so it stays fixed across a station's lifetime instead of drifting via live settings. `paths.py` is import-linter contract C1 foundation (stdlib only), the same module `log_directory()` lives in. |
| **Session** | The tier between **Measurement root** and an **Experiment**: a named, resumable, per-user folder holding multiple experiments (`Session`, `session/models.py`; persisted as `<measurement_root>/sessions/<user_id>/<session_id>/session.json` by `SessionStore`, `session/store.py`). Nested under the owner's `user_id` — ownership is structural (a directory), not just a field read out of `session.json` — via `SessionStore.list_sessions(user_id)`/`load(user_id, session_id)`/`save()`. One user can own several sessions — a session is not identified by its owner alone. Carries `default_experiment_dir` (dead field — never read/written outside `models.py`), `last_open_experiment_id` (auto-reopened on resume), the **Experiment index** (`experiments`), and — one level up, at `sessions/active.json` — a machine-wide `(active_user_id, active_session_id)` resume pointer (distinct from `ExperimentStore`'s own `active.json`, which tracks the active *experiment* one level deeper, inside one session folder). Experiment-directory containment under the active session is hard-enforced — a folder name containing a path separator, `.`/`..`, or colliding with an existing one is refused outright by `ExperimentManager.start_experiment()`, not just warned. Switching sessions is deferred-until-restart: the User menu's `Resume Session…` action picks or creates one and calls `SessionStore.set_active(user_id, session_id)`, but `ExperimentManager`'s own `ExperimentStore` stays fixed to whichever session was active at launch (see **User menu**). Not to be confused with `gui/form_autosave.py`'s form-field persistence (historically also called "session") or `core/plan.py`'s **Session envelope** (per-experiment safety bounds) — resolving that four-way name collision is what introduced this tier; see `docs/plans/session-tier-and-terminology.md`. |
| **Guest user** | The fixed roster identity (`session.models.GUEST_USER_ID = "guest"`, `GUEST_USER_NAME = "Guest"`) used whenever nobody has logged in (`app_settings.current_user_id()` returns `None`). Auto-registered into `users.json` at every startup (`cryosoft.main._ensure_guest_user_registered`, idempotent — never clobbers an existing, possibly admin-customized, Guest entry), so a logged-out operator always has a real roster entry to own sessions under `sessions/guest/` and to satisfy `ExperimentManager.start_experiment()`'s roster-membership check. A logged-out bootstrap session (`cryosoft.main._resolve_active_session`) is named `"guest"`. |
| **Experiment** | A named group of **runs** on one sample toward one scientific question, owned by the Session Manager (L6): `ExperimentRecord` holds the **user**, the sample-info snapshot, the config identity, the **session envelope**, the run list, free-text findings, the GUI-authored run `queue` (opaque JSON the session layer stores but never interprets — contract C11), and (publishing track) the ELN linkage. Persisted as `<measurement_root>/sessions/<user_id>/<session_id>/<experiment_id>/experiment.json` — one level inside the **Session** tier's own folder (`SessionStore`, `cryosoft/session/store.py`), itself rooted at `cryosoft.core.paths.measurement_root()` (a fixed, machine-level, admin-set location independent of any GUI form field) — alongside a `gui_state.json` (GUI form/plot state, also opaque to this layer) and a `data/` folder holding the experiment's HDF5 files (sub-folders allowed, e.g. `data/heating_runs/`) — the whole `<experiment_id>/` folder is the complete, portable record. `experiment_id` is also the folder's name, directly under the session folder (flat — no nesting); normally auto-derived (`ExperimentStore.make_experiment_id()`) but may be overridden by the operator at Start Experiment time (`StartExperimentDialog`'s Folder name field → `ExperimentManager.start_experiment(experiment_dirname=...)`), still contained to a single path segment under the session. `RunRecord.data_file` is stored relative to that folder when the file lives inside it (`ExperimentStore.relativize_data_file()`/`resolve_data_file()`), so the folder can be copied or moved and still resolve; a file saved deliberately outside it stays an absolute path. Every persisted file (`experiment.json`, `session.json`, `gui_state.json`, both `active.json` files) carries a top-level `schema_version` (`models.SCHEMA_VERSION`, currently `2`); a value newer than the running app's is loaded tolerantly but treated read-only (never re-saved). The `active.json` pointer resumes the open experiment across restarts; `ExperimentManager.switch_experiment()` moves between several open experiments without closing the one switched away from. One experiment ↔ one ELN entry. The Experiment tier — as opposed to the **Setup tier** — is what `ExperimentManager.experiment_context()`'s `"experiment"` key holds; empty (`{}`) when none is open. |
| **Experiment index** | `Session.experiments` (`list[ExperimentIndexEntry]`) — a session's enumeration of its own experiment folders: `experiment_id`, `title`, `user_id`, `status`, `created_utc`, `closed_utc`, self-describing via the fixed `experiment_id + "/data"` convention rather than a stored second copy of the data path. Reconciled by `ExperimentManager._reconcile_session_index()` on `start_experiment()`/`close_experiment()`/`switch_experiment()` — the three points an experiment becomes or stops being the one in view — by rescanning `ExperimentStore.list_experiments()` and reading every `experiment.json` found, then replacing the list wholesale (never edited elsewhere), so a session answers "what experiments do I contain and where" straight from `session.json` with no scan for whatever reads it, while the scan itself only runs at those three points. Because it is a full rebuild rather than a per-entry upsert, an experiment folder moved into or out of a session by hand (e.g. handed off to a different user's session to continue the project) is picked up or dropped the next time any experiment in that session opens or closes, and a session that already had experiments on disk before this index existed backfills them all the same way — no separate "move" step, no permanently-stuck-empty index. Each entry's `user_id` is copied verbatim from its `ExperimentRecord` and never re-derived from the session it currently sits in, so a move never rewrites who actually ran the experiment. Flat-only: no nested subfolders. |
| **Setup tier** | The metadata that describes the rig, not any one experiment: which config is active, each VI's **instrument metadata**, and who's logged in. Changes rarely (switching config/instrument description/user), unlike the Experiment tier which changes per run. Not owned by any one L6 class — it's assembled from `core.station.read_instrument_metadata()` + the config's identity (both cached by `ExperimentManager` at construction) and `app_settings.current_user_id()`/`UserRoster` (GUI-level). Surfaced in the GUI through menus (User, Config), not a docked panel — see **User menu**. `ExperimentManager.experiment_context()`'s `"setup"` key holds it, present even with no experiment open. |
| **Instrument metadata** | An optional `metadata:` block per VI in `devices.yaml` (free-text fields — `role`, `manufacturer`, `model`, `notes`, whatever the setup wants to record about what a VI physically is). A setup property like everything else in `devices.yaml`; edited via the Config Editor, never in the running app. Read by `core.station.read_instrument_metadata(config_path)` — YAML-parse only, never imports a driver/VI class, so it's safe to call from the GUI thread. Displayed read-only in `InstrumentInfoDialog` and stamped into every run's `experiment_info["setup"]["instruments"]`. |
| **Run** | One execution of one procedure, producing exactly one HDF5 file. Typed as `RunRecord` (L6): id, procedure, kind (`run`/`probe`), params, data-file path, timestamps, terminal status (`done`/`failed`/`aborted`). Recorded automatically from the Orchestrator's **run manifests**; runs outside an open experiment are not recorded (their HDF5 file still exists, unstamped). |
| **User** | The person measuring — identity, not authentication. `User` records (id, name, email, ORCID, ELN identity) live in the setup-local roster `users.json` next to the app settings, managed by `UserRoster`. Experiments reference a roster `user_id`, and the id/name are stamped into every run's HDF5 `experiment_info`. |
| **Attendance** | The per-experiment attended/unattended flag (`ExperimentRecord.attended`, set via `ExperimentManager.set_attended()`). Governs how much autonomy debug agents get in the agent-native track: gentle recovery actions are reserved for unattended sessions; attended sessions get diagnose-and-report only. |
| **Run manifest** | The dict the Orchestrator emits on `run_started` (once per run, after a successful `initiate()`) and re-emits on `run_finished` (with `finished_utc`, terminal `status` done/aborted/failed, `reason`, `postconditions_unmet`, and `summary` added). Carries `run_id`, `procedure`, `kind` (`run`; probe runs will carry `probe`; `operation` for an operation), `params`, `data_file` (the HDF5 path, captured at start because the procedure closes its file before the run ends; empty for a dataset-less operation), and `started_utc`. `summary` (plan operation-concurrency-and-error-scoping.md §4) is the duck-typed `procedure.run_summary()` result — `{}` for a plain procedure or an operation that does not override it — merged in by the Orchestrator without ever importing `OperationBase` (contract C5); a raising or non-dict override yields `{}` rather than blocking the run. The session layer records runs from these signals; a run whose setup fails emits no manifest. |
| **Session envelope** | `core/plan.py`'s `ExperimentEnvelope` (+ `EnvelopeBound`): per-experiment safety bounds narrower than the config limits, keyed by system VI name. Config `init_params` limits protect the *instrument* (setup property, YAML); the envelope protects the *sample* mounted for one experiment (experiment property, set by the session layer via `Orchestrator.set_experiment_envelope()`). Enforced in the Orchestrator so it binds every writer — targets are validated before dispatch (violation ⇒ the plan is rejected), a manual action on the **Direct action path** is validated the same way on the parameter the **Setpoint-parameter convention** identifies (at submission and again when the tick drains the queue), and each bound with a `state_key` is checked against the VI's live reading every tick: a violation becomes an envelope-origin, critical-severity `Condition` (`core.conditions.envelope_conditions()`, see **System condition**), folded into the same tick's condition list `decide()` consumes, so it drives EMERGENCY unconditionally — exactly like a tripped **Critical safety flag** — since a violation has no per-VI attribution to narrow it to a **Safety hold** instead. |
| **Servicing log** | The L6 framework for per-setup, human-facing logs of servicing events. Each log is one **log kind**; entries are typed records, editable via **entry revisions**, persisted append-only. Independent of experiments; what technical staff consult and maintain. Unification (docs/plans/archive/unified-servicing-log-and-run-recording.md): the legacy split between the **Cryogenics log** kind and the machine-only `operations` stream is replaced by ONE flat `"servicing"` log kind — every entry (a fill, a sample change, a future operation, or a hand-added note) shares exactly the same field table (`entry_kind`, `person`, `start_utc`/`end_utc`, `helium_start_pct`/`helium_end_pct`, `ln2_start_pct`/`ln2_end_pct`, `notes`, `recording`, `origin`) with no kind-specific columns and no `status` field; `origin` (`"machine"`/`"manual"`) replaces the old per-kind `editable=False` machine-stream concept — every entry, of either origin, is addable/editable through the same entry-revision mechanism. Phase 1 landed the kind declaration, store support, and a legacy-migration routine (`migrate_legacy_servicing_log`) that merges `cryogenics.jsonl` + `operations.jsonl` into `servicing.jsonl`, converting an embedded `level_curve` into a **Recording** sidecar. Phase 2 rewires `CryogenicsRecorder` to write ONLY `"servicing"` (one merged entry per finished operation run, He/LN2 levels stamped for every run kind, notes carrying abort/failure reason + unmet postconditions, a **Recording** sidecar when the operation hands one off) and wires `ServicingLogStore.migrate_legacy()` into `cryosoft.main`'s startup; the legacy kinds stay declared (readable, `cryogenics` still manually editable) for any not-yet-migrated setup, but are no longer machine-written. Phase 3 gave the original `SampleChangeOperation` (since split into `SampleLoadOperation`/`SampleUnloadOperation`, sharing `_SampleAccessOperationBase`) a true **Hold phase** (records via `sample()`, ends only on Finish) and generalises the fill's decimating curve into a shared `OperationBase` recorder helper any operation can opt into. Phase 4 unifies the viewer (`gui/servicing_log_page.py`'s `_ServicingLogTable`, docs/plans/archive/unified-servicing-log-and-run-recording.md §4, DONE 2026-07-23): one chronological timeline over the `"servicing"` kind (sorted by parsed `start_utc`, falling back to `created_utc`, newest first — parsed defensively rather than by string order, since hand-edited entries are not guaranteed one ISO 8601 format), filter chips derived from the data's `entry_kind` values (never hardcoded), a row-detail dialog (`ServicingRecordingDialog`) with a lazily-loaded **Recording** plot (tolerant of a missing/corrupt sidecar), and two CSV exports ("Export table as CSV" over the filtered rows, "Export recording as CSV" — time column plus one column per channel) built on plain, Qt-free helper functions (`sorted_servicing_entries`, `distinct_entry_kinds`, `filter_entries_by_kind`, `write_servicing_table_csv`, `load_recording_sidecar`, `write_recording_csv`) so tests never have to drive a file dialog. |
| **Log kind** | One declared servicing-log table: a key (`"cryogenics"`, `"operations"`, or the unifying `"servicing"`), a title, and an ordered field schema (reusing `ParamSpec`). Adding a log kind for a new setup is a declaration + config reference — the storage, revision handling, table view, and add/edit dialogs all follow automatically. The standards-over-one-off-code move, applied to record keeping. |
| **Cryogenics log** | The legacy log kind, superseded by the flat `"servicing"` kind (see **Servicing log**) as of Phase 2 of the unification: one entry per cryogen fill — `person`, `start_utc`, `end_utc`, `helium_start_pct`, `helium_end_pct`, `ln2_filled` (bool), `notes`, `level_curve` (JSON string; `""` for a manual entry or an entry written before this field existed). Historical/legacy only — `CryogenicsRecorder` no longer writes it; it stays declared (readable, still manually addable/editable) purely so a setup that has not yet run the migration keeps its existing entries visible. `ServicingLogStore.migrate_legacy()` (called once from `cryosoft.main` at startup) converts its entries (merged with the matching `operations` entry) into `"servicing"` entries, converting an embedded `level_curve` into a **Recording** sidecar, and renames the original file to `.bak`. |
| **Entry revision** | How editability and trustworthiness coexist: every entry has a stable `entry_id`; an edit appends a new revision (`revised_utc`, `revised_by`) rather than rewriting; a deletion appends a tombstone. The store presents the latest revision per entry; the full history stays on disk. The file itself is never rewritten. |
| **Helium record** | The machine companion to the servicing log: one `(utc, helium_pct, nitrogen_pct)` sample per hour, appended by the recorder from the monitoring tick. Powers the consumption display and start/end-level lookup; not human-editable. |
| **Recording** | A per-run sidecar JSON file under `servicing/<config_name>/recordings/<run_id>.json`, shaped `{"unix_time": [...], "channels": {"<vi>.<value>": [...], ...}}` — the general home for "all system parameters recorded during a servicing run" (docs/plans/archive/unified-servicing-log-and-run-recording.md §3), referenced from its `"servicing"` log entry's `recording` field (`""` if none). `CryogenicsRecorder` (Phase 2) writes it whenever an operation's `run_summary()` hands off a well-formed `"recording"` key in this generic shape. Phase 3 moved the shape's construction onto a shared, decimating, multi-channel recorder helper on `OperationBase` itself (`_record_sample(unix_time, {channel: value, ...})` appends one sample across every declared channel at once; `_recording_dict()` returns the sidecar shape; `_MAX_RECORDING_POINTS`, default 4000, bounds memory via stride-doubling `series[::2]` decimation, shared across every channel and the time axis together) — `HeliumFillOperation` (one channel, `"<level_vi>.helium_pct"`) and `_SampleAccessOperationBase` (the VTI temperature plus every magnet's field, shared by `SampleLoadOperation`/`SampleUnloadOperation`) both use it; a future operation opts in the same way with no recorder changes. Phase 1's legacy migration performs the equivalent one-time conversion for an old embedded `level_curve` JSON string. |
| **Helium fill (operation)** | `procedures/operations/helium_fill.py`'s `HeliumFillOperation` — the first concrete `OperationBase` (plan §8.1): ramps every magnet (`Station.magnet_vi_names()`) to zero field (`initiation_gates()` holds until zero field is confirmed and held), switches the level meter to FAST refresh, samples the helium level once per `sample_period_s` into a bounded in-memory curve (no HDF5 file — plan operation-concurrency-and-error-scoping.md §4), and finishes once the level has held at/above `fill_target_pct` and non-rising for `fill_complete_window_s` (or `max_fill_duration_s` elapses). `standby()`/`abort()` restore SLOW refresh so an aborted fill never leaves the meter in FAST; `postcondition_gates()` verifies that restoration and that the level did not fall below its start value. Tolerates `helium_low` (`tolerated_safety_flags`) — the fill's whole purpose. Configured from the `cryogenics:` block (`core.station.read_cryogenics_config()`); `run_summary()` hands the level curve (in the generic **Recording** shape, `{"<level_vi>.helium_pct": [...]}`) plus start/end level to the Orchestrator's run manifest on finish, and `CryogenicsRecorder` writes it as this run's **Recording** sidecar, referenced from the single **Servicing log** entry it writes for every finished run. |
| **Sample load / Sample unload (operations)** | `procedures/operations/sample_load.py`'s `SampleLoadOperation` and `procedures/operations/sample_unload.py`'s `SampleUnloadOperation` — a pair of concrete `OperationBase` subclasses sharing everything but identity via `procedures/operations/sample_access_base.py`'s `_SampleAccessOperationBase` (originally one class, `SampleChangeOperation`, split so loading and unloading a sample — often hours or days apart — no longer share one long-lived run, freeing the Orchestrator between the two events): "verify the cryostat is safe to open", and the reference **Hold phase** operation (`hold_for_operator = True`, docs/plans/archive/unified-servicing-log-and-run-recording.md §1). `initiate()` commands every magnet (`Station.magnet_vi_names()`) to `standby()` and ramps the configured VTI VI to `target_temperature_K` (default 290 K), and sends `standby` to every measurement VI (`Station.measurement_vi_names()`); no `initiation_gates()`, no switch-VI dispatch. Once the ramps land, `step()` never returns `None` on its own — the run holds while the operator walks through the declared **Operation step** sequence (warm the VTI, close the needle valve, load or unload the sample — the wiki-documented physical procedure, confirmed as one identical step for both load and unload) and `sample()` records *every numeric monitored channel on the station* once per `sample_period_s` (default 10 s) into the shared recorder (see **Recording**), read from `cached_state` rather than live VI calls so a station-wide trace costs no extra bus traffic in the tick path — until the operator clicks Finish or Abort; `run_summary()` hands the accumulated series and the step timeline off as `{"recording": {...}, "steps": [...]}`. Every step is skippable (see **Step skip / override**), including the warm-up. `postcondition_gates()` (evaluated once as the run ends, Finish only) reads only cached state: `zero_field` (every magnet's `magnet_state() == "standby"` — see **Magnet state**; this already covers the switch heater being off wherever a magnet has one, so there is no separate heater gate); `vti_at_target`; and one `step_<key>` gate per declared step, met only when that step was recorded *done*. `vti_at_target` and `step_warm_vti` are deliberately both present and are not the same assertion — the first is a live reading now, the second is whether the warm-up was ever completed rather than skipped. `needle_valve == "manual"` remains the only wired mode, not because the stack lacks the capability (`VTITemperatureControllerVI.set_needle_valve()`/`set_needle_valve_mode()` have existed since 2026-07-26, and its `standby()` already closes the valve) but because the 12 T cryostat's needle valve has no motor: the controller channel exists, commanding it moves nothing, so the operator's confirmation is the only honest verification there is on that setup. An unmet gate never blocks finishing — see **Postcondition gate**. `tolerated_safety_flags` is left empty — neither operation has any business running under an active safety condition. `SampleLoadOperation` configures from `operations.sample_load:`, `SampleUnloadOperation` from `operations.sample_unload:` (both via `core.station.read_operations_config()`); `CryogenicsRecorder` derives each run's servicing-log `entry_kind` (`"sample_load"`/`"sample_unload"`) from the manifest's `procedure` name, so no extra wiring distinguishes the two. |
| **Operator confirmation** | A human attestation an operation's `postcondition_gates()` can gate on when no machine-verifiable capability exists (e.g. `SampleLoadOperation`'s/`SampleUnloadOperation`'s manual needle valve). Today every confirmation is an **Operation step** of kind `operator_ack`: the operation declares it in `steps()`, `confirm(key)` / `confirmed(key)` set and read it, and `Orchestrator.confirm_operation(key)` (mirroring `finish_operation()`) is the GUI's entry point, duck-typed exactly like `finish_operation()`'s `request_finish()`. An unconfirmed key surfaces in the gate name `CryogenicsRecorder` folds into the run's single **Servicing log** entry's `notes` (via `postconditions_unmet`, e.g. `"unmet: step_close_needle_valve"`); a confirmed key leaves no trace beyond the gate simply passing — the legacy `operations` stream's per-field `verified` column is gone with that kind. Contrast **Pre-run toggle**: confirmed post-hoc during a run vs. decided up front, before one starts. |
| **Operation step** | `core/operation.py`'s `OperationStep` (a frozen dataclass: `key`, `label`, `kind`, `skippable`, optional `detail(state)` and `skip_warning(state)`) — one named stage of an operation whose hold phase is a *sequence* rather than a single wait. An operation opts in by overriding `steps()`; `current_step()` is the first step with no recorded outcome, which is what makes the sequence sequential with no extra bookkeeping. Two kinds: `auto_ramp` (the system performs it, e.g. the VTI warm-up, and records it done itself) and `operator_ack` (a physical act the software can neither perform nor verify). `confirm_step(key)` / `skip_step(key)` stamp a `StepRecord` — status, unix time, and a flat snapshot of station conditions at that instant, which is where *non-numeric* monitored values (a needle valve's AUTO/MANUAL mode, a magnet's state) are captured since the numeric **Recording** cannot hold them. `steps_summary()` hands the whole timeline, pending steps included, to `run_summary()`. The Operations panel renders one checklist row per step plus a Confirm/Skip action for the current one, with zero per-operation GUI code. Conformance-checked (unique keys, valid kinds, every step reachable in order). |
| **Step skip / override** | Skipping an **Operation step**: always permitted, always warned about, always recorded. The design premise is that a sample sometimes has to be changed at base temperature, and an operation that refuses to run then does not prevent the sample change — it only means the change happens with no record of it at all. The GUI warns with the live conditions (`OperationStep.skip_warning`), then calls `Orchestrator.skip_operation_step(key)`; the step is recorded `skipped`, its postcondition gate reports unmet, and that lands in the manifest's `postconditions_unmet` and the **Servicing log** notes. A skipped step is never painted as a failure — the panel gives it its own amber icon state, distinct from both met and unmet. Skipping an `auto_ramp` step additionally has to stop the ramp it started, which the operation cannot do itself (while the ramp runs the state is RAMPING, where `step()` is never called, and `stop_ramp()` refuses a VI claimed by an active run): it raises `skip_ramp_requested` and the Orchestrator's RAMPING branch calls `Station.stop_ramps()`, the same hold-in-place `pause_procedure()` uses, leaving the instrument clamped where it reached. |
| **Pre-run toggle** | A per-run override of a config default, decided by the operator *before* Start rather than confirmed after (contrast **Operator confirmation**). An operation declares a class-level `pre_run_toggles: dict[str, str]` (config kwarg name → checkbox label) — e.g. `SampleLoadOperation`'s/`SampleUnloadOperation`'s `disarm_measurement_vis` ("Disarm measurement instruments"), so a run can skip standing by (and claiming) every measurement VI when one is already armed for something unrelated. The Operations panel renders one **persistent** checkbox per declared entry (visible/editable regardless of run state, unlike an operator-confirmation checkbox, which shows only while running), checked by default; its state at the instant Start is clicked is passed to the panel's factory closure as an extra `bool` keyword matching the declared key, merged into the constructed instance's `**config` exactly like a `devices.yaml` value would be — the constructor reads it with the same `config.get(key, default)` call as any other config key, so there is no toggle-specific plumbing beyond the declaration itself. An operation with no declared toggles gets no extra keywords and no card checkboxes. |
| **Readiness condition** | `core/operation.py`'s `ReadinessCondition` (a frozen dataclass: `key`, `label`, `check(state) -> bool`, optional `detail(state) -> str`) — one live checklist row the Operations panel renders for an operation, declared via `OperationBase.readiness_conditions() -> tuple[ReadinessCondition, ...]` (plan §12, default `()`). `check`/`detail` are pure reads against the Orchestrator's per-tick state snapshot (`{vi_name: {field: value}}`) — no hardware access, no extra poll. E.g. `HeliumFillOperation`'s `zero_field` row; `_SampleAccessOperationBase`'s (shared by `SampleLoadOperation`/`SampleUnloadOperation`) `zero_field` row followed by one row per declared **Operation step**, so the panel's checklist *is* the sequence the operator is working through. |
| **Next due** | `core/operation.py`'s `NextDue` (a frozen dataclass: `due_unix: float \| None`, `text: str`) — an operation's schedule prediction, returned by `OperationBase.next_due(context) -> NextDue \| None` (plan §12, default `None` — no schedule). `context` is a GUI-assembled dict (`"state"`, `"now_unix"`, `"consumption_rate_pct_per_h"`); an operation must not import the session layer to compute its own rate (contract C12), which is why the rate is passed in rather than computed in `next_due()`. `HeliumFillOperation.next_due()` predicts time-to-`helium_warning_pct` from the measured consumption rate; `SampleLoadOperation`/`SampleUnloadOperation` have none. |
| **config_key** | `OperationBase`'s class attribute (`str`, default `""`, plan §12) naming the `operations:` config-block key this operation class should be built from generically — e.g. `SampleLoadOperation.config_key = "sample_load"` matches an `operations.sample_load:` block (`SampleUnloadOperation.config_key = "sample_unload"` likewise). The Operations panel maps every declared `operations:` key to the discovered class whose `config_key` matches (unknown keys log a warning and are skipped); a non-empty `config_key` must be unique across operations (checked by `tests/test_conformance.py`). The helium fill leaves it `""` — it is wired from `cryogenics:`, not the generic `operations:` lookup. |
| **Sweep axis** | `core/sweep_builder.py`'s `SweepAxis` dataclass + `sweep_axis_param_specs()` + `build_axis_sweep()` — the systematic, low-code way a Procedure gets sweep-shape flexibility (linear range / piecewise segments for a fine subfield / custom CSV, each optionally with hysteresis). A Procedure declares one `sweep_axis = SweepAxis(key=..., unit=..., data_key=..., description=..., default_start=..., default_end=..., default_steps=...)` class attribute (see `FieldSweep`, `TemperatureSweep`); `BaseProcedure.__init_subclass__` merges its seven hidden parameters (`{key}_mode`, `{key}_start`, `{key}_end`, `{key}_steps`, `{key}_segments`, `{key}_csv_path`, `{key}_hysteresis`) into `cls.parameters`, and the default `_build_sweep_array()` delegates to `build_axis_sweep()` — no per-procedure sweep-array code is needed. `gui/sweep_axis_widget.py`'s `SweepAxisWidget` renders the matching mode-selector form (Linear / Segments / CSV + a hysteresis checkbox) automatically in `ProcedureWindow`; a new sweep procedure never needs its own GUI code, only the `sweep_axis` declaration. |
| **Control contract** | The frozen, JSON-safe message families in `core/events.py` that the Orchestrator and its clients exchange: a client sends a `Command`, gets back exactly one `Verdict`, and sees the consequences as `Event`s (`StateChange`, `StatusSnapshot`, `StationInfo`, `Readings`, `Datapoint`, `RunStarted`, `RunFinished`, `QueueChanged` — each carrying `seq`, `ts`, a `kind` discriminator for `event_from_json()`, and where relevant `request_id` and `actor`). The engine has exactly two clients, the GUI and the agent, and the contract is declared ONCE so both are rendered from it — neither can offer an action the other cannot see, and each reflects what the other did, because every message names its **Actor**. Every type is a frozen dataclass with JSON-safe fields and `to_json()`/`from_json()`, round-tripped by conformance, which is what lets the same declaration cross a thread boundary and later a process boundary with no second contract. |
| **Actor** | `core/events.py`. Who acted: `kind` (`operator` \| `agent` \| `system`), `id`, `role`. Carried on every `Command` and on every event it causes, so accountability is a value rather than an ambient fact — the status bar can say "paused by agent", the queue shows who queued a run, and an agent's self-confirmation is never byte-identical to the physicist's. `OPERATOR` is the sentinel every public entry point defaults to, so no existing call site changes. |
| **Command** (control contract) | `core/events.py`. A client's request for the engine to act: `name` (a `CommandName` — the enumeration of every public Orchestrator command, each value the name of the method implementing it), `actor`, JSON-safe `args`, `request_id`, `issued_at`. Distinct from `core/plan.py`'s **Command**, which is one method call a procedure hands the Orchestrator to dispatch on a VI. Conformance diffs `CommandName` against the Orchestrator's public methods in both directions; reads (answered from a client's `StatusSnapshot`) and `shutdown()` (process lifecycle, `main.py`'s) are exempt by name with a rationale each. |
| **Verdict** (control contract) | `core/events.py`. The engine's single answer to one `Command` — every refusal answers, since a broadcast signal is not something an agent can await: `request_id`, `command`, `code` (`OK`, `BLOCKED_STATE`, `BLOCKED_CLAIM`, `BLOCKED_FAULT`, `BLOCKED_LIMIT`, `BLOCKED_ENVELOPE`, `BLOCKED_ROLE`, `FAILED`), `actor`, human-readable `reason`, optional structured `detail`, optional `result`, `seq`, `ts`; `ok` is derived from `code`. A client decides from the code and the `detail` dict, NEVER by parsing `reason` — which is why the `@control` limit wrapper attaches `param`/`value`/`lo`/`hi`/`limit_name` to the `CryoSoftSafetyError` it raises while leaving the message text unchanged for the banner. Distinct from `core/conditions.py`'s **Verdict**, the enforcement decision `decide()` computes from a set of system conditions. |

## GUI concepts

| Term | Definition |
|---|---|
| **Quadrant layout** | The fixed 2x2 grid both `MonitorWindow` and `ProcedureWindow` use below their header/banner: a `main_splitter` (`QSplitter(Horizontal)`) containing `left_splitter` and `right_splitter` (each `QSplitter(Vertical)`), giving four panes whose boundaries are draggable but which can never be closed, detached, or floated — unlike the `QDockWidget` layout it replaced, which let panels overlap, hide each other, and become glitchy to resize. In `MonitorWindow`: top-left Instruments (scrollable 2-column `InstrumentPanel` grid holding EVERY VI — system/level plus role-tagged measurement and switch cards), top-right Trends, bottom-left the `ExperimentInfoPanel` (Experiment tier: status/Start-Close/attendance/findings, sample fields, eLab status), bottom-right the optional `OperationsPanel`. In `ProcedureWindow`: top-left the parameter form (filling the quadrant, not capped at a fixed height), top-right the Queue, bottom-left/right Plot 1/Plot 2. Splitter proportions persist via `QSettings` alongside window geometry, restored defensively — see `MonitorWindow._restore_splitter_state()`'s shape-mismatch guard, which discards a restored blob whose orientation/child-count doesn't match (protects against a stale value under a reused settings key, e.g. from a since-removed earlier layout). |
| **Operations panel** | `gui/operations_panel.py`'s `OperationsPanel` (plan §12) — `MonitorWindow`'s bottom-right "Operations" selector entry (renamed from "Cryogenics", which it absorbs, not replaces), available when cryogenics is enabled OR the `operations:` config is non-empty. An optional cryogenics status section (levels/consumption/plot, gated on `cryogenics:`) followed by one generic `OperationCard` per available operation — the helium fill (iff cryogenics is configured) plus one per `operations:` config block whose `config_key` matches a class from `gui/procedure_discovery.py`'s `discover_operations()`. Answers, at a glance: what state is the setup in, is it ready right now for operation X, and when will X next be needed? |
| **OperationCard** | `gui/operations_panel.py`'s `OperationCard` — one operation's fully generic panel widget (plan §12): a header (name + **next due** line, hidden when `next_due()` returns `None`), one row per **readiness condition** (colored ✓/✗ icon, label, live detail text, re-evaluated every `on_states_updated` tick), an operator-confirmations row (hidden unless this operation is the active run and declares `operator_confirmations`), a **ready banner**, and a start/finish button. Built from one *display* operation instance (constructed once, for readiness/next-due/labels only, never run) plus a panel-supplied *factory* closure that builds a FRESH instance per actual run — this is what keeps the class free of any per-operation code. |
| **Ready banner** | `OperationCard`'s prominent success message (plan §12), using the operation's `ready_message` class attribute (e.g. `"Ready — sample can be taken out"`; empty = no banner, ever). For a plain operation (`hold_for_operator = False`, e.g. the helium fill): shown once a run finishes `done` AND every current **readiness condition** holds. For a **Hold phase** operation (`hold_for_operator = True`, e.g. the sample change, docs/plans/archive/unified-servicing-log-and-run-recording.md §1): ALSO shown mid-run, the instant every condition holds — the run being still active does not withhold it, since "ready" answers "you may act now", true before Finish. Clears the instant a condition stops holding or a new run starts (`request_finish`/`run_started`) — it never shows a stale "ready" after the setup has moved on. |
| **Hold phase** | docs/plans/archive/unified-servicing-log-and-run-recording.md §1: an operation whose `step()` never returns `None` on its own once its setup work (ramps, etc.) is done — the run stays active indefinitely, recording via `sample()`, until the operator clicks Finish (`Orchestrator.finish_operation()` → `request_finish()` → the next `change_sweep_step()` returns `None`, exactly the existing graceful-finish mechanism). Declared via `OperationBase.hold_for_operator: bool = False`; `_SampleAccessOperationBase` (shared by `SampleLoadOperation`/`SampleUnloadOperation`) is the only operation base that sets it `True` today — the physical sample load/unload happens during the hold, not after some fixed condition, so the run's `started_utc`/`finished_utc` span the true servicing window rather than just the ramp-down. The Operations panel's **Ready banner** reads this flag to decide whether to show mid-run. |
| **User menu** | `MonitorWindow`'s leftmost menu (`monitor_window.py`), holding **Setup tier** concerns: `Log in as…` (opens `setup_dialogs.LoginDialog`, identity only — no password), `Load Session…` (opens `open_experiment_dialog.OpenExperimentDialog` to switch the open L6 experiment via `ExperimentManager.switch_experiment`/`MonitorWindow._switch_experiment`), `Resume Session…` (opens `session_dialogs.ResumeSessionDialog` to pick or create the **Session** — the folder tier holding multiple experiments — and persists the pick as active via `SessionStore.set_active(user_id, session_id)`; deferred-until-restart, since the running `ExperimentStore` stays fixed to whichever session was active at launch, same precedent as the old sessions-root relocate action it replaces), and `New Session`/`Save Session Now` (operate on `form_autosave`). Nobody-logged-in resolves to the **Guest user** for `Resume Session…`'s listing, since sessions now nest under a concrete `user_id`. Named "User", not "Session" — a "Session" menu existed here once, before "Session" was freed to name the new folder tier and the old L6 manager was renamed `SessionManager`→`ExperimentManager`; reusing "Session" for this menu today would recreate exactly the collision that rename resolved (see `docs/plans/session-tier-and-terminology.md`). |
| **Current user (login)** | `app_settings.current_user_id()`/`set_current_user_id()` — identity only, no password, persisted in `QSettings` like the active config. Governs which per-user `form_autosave` file (`app_settings.autosave_file_path(user_id)`, under `sessions/<user_id>.json`) `ExperimentInfoPanel`'s sample fields load from/save to, so switching users switches what's remembered instead of one person's fields overwriting another's. `MonitorWindow._switch_user()` does the save-outgoing/load-incoming swap; the header's `current_user_label` reflects it. Independent of any experiment's `user_id` (`ExperimentRecord.user_id`, assigned at Start Experiment) — logging in does not open or require an experiment. |
| **Form autosave** | `cryosoft/gui/form_autosave.py` — the GUI's persisted form content (sample metadata, data dir, last procedure + params, run queue), written to one JSON file so a reopened app restores what the physicist typed. Historically named the "session model" (`gui/session.py`); renamed so **session** unambiguously means the L6 Session Management concept. Its class (`FormAutosaveState`, formerly `SessionState`) was renamed too; the on-disk `last_session.json` filename is unchanged, so existing autosave files keep loading unchanged. |
| **MonitorHistory** | `cryosoft/gui/monitor_history.py`. A Qt-free, pure-Python ring buffer that accumulates flattened `{vi_name}_{field_name}` time-series history from `Orchestrator.states_updated`, one bounded `deque` per key, for the Trends panels' plots. |
| **Trends grid** | 1–4 `TrendPlotPanel`s arranged in the Trends quadrant's `QGridLayout`, auto-recomputed to `ceil(sqrt(N))` columns on every add/remove (1→1x1, 2→2x1, 3–4→2x2). The quadrant's "Add trend plot" button adds panels up to a cap of 4 (disabling once reached); each panel's own remove button drops it, never below a floor of 1. The two default panels opportunistically select a temperature/level reading (not a setting/rate field) once `MonitorHistory` has data. Each panel's Y-variable `QComboBox` uses `SizeAdjustPolicy.AdjustToContents` and a layout stretch factor of 1 so long flat keys (e.g. `temperature_sample_temperature`) get first claim on the row's width, ahead of the time-window selector and remove button. |
| **LifecycleToggleButton** | `cryosoft/gui/lifecycle_toggle.py`. A single state-dependent button + status glow dot replacing the old separate Initiate/Standby `QPushButton` pair, shared by `InstrumentPanel` (in its custom header row next to the VI name, since `QGroupBox` can't embed a widget next to its native title), present on every card. Clicking only submits the opposite action (`"initiate"`/`"standby"`) via a callback — it never flips state optimistically. `set_initiated(bool)` is the only thing that changes the displayed state (text, icon, dot colour), and both call sites wire it to `Orchestrator.action_succeeded`, so the glow reflects confirmed instrument state, not a hopeful click. |

## Development harness

| Term | Definition |
|---|---|
| **Layer contracts (C1–C12)** | The machine-checked import rules in `pyproject.toml` `[tool.importlinter]`. Run with `make contracts`. A broken contract means the change crosses a layer boundary — route through the proper interface instead of editing the contract. C9/C10 isolate the troubleshoot toolbox in both directions; C11/C12 place the session layer (L6) between core and the GUI. |
| **Troubleshoot toolbox** | `cryosoft/troubleshoot/` — the diagnostic package (engine + CLI) for commissioning and debugging a setup. A leaf entry point beside the stack, like `main.py`: it may import drivers and the Station's config helpers; nothing in cryosoft imports it. Run while the main app is closed (serial ports are exclusive-open). CLI: `python -m cryosoft.troubleshoot scan/probe/check/methods/idn/read/write/query/send`, each one-shot with `--json` and exit code 0/1; `write`/`query`/`send` are the permission-gated verbs. Every invocation appends to the transcript `cryosoft/logs/troubleshoot.jsonl`. |
| **Fault taxonomy / FaultCode** | The stable machine-readable outcome codes every troubleshoot probe returns (`OK`, `CONFIG_INVALID`, `ADDRESS_NOT_ON_BUS`, `OPEN_FAILED`, `NO_RESPONSE`, `WRONG_IDN`, `GARBLED_RESPONSE`, `DRIVER_ERROR`). Codes are API for the triage skill: never renamed, only extended. |
| **Config preflight** | `check_config()` in the troubleshoot engine: for every `real_drivers` entry, verify bus presence, construct the driver, call `get_idn()`, and optionally match the config's `expect_idn` substring. The "is everything connected?" check run before a cooldown. |
| **Driver bench** | `DriverBench` in the troubleshoot engine: wraps one driver instance for method introspection, read/write-gated calls, and raw SCPI query/send. The primitive behind driver development and per-instrument debugging. |
| **`expect_idn`** | Optional key on a `real_drivers` entry in `devices.yaml`: a case-insensitive substring the instrument's `get_idn()` reply must contain. Lets the preflight detect swapped addresses/cables (`WRONG_IDN`). |
| **`get_idn()` (driver contract)** | Every driver — sim and real — exposes `get_idn()` taking no arguments, returning an identification string. Pre-SCPI Oxford instruments implement it with their native `V` command. Enforced by conformance. |
| **setup.md** | Per-config ground-truth document (`<config dir>/setup.md`): instrument purposes, wiring notes, dated known quirks, per-setup safe-testing limits. Written once during commissioning (human-confirmed), maintained by agents after every diagnosis. Template in `.claude/skills/setup-commission/references/`. |
| **Safe-testing ladder** | The excitation discipline for diagnostics (`.claude/skills/setup-supervisor/references/safe-testing.md`): L0 passive → L1 zero-excitation set/read-back → L2 minimal excitation (≤10 mA magnet lead current, ≤1 nA precision sources) → L3 operational values (human-confirmed state only). Instruments are not code: damage is irreversible. |
| **Incident report** | `cryosoft/logs/incidents/YYYY-MM-DD-<slug>.md` — the structured "cannot conclude" exit of the setup-supervisor skill (evidence table, layers ruled out, hypothesis with confidence, recommended next steps). A good report is a successful outcome; a guess is not. |
| **Conformance tests** | `tests/test_conformance.py`. Auto-discover every driver, VI, procedure, and config and check they follow their interface contracts. A new module is covered automatically, with no test-writing needed. |
| **`make check`** | The blocking quality gate (lint + contracts + tests). Run it before declaring any work done; CI runs exactly the same targets. |
| **`hardware` marker** | Pytest marker for tests needing physical instruments. Excluded by `make test` and CI; run manually at the cryostat. |
| **LOGBOOK.md** | The running development log at the project root (newest first, not git-tracked). Every work session — human or agent — ends by prepending an entry. |
